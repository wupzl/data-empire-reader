第一幕：一秒钟，一万道命令

公元 2026 年，数据大陆。

在大陆中央，有一个名为 Spring 王国 的小国。

国王名叫 Java，宰相名叫 Spring Boot。

王国有一座巨大的交易城，名为 MySQL。

城内存放着所有臣民的账户、订单、商品与库存。

每天，王国都会收到来自各地的请求。

有的请求是查询商品。

有的请求是创建订单。

有的请求是支付。

有的请求是领取优惠券。

王国的运转十分稳定。

直到某一天。

一位商人找到国王。

“陛下，我们准备举行一场史无前例的促销活动。”

“预计有多少人参加？”国王问。

“一百万人。”

国王并不在意。

“一百万人又如何？我们的数据库能够存储上亿条记录。”

商人摇了摇头。

“陛下，我说的不是一百万人注册。”

“而是活动开始时，可能有一万人在同一秒内发起请求。”

宫殿瞬间安静。

宰相 Spring Boot 脸色一变。

“陛下，这不是存储问题。”

“这是战争。”

第二幕：什么是高并发？

国王召集了帝国所有工程师。

首席架构师拿出一张图纸。

“陛下，您需要先理解两个概念。”

“并发（Concurrency）与并行（Parallelism）。”

他在地上画出两座城门。

并发：一个守卫交替处理多个请求

通过调度交替推进多个任务，不代表它们在同一瞬间都在执行。

并行：多个守卫同时处理不同请求

多个处理核心真正同时执行任务。并发系统可以包含并行执行。

架构师解释道：

“假设一名士兵需要十秒钟处理一份公文。”

“如果十份公文接连送来，他可以在不同公文之间切换，这叫并发。”

“如果安排十名士兵，同时处理十份公文，这叫并行。”

国王思索片刻。

“那么，高并发就是有很多人在同一时间请求我们的系统？”

“基本正确。但是还需要更加精确。”

“我们需要衡量系统究竟承受多大的压力。”

架构师写下三个指标。

QPS、TPS、RT。

第三幕：QPS、TPS 与 RT

架构师指向城门。

“陛下，假设一秒钟内，有 10,000 次查询抵达王国。”

“那么我们的查询吞吐量就是 10,000 QPS。”

QPS（Queries Per Second） 通常表示每秒查询请求数，Web 系统中也常被用来描述请求吞吐量，但不同监控系统对 query 的定义可能不同。

“如果每秒成功完成 3,000 笔交易呢？”

“那么在每笔交易被定义为一个业务事务的前提下，TPS 就是 3,000。”

TPS（Transactions Per Second） 表示每秒处理的事务数。

注意，一笔业务交易不一定等于一次 HTTP 请求，也不一定等于一次数据库事务。

国王又问：

“如果有些人等了很长时间才得到回应，我们又该如何衡量？”

“这就要看 RT。”

RT（Response Time） 是请求响应时间，也称延迟。

一名臣民请求查看商品：

  • 20ms 返回：体验很好。
  • 200ms 返回：通常仍然比较流畅。
  • 2s 返回：可能已经明显感觉到等待。
  • 10s 返回：用户可能直接放弃。

这些只是直观示例，实际性能目标取决于业务场景、网络与设备。

架构师补充：

“还有一个指标比平均响应时间更容易暴露问题。”

“叫作 P99。”

国王皱眉。

“什么意思？”

“假设我们记录了 10,000 个请求的响应时间并排序。”

“P99 约表示 99% 的请求响应时间不超过该数值，还有约 1% 更慢。”

“如果平均 RT 是 100ms，但 P99 达到 5 秒，说明仍然有不少用户会遭遇严重延迟。”

“陛下，仅仅提高 QPS 并不意味着系统一定更好。”

“如果一秒可以接收十万个请求，但其中八万个超时，那么这种繁荣毫无意义。”

第四幕：一条神秘公式——利特尔法则

国王终于明白了。

然而，他又提出一个问题。

“假设王国一秒能够完成 1,000 个请求，每个请求平均耗时 0.2 秒，那么系统里平均同时有多少个请求？”

架构师微微一笑。

“这就是高并发领域著名的 Little's Law（利特尔法则）。”

他在黑板上写道：

L=λW L=\lambda W

其中：

  • LL：系统内平均请求数量。
  • λ\lambda：长期平均完成吞吐率。
  • WW：平均请求在系统内停留的时间。

代入数字：

L=1000×0.2=200 L=1000\times0.2=200

“陛下，在符合稳态等适用条件时，系统中平均存在约 200 个尚未完成的请求。”

国王恍然大悟。

“也就是说，如果请求越来越慢，即使吞吐量不变，系统内积压的请求也可能越来越多？”

“正是如此！”

“这就是为什么高并发系统特别害怕响应时间恶化。”

第五幕：第一次灾难——线程耗尽

促销当天终于到来。

上午十点整。

“活动开始！”

一万名臣民同时冲向城门。

第一秒。

城门守卫 Tomcat 还在努力工作。

第二秒。

大量请求排队。

第三秒。

有些请求迟迟得不到响应。

监控平台开始报警。

“陛下！线程池的工作线程已经全部占用！”

“数据库连接池也快耗尽了！”

“请求超时数量正在快速增加！”

国王愤怒地质问：

“为什么会这样？”

架构师走进大殿。

“因为我们的处理模式存在瓶颈。”

他画出一段 Java 代码：

@GetMapping("/product/{id}")
public Product getProduct(@PathVariable Long id) {
    return productService.getById(id);
}

“陛下，假设这个接口使用传统 Spring MVC 阻塞式处理。”

“一名平台线程接到请求后，需要等待数据库查询完成。”

“数据库没返回时，这名线程也许并没有使用 CPU 进行计算，但它仍然被占用。”

“当请求持续涌入，线程池达到上限，后续请求就需要等待或被拒绝。”

国王问：

“那我们增加线程不就行了？”

“不一定。”

“线程不是免费的。”

“线程需要内存、调度资源；线程过多还可能增加上下文切换开销。”

“更关键的是，如果真正的瓶颈在数据库，增加线程可能只会让更多请求挤到数据库门口。”

架构师在城墙上写下第一条法则：

高并发优化不是无止境地增加线程，而是识别瓶颈、减少等待、控制资源消耗，并让系统在过载时仍然可控。

国王不愿放弃。

“既然一座城门不够，那就建十座！”

十台应用服务器被迅速部署。

架构师在城门前设立一座新的指挥塔。

名字叫作：

Nginx。

大量客户端请求

Nginx 负载均衡

分发请求、反向代理、健康检查等

Java 1

MySQL 数据库

共享持久化存储

国王满意地点头。

“现在是不是能够承受十倍流量了？”

架构师摇头。

“未必。”

“应用服务器增加十倍，不意味着数据库吞吐量增加十倍。”

“原本一千个请求访问数据库，现在可能变成一万个。”

“数据库反而可能更快崩溃。”

“而且，如果服务实例内部保存了用户登录状态或关键业务状态，扩容之后还可能出现状态不一致的问题。”

“所以我们必须继续改革。”

第七幕：Redis——建立帝国的高速粮仓

架构师带着国王来到 MySQL 城外。

“陛下，我们每一次查商品，都要进入 MySQL 城。”

“但很多商品数据并不会频繁变化。”

“为什么不把经常访问的数据放到城门外？”

国王问：

“城门外？”

“不错。建立一个高速粮仓。”

“它叫作 Redis。”

第八幕：库存战争——最后一件商品卖给了两个人

傍晚，帝国迎来了更严重的危机。

有一件限量商品。

库存只有一件。

两名顾客，张三和李四，同时发起购买请求。

程序原本这样写：

int stock = queryStock(productId);

if (stock > 0) {
    deductStock(productId);
    createOrder(userId, productId);
}

张三查询库存。

结果：1。

李四查询库存。

结果：1。

张三通过检查。

李四也通过检查。

最后，两人都尝试扣减并创建订单。

“陛下！”

库存官员冲进王宫。

“发生了超卖风险！”

国王震怒：

“库存明明只有一件，为什么两个人都能通过检查？”

架构师解释：

“因为 查询与扣减并不是一个原子操作。”

“多个线程同时执行时，它们可能看到相同的旧数据。”

“这叫作典型的竞态条件（Race Condition）。”

“该如何解决？”

“方法不止一种。”

“我们可以使用数据库条件更新、事务与锁。”

“也可以在满足条件时使用 Redis Lua 脚本执行原子校验与扣减，再通过消息队列完成后续履约。”

他先写下最简单的数据库方案：

UPDATE product
SET stock = stock - 1
WHERE id = 1001
  AND stock > 0;

“这条 SQL 中，检查库存与扣减库存由同一条条件更新完成。”

“如果影响行数为 1，表示成功扣减。”

“如果影响行数为 0，说明库存不足，或者商品不存在。”

“对于单条库存记录，这已经能够防止并发扣减导致库存变成负数。”

国王疑惑：

“那是不是不需要 Redis 了？”

“如果流量和业务复杂度不高，确实没必要为了高并发而强行引入 Redis。”

“但如果一秒有数十万次抢购请求直接争夺同一行库存，数据库锁竞争可能会成为瓶颈。”

“我们就需要更加复杂的方案。”

第二章预告：《Redis 要塞——十万请求与最后一张优惠券》

图片来源：Privacy Quest

下一章，帝国将迎来真正的秒杀战争。

我们会继续保持完整小说叙事，同时深入讲解：

  1. 高并发秒杀架构：为什么 10 万 QPS 不应该全部进入 MySQL。
  2. Redis 库存扣减：DECR、Lua 原子操作、为什么 GET + SET 不安全。
  3. 分布式锁：SET NX、锁过期、误删、Redisson，以及什么时候根本不需要锁。
  4. 幂等性：如何防止同一用户重复领取优惠券。
  5. RabbitMQ 削峰填谷：为什么消息队列不能凭空提升数据库处理能力。
  6. 异步履约：消息丢失、重复消费、事务一致性、补偿机制。
  7. 千万级数据挑战：当订单量达到一亿条，索引、分页、分库分表为何逐渐出现。

而在未来的大数据篇，故事将从“如何同时处理大量请求”，转向“如何处理海量数据”，逐步引出 Hadoop、HDFS、MapReduce、Spark、Flink、Kafka、Hive、ClickHouse、OLAP、实时计算，以及 Lambda/Kappa 架构。

两条主线的核心区别是：

  • 高并发：大量请求同时到来，系统如何保证吞吐量、延迟、正确性和可用性？
  • 大数据：数据规模巨大或持续高速产生，系统如何高效存储、计算、分析并提取价值？

二者经常结合，但不是一回事：千万 QPS 的简单读取业务未必需要 Spark；数百 TB 的离线数据分析也未必涉及高并发请求。
