上一章，Spring 王国遭遇了亿级数据危机。MySQL 巨城开始不堪重负，B+ 树骑士团、分库分表、读写分离和 ClickHouse 分析城相继登场。

然而，首席架构师很快发现，真正的海量数据远不止一亿条订单。

当数据从 GB 膨胀至 TB，再从 TB 膨胀至 PB，帝国将面对一个更加根本的问题：如果一台计算机根本无法高效完成任务，我们能否让一千台计算机共同完成？

本章将沿着一个真实的工程问题，从最基础的分布式思想出发，逐渐深入 HDFS、NameNode、DataNode、YARN、MapReduce、Shuffle、数据倾斜与容错机制。

第一幕：一百 TB 的秘密档案

数据大陆，公元 2027 年。

距离 MySQL 巨城的危机已经过去半年。

Spring 王国再次迎来了繁荣。

交易系统运行稳定。

Redis 要塞抵挡了大量热点请求。

RabbitMQ 军团保证异步任务不断向前推进。

MySQL 负责交易事务。

ClickHouse 分析城负责大规模统计。

一切似乎已经步入正轨。

直到某个清晨。

帝国情报总管带来一道新的命令。

“陛下，我们想分析全国用户过去五年的行为日志。”

国王 Java 放下手中的咖啡。

“有多少数据？”

“一百 TB。”

“多少？”

“一百 TB。”

整个大殿陷入死寂。

国王转头看向首席架构师。

“我们的 MySQL 不是已经能够处理亿级数据了吗？”

架构师摇了摇头。

“陛下，这次不是简单的订单点查。”

“我们需要扫描五年的日志，统计不同地区的用户行为，分析访问路径，提取关键特征。”

“而且，这只是第一次计算。”

“未来每天还会产生数 TB 的新数据。”

国王皱起眉头。

“那就买一台更强大的服务器。”

“给它一 TB 内存，一百 TB 硬盘，一百二十八个 CPU 核心！”

架构师没有立刻回答。

而是在黑板上写下一句话。

单机性能可以不断提高，但扩展成本、硬件上限与故障风险不会因此消失。

一、100 TB 到底有多大？

“陛下，我们先做一个简单的计算。”

“假设有 100 TB 数据，需要全部扫描一遍。”

“我们暂时忽略文件系统、解析和计算开销，只计算读取时间。”

假设顺序读取速度为 500 MB/s，以十进制单位估算：

T=100×106 MB500 MB/s T=\frac{100\times10^6\text{ MB}}{500\text{ MB/s}}

T=200000 s≈55.6 小时 T=200000\text{ s}\approx55.6\text{ 小时}

国王震惊。

“只是读一遍，就可能需要两天多？”

“在这个假设下，是的。”

“而真实任务还需要解压、解析、过滤、聚合、排序，甚至多次扫描。”

“当然，具体时间与存储类型、并行度、缓存、压缩率和访问方式有关。这不是所有单机的实际速度。”

“但它足以说明一个问题。”

“我们需要并行读取。”

二、纵向扩容与横向扩容

架构师展示了两种方案。

纵向扩容 Scale Up

图片来源：The Agentic SRE: Why Autonomous Stacks Will Break Your Cloud (And How To Fix It) | by Damian Figiel | Mar, 2026 | Medium

给一台机器增加 CPU、内存、磁盘和 I/O 能力。

简单直接，但存在单机资源与成本上限。

横向扩容 Scale Out

图片来源：Intra data center | Solutions | EXFO

增加多台机器，让它们共同存储和计算。

具备水平扩展空间，但需要协调、通信与故障处理。

国王恍然大悟。

“原来如此。”

“一台机器读不动，我们就让一百台机器一起读。”

“正是。”

“这就是分布式大数据处理的基本思路之一。”

“不过，陛下，新的问题也随之而来。”

“什么问题？”

“谁负责把数据分给这一百台机器？”

“如果其中一台突然坏了怎么办？”

“如果有些机器干得快，有些机器干得慢怎么办？”

“如果我们需要把一百台机器的结果合并，又该如何协调？”

架构师望向北方。

“解决这些问题的技术，正是我们即将拜访的 Hadoop 帝国。”

第二幕：Hadoop 帝国——三大军团

在数据大陆北方，有一个庞大的联邦。

它的名字叫作：

Hadoop。

这不是一座单独的城市。

而是一套由多种组件构成的大数据基础设施。

帝国最重要的三大军团分别是：

Hadoop 核心架构

层次 组件 职责
存储 HDFS 大文件分块，分散保存到多台机器
资源管理 YARN 资源分配、应用调度与运行管理
计算 MapReduce 拆分计算任务，处理并聚合结果

配合关系：MapReduce 读取 HDFS 中的数据；在 YARN 上运行时，由 YARN 协调其执行资源。

国王问：

“他们有什么关系？”

架构师回答：

“HDFS 像仓库军团。”

“YARN 像调兵遣将的军事指挥机构。”

“MapReduce 像具体的作战战术。”

“我们先拜访仓库军团。”

第三幕：HDFS——将巨大的卷宗切成碎片

Hadoop 帝国边境。

国王来到一座巨大的仓库。

一名管理员正试图把一份庞大的文件搬进去。

文件名：

access_log_2027.txt

文件大小：

1 TB。

普通仓库无法轻松容纳和处理。

于是 HDFS 的指挥官走了出来。

“把它拆开。”

国王一愣。

“拆开？”

“没错。”

“一个大文件，在 HDFS 中会被划分成多个 Block。”

一、Block：数据块

假设我们使用 128 MiB 的 Block 大小。

那么对于一个约 1 TiB 的文件，理论上需要：

1024×1024128=8192 \frac{1024\times1024}{128}=8192

即大约 8192 个数据块。

注意：这里使用的是二进制存储单位 TiB 和 MiB。HDFS 的 Block 大小可配置，并非所有集群都固定为 128 MiB。

国王惊讶。

“8192 个数据块？”

“然后呢？”

“然后，我们把这些数据块分散存储到不同的 DataNode 上。”

HDFS 文件分块示意

② 副本放置：逻辑块与物理节点是两层关系。

逻辑块 DataNode 1 DataNode 2 DataNode 3
Block 0 副本 副本 副本
Block 1 副本 副本 副本
Block 2 副本 副本 副本
Block 3 副本 副本 副本

本表仅以三个节点、每块三副本说明存储关系；实际节点选择与机架放置由 HDFS 策略决定。分块解决文件拆分，副本解决同一块的冗余保存，两者不要混淆。

二、为什么 Block 要设计得比较大？

国王好奇地问：

“为什么不把一 TB 文件切成几亿个极小的数据块？”

指挥官笑了。

“陛下，数据块不是越小越好。”

“假设每个 Block 只有 4 KB。”

“一个 TB 级文件会被拆分成数量极其庞大的小块。”

“每个 Block 都需要相应的元数据管理。”

“数量过多还会造成任务调度开销。”

“而较大的 Block 通常更适合大文件的顺序读取和吞吐型工作负载。”

“当然，Block 太大也可能影响并行任务的切分粒度。”

“这是工程权衡。”

第四幕：NameNode——掌管全帝国地图的总指挥

国王望着散落在各处的数据块。

“如果我要读取文件，怎么知道第 100 个 Block 在哪台机器？”

仓库指挥官说道：

“您需要询问 NameNode。”

一、NameNode 负责什么？

“NameNode 是 HDFS 的元数据管理核心。”

“它负责维护文件目录结构、权限、文件与 Block 的映射，以及 Block 位置信息等。”

国王问：

“那它是不是负责存储所有文件内容？”

“不是。”

“真正的数据块存储在 DataNode 上。”

例如：

文件：/logs/2027/access.log

Block 001
  DataNode A
  DataNode B
  DataNode C

Block 002
  DataNode B
  DataNode D
  DataNode E

“NameNode 知道这些 Block 的位置。”

“客户端先与 NameNode 交互获取所需元数据，再直接与相关 DataNode 传输文件数据。”

HDFS 客户端读取数据

二、FsImage 与 EditLog

NameNode 还需要记住文件系统的状态。

架构师解释：

“这就涉及两个重要概念。”

FsImage：文件系统命名空间元数据的持久化检查点映像。

EditLog：记录命名空间变更操作的编辑日志。

“NameNode 可以通过这些持久化信息恢复命名空间状态。”

“但陛下，不要把 SecondaryNameNode 理解成 NameNode 的实时备用节点。”

“传统 SecondaryNameNode 主要承担检查点相关工作，并不能直接等同于高可用架构中的 Standby NameNode。”

国王点了点头。

“那么，如果 NameNode 本身坏了怎么办？”

“这就是 HDFS 高可用架构需要解决的事情。”

“在 HA 部署下，我们通常会有 Active NameNode 和 Standby NameNode，配合共享编辑日志与故障切换机制。”

“但它并非仅仅多启动一个 NameNode 就能自动实现高可用。”

第五幕：副本军团——一台服务器坏了怎么办？

当天夜里。

HDFS 帝国的一座数据仓库突然发生故障。

DataNode B 失去联系。

国王脸色骤变。

“我们保存在上面的文件是不是丢失了？”

指挥官回答：

“不一定。”

“因为我们采用了数据块副本机制。”

一、三副本策略

假设某个 Block 配置三个副本。

那么它可以分别保存在三个 DataNode 上。

当其中一台服务器故障时，其他节点上的副本仍可能提供数据。

“NameNode 会通过心跳等机制感知 DataNode 的状态。”

“还可以根据块报告等信息维护 Block 的副本情况。”

“如果某个 Block 副本数量低于要求，系统能够在符合条件时安排补副本。”

国王问：

“三副本是不是意味着，无论损坏几台机器都不会丢数据？”

“当然不是。”

“如果一个 Block 的全部副本都不可用，就仍然可能发生数据不可用或丢失。”

“此外，副本如何跨机器、机架分布，以及集群故障范围，都非常重要。”

二、副本的代价

“陛下，假设我们要存储 100 TB 逻辑数据，全部使用三副本。”

“在忽略元数据与其他额外开销的情况下，副本数据大约需要 300 TB 的原始存储容量。”

国王皱起眉头。

“存储成本增加三倍？”

“副本机制确实会带来较高的存储开销。”

“不过现代 HDFS 也支持纠删码等存储策略，可以在特定场景下降低冗余容量成本，同时带来编码、恢复和访问方面的权衡。”

第六幕：MapReduce——一千名士兵，如何完成同一项任务？

HDFS 的问题终于基本解决。

数据可以分块保存。

节点损坏时可以利用副本恢复。

但国王发现：

“我们现在只是有了足够大的仓库。”

“还没有解决计算问题。”

架构师点头。

“所以，接下来是 MapReduce。”

“陛下，请先忘记编程。”

“我们从一个简单故事开始。”

一、统计一亿篇文章中每个单词出现的次数

国王下令：

“统计全国所有文章中，每个单词出现了多少次。”

“例如 Java、Redis、MySQL。”

如果只有一个人计算，他需要：

打开所有文章。

阅读所有内容。

逐个统计单词。

最后汇总。

但如果有一千名士兵呢？

架构师说道：

“我们可以把文章分给不同士兵。”

“每个人只处理自己负责的内容。”

“然后把同类结果汇总。”

“这就是 MapReduce 思想的核心。”

二、Map：映射阶段

假设我们有三份文本。

文件 A：Java Redis Java
文件 B：Redis MySQL
文件 C：Java MySQL Redis

Map 阶段会把单词转换成键值对。

(Java, 1)
(Redis, 1)
(Java, 1)

(Redis, 1)
(MySQL, 1)

(Java, 1)
(MySQL, 1)
(Redis, 1)

国王问：

“为什么要变成 (单词, 1)？”

“因为后续需要根据单词这个 Key 汇总数量。”

“这里 Value 为 1，表示发现一次。”

三、Shuffle：重新分组

Map 的结果分散在不同机器。

但是同一个单词可能出现在不同机器上。

例如：

机器 A：
(Java, 1)
(Redis, 1)

机器 B：
(Java, 1)
(MySQL, 1)

机器 C：
(Java, 1)
(Redis, 1)

“接下来，我们需要把相同 Key 的记录送到负责它们的 Reduce 任务。”

这个过程涉及分区、网络传输、排序与分组等操作，统称 Shuffle 阶段的相关工作。

四、Reduce：归约阶段

把同一个 Key 对应的 Value 汇总。

Java  → [1, 1, 1] → 3
Redis → [1, 1]    → 2
MySQL → [1]       → 1

最终结果：

Java: 3
Redis: 2
MySQL: 1

国王眼前一亮。

“原来 MapReduce 并不神秘！”

“就是先拆分任务，再把同类数据聚集起来计算！”

“可以这样理解。”

“不过实际的 MapReduce 框架还需要负责输入切分、任务调度、数据本地性、Shuffle 文件管理、失败重试等大量工程细节。”

第七幕：Shuffle 战争——为什么数据交换如此昂贵？

MapReduce 军团取得了第一次胜利。

但就在国王准备庆祝时，一名工程师跑进大殿。

“陛下！新的问题出现了！”

“十台计算机都已经完成 Map，可整个任务仍然很慢！”

国王不解。

“计算不是完成了吗？”

架构师回答：

“Map 完成，并不意味着整个计算完成。”

“因为我们还必须把相同 Key 的数据汇集到对应的 Reduce 任务。”

“这场数据大迁徙，就是 Shuffle。”

一、Shuffle 为什么需要网络传输？

假设一百台 Mapper 分别分析一部分用户订单。

每台机器都会产生这样的中间结果：

(北京, 100)
(上海, 200)
(广州, 150)

如果我们按照城市汇总销售额，就要保证同一个城市的数据到达同一个 Reducer。

于是，系统必须根据 Key 进行分区。

默认 HashPartitioner 的典型计算方式可以理解为：

partition = (key.hashCode() & Integer.MAX_VALUE)
            % numReduceTasks;

如果有四个 Reducer，那么不同城市的 Key 会被分配到对应的分区。

但是，同一个城市的数据可能来自几十台 Mapper。

这意味着什么？

大量数据需要跨机器传输。

国王问：

“网络不是很快吗？”

架构师回答：

“网络很快，但如果 Shuffle 需要传输数十 TB 数据，网络就可能成为主要瓶颈。”

“并且这并不只有网络开销。”

他展开 Shuffle 的详细作战地图。

MapReduce Shuffle 过程

架构师说道：

“在 Hadoop MapReduce 中，Map 中间输出通常需要在本地组织并可能溢写磁盘，而 Reduce 端需要获取对应分区并进行合并与分组。”

“所以 Shuffle 可能同时消耗磁盘 I/O、网络带宽、CPU 和内存。”

二、Combiner：先在本地汇总

国王忽然想到了一个办法。

“假设机器 A 产生了一百万个 (Java, 1)。”

“为什么不先在机器 A 上统计为 (Java, 1000000)，然后再传输？”

架构师露出了笑容。

“陛下，您已经理解 Combiner 了。”

Combiner 可以在 Map 端对符合条件的中间数据进行局部聚合。

例如：

原本：

(Java, 1)
(Java, 1)
(Java, 1)
(Java, 1)

经过本地汇总：

(Java, 4)

需要传输的数据量可能大幅下降。

但是必须注意：

Combiner 不保证一定执行，也不保证只执行一次。

因此，不能把需要精确执行一次的业务逻辑放进 Combiner。

而且，局部汇总必须在数学和业务语义上是安全的。

求和、计数通常适合这种设计。

直接把平均值做成简单的局部平均再平均，则可能得到错误结果。

例如：

A 组有 2 个学生，平均分 90。

B 组有 8 个学生，平均分 60。

直接求两组平均：

(90+60)/2=75 (90+60)/2=75

但真实总体平均：

2×90+8×6010=66 \frac{2\times90+8\times60}{10}=66

“所以如果要分布式计算平均值，可以先聚合 (sum,count)，最终再用 sum/count。”

国王恍然大悟。

“看来分布式计算，不只是把任务拆开。”

“还要确保拆开以后，计算结果依然正确。”

第八幕：数据倾斜——为什么九十九名士兵已经休息，最后一人还在拼命？

帝国再次举办了一场大型计算任务。

这次有一百名 Reducer。

任务开始时，所有人都很忙碌。

一个小时后。

九十九名 Reducer 全部完成工作。

只有最后一名还在不停处理。

国王愤怒地问：

“为什么我们拥有一百台机器，却依然要等最后一个人？”

架构师回答：

“因为数据没有均匀分配。”

“这就是数据倾斜（Data Skew）。”

一、热点 Key 导致倾斜

假设我们统计电商平台用户的行为。

其中一个超级热门商品占据了全部事件的 80%。

其他商品总共只占 20%。

如果按照 productId 分区，那么这个热门商品对应的所有记录可能被分配到同一个 Reducer。

结果：

其他 Reducer 很快完成。

热点 Reducer 却承担了绝大部分计算。

数据倾斜模拟

二、如何解决数据倾斜？

架构师向国王提出四种策略。

第一种：局部预聚合。

对于可结合的聚合操作，先在 Mapper 本地合并热点 Key 的大量记录，降低网络和 Reduce 输入的数据量。

第二种：热点 Key 加盐。

例如原本：

(product_1001, value)

可以在允许的聚合场景中拆成：

(product_1001_0, value)
(product_1001_1, value)
(product_1001_2, value)

第一阶段分别聚合。

第二阶段再合并回原始 product_1001。

“这样可以把热点 Key 的计算压力分散出去。”

“但要注意，添加随机后缀并不总是正确，尤其涉及 Join、去重或对顺序敏感的操作时，需要专门设计。”

第三种：自定义分区策略。

通过分析 Key 分布，让任务分配更加合理。

但国王必须记住：

“仅仅增加 Reducer 数量，并不能自动拆散同一个热点 Key。”

第四种：针对大表 Join 的专门优化。

例如在后续 Spark 篇中，我们还会介绍广播 Join、倾斜 Join 优化和自适应查询执行。

第九幕：容错战争——执行一半，服务器突然死亡

就在集群准备完成一次耗时三小时的大型计算时。

轰！

一台服务器突然断电。

国王望着损坏的计算节点，脸色苍白。

“任务已经运行两个小时了！”

“难道所有工作都要重新来过？”

MapReduce 指挥官走了出来。

“陛下，这正是分布式计算框架必须解决的问题。”

一、任务失败重试

“MapReduce 会将作业拆分成多个任务。”

“如果一个 Task 失败，框架可以在符合策略的情况下重新执行该任务。”

“这样通常不需要从头重新执行整个作业。”

不过，如果 Map 所在节点故障，且其本地中间输出丢失，对应 Map 任务可能需要重新执行，以便 Reducer 重新获取相关结果。

国王问：

“那如果整个计算过程中，有十几台机器发生故障呢？”

“需要根据任务失败次数、节点健康状态、集群剩余资源等条件决定能否继续执行。”

“容错不代表无限次失败都能成功。”

二、推测执行：处理拖后腿的慢任务

架构师继续解释：

“有时候一台机器没有彻底坏掉。”

“它只是特别慢。”

“可能是磁盘性能下降，也可能是资源竞争。”

“如果整个作业都在等待最后一个慢任务，框架可以在一定条件下启动同一任务的另一次尝试。”

“谁先成功完成，就采用符合框架提交规则的结果。”

“这叫推测执行（Speculative Execution）。”

国王问：

“那岂不是执行了两次？”

“是的，所以业务代码必须注意重复执行问题。”

“如果一个 Map 任务只是读取数据并产生中间结果，通常比较适合重试。”

“但如果它直接调用外部支付接口、发送不可撤销的通知，重复执行就可能造成严重副作用。”

这与 Java 后端消息队列的重复消费问题，本质上有相似之处：分布式系统中的任务可能重试，所以外部副作用需要幂等与可靠提交设计。

第十幕：YARN 指挥部——谁来分配一千台机器？

MapReduce 成功运行后，国王又发现一个问题。

“Hadoop 帝国有一千台服务器。”

“现在同时来了三个任务。”

“第一个任务需要分析日志。”

“第二个任务需要训练数据预处理。”

“第三个任务需要统计订单。”

“究竟由谁负责分配 CPU 和内存？”

架构师回答：

“YARN。”

YARN 的基本架构中，有三个重要角色。

ResourceManager：总资源管理者

负责集群范围内的资源管理和调度决策。

NodeManager：机器管理员

每台计算节点上运行 NodeManager，负责节点资源与 Container 的运行和监控。

ApplicationMaster：应用指挥官

负责某个应用的任务协调，并向 ResourceManager 申请资源，配合 NodeManager 启动任务。

YARN 资源管理架构

范围 组件 管理对象与协作关系
集群 ResourceManager 统一资源调度，与各 NodeManager 通信
单个应用 ApplicationMaster 申请 Container，协调当前应用任务
单个节点 NodeManager 1 / 2 / 3 管理各自节点上的 Container 与任务
分配的运行资源 Container 应用任务获得的资源分配与执行环境

层次关系：集群包含多个节点；节点可运行多个 Container；应用的 ApplicationMaster 协调其任务使用分配到的资源。此处为逻辑结构，不代表每个节点只能运行一个任务。

架构师补充：

“YARN 将全局资源管理与每个应用的任务管理分开，使不同计算框架可以共享集群资源。”

“因此，YARN 并不是只能运行 MapReduce。”

国王问：

“这是不是和 Kubernetes 很像？”

“在资源调度、容器化工作负载管理等方面存在一定相似性。”

“但两者的设计背景、调度模型和生态系统不同，不能简单视为完全相同的产品。”

第十一幕：真正的分布式工程——数据本地性与 InputSplit

国王原以为一切已经结束。

突然，HDFS 指挥官提出了一个问题。

“陛下，假设一块 128 MiB 的数据在机器 A 上。”

“但我们的 Map 任务却被调度到了机器 B。”

“会发生什么？”

国王回答：

“机器 B 要从机器 A 读取数据。”

“没错。”

“如果上千个任务都需要跨网络读取大量数据，就可能产生可观的网络压力。”

“所以，Hadoop 引入了一个非常重要的设计思想。”

移动计算，尽量靠近数据，而不是总把大量数据搬向计算。

一、数据本地性

架构师解释：

“如果某个计算任务需要处理 HDFS 上的数据，调度器会尽可能利用数据位置信息，将计算安排在靠近数据的位置。”

常见情况包括：

  • 节点本地：任务运行在持有所需数据的节点。
  • 机架本地：任务运行在同一机架的其他节点。
  • 非本地：任务需要通过更远的网络路径读取数据。

“当然，这不是绝对要求。”

“如果数据所在节点已经非常繁忙，调度器也需要考虑资源利用率和等待时间。”

二、Block 与 InputSplit 的区别

国王突然问：

“既然 HDFS 已经有 Block，为什么 MapReduce 还需要 InputSplit？”

架构师笑了。

“这是面试里非常容易混淆的概念。”

Block 是存储层概念。

它描述 HDFS 如何将文件划分为物理存储的数据块。

InputSplit 是计算层概念。

它描述一个 Map Task 需要处理的逻辑输入范围。

两者并不必然一一对应。

例如：

HDFS 把文件保存成若干 Block。

MapReduce 的 InputFormat 则决定如何生成 InputSplit。

RecordReader 再把 Split 中的数据解析为 Mapper 能处理的 Key-Value 记录。

“所以，一个 Mapper 通常对应一个 InputSplit，而不是严格地对应一个 HDFS Block。”

“如果文件由多行文本组成，InputSplit 的边界还可能落在一行中间，RecordReader 必须正确处理记录边界。”

国王终于理解。

“原来数据存储的切分方式，与计算任务的切分方式，并不是同一个概念。”

第十二幕：Java 工程师的试炼——亲手写一个 MapReduce

第二天，首席架构师召集了 Spring 王国的 Java 工程师。

“诸位，你们已经理解 MapReduce 的基本思想。”

“现在，请用 Java 实现 WordCount。”

大厅里瞬间安静下来。

一名年轻工程师走上前。

“我来。”

他拿出纸笔，写下一段 Hadoop MapReduce 程序。

Mapper：把单词转换成键值对

public class WordCountMapper extends Mapper<
        LongWritable,
        Text,
        Text,
        IntWritable> {

    private static final IntWritable ONE =
            new IntWritable(1);

    private final Text word = new Text();

    @Override
    protected void map(
            LongWritable key,
            Text value,
            Context context
    ) throws IOException, InterruptedException {

        String[] words = value.toString()
                .split("\\s+");

        for (String w : words) {
            if (!w.isEmpty()) {
                word.set(w);
                context.write(word, ONE);
            }
        }
    }
}

国王看到了一些陌生类型。

“LongWritable 是什么？”

“为什么不用 Java 原生的 Long？”

工程师解释：

“Hadoop 提供了一套 Writable 类型，用于框架中的数据序列化和传输。”

例如：

  • IntWritable 对应整数值。
  • LongWritable 对应长整数值。
  • Text 表示文本数据。

“Mapper 的输入 Key 通常由具体 InputFormat 和 RecordReader 决定。”

“对于常见 TextInputFormat，Key 通常是行在文件中的字节偏移量，Value 是一行文本。”

Reducer：汇总相同单词的计数

public class WordCountReducer extends Reducer<
        Text,
        IntWritable,
        Text,
        IntWritable> {

    @Override
    protected void reduce(
            Text key,
            Iterable<IntWritable> values,
            Context context
    ) throws IOException, InterruptedException {

        int sum = 0;

        for (IntWritable value : values) {
            sum += value.get();
        }

        context.write(key, new IntWritable(sum));
    }
}

架构师点头。

“很不错。”

“对于 WordCount，我们还可以把这个 Reducer 用作 Combiner，因为计数求和支持安全的局部聚合。”

Job：组织整个计算任务

Configuration conf = new Configuration();

Job job = Job.getInstance(conf, "word-count");

job.setJarByClass(WordCountApp.class);

job.setMapperClass(WordCountMapper.class);
job.setCombinerClass(WordCountReducer.class);
job.setReducerClass(WordCountReducer.class);

job.setOutputKeyClass(Text.class);
job.setOutputValueClass(IntWritable.class);

FileInputFormat.addInputPath(
    job,
    new Path("/input/logs")
);

FileOutputFormat.setOutputPath(
    job,
    new Path("/output/wordcount")
);

System.exit(job.waitForCompletion(true) ? 0 : 1);

“这样，我们就定义了输入、Mapper、Combiner、Reducer 与输出路径。”

国王问：

“那 MapReduce 是不是比普通 Java Stream 强得多？”

架构师摇头。

“它们解决问题的范围不同。”

“Java Stream 主要是在一个 JVM 的执行环境中表达数据处理流水线。”

“Hadoop MapReduce 则可以协调多个节点完成分布式数据处理。”

“但如果数据只有几万条，单机 Java 程序就能快速处理，使用 Hadoop 可能反而带来不必要的调度和 I/O 开销。”

工程原则：数据量大，不一定非要使用 Hadoop；数据量小，更不应该为了使用分布式技术而使用分布式技术。

第十三幕：为什么 MapReduce 最终遇到了瓶颈？

十年后。

Hadoop 帝国的威望达到了巅峰。

它可以在大规模集群中处理海量数据。

然而，一位新的挑战者悄然出现。

这位挑战者的名字，叫作 Spark。

在正式登场之前，国王必须先理解 MapReduce 的局限。

一、多阶段计算与中间结果物化

假设我们需要完成以下任务：

  1. 读取一百 TB 的日志。
  2. 过滤无效记录。
  3. 按用户进行聚合。
  4. 与用户画像数据关联。
  5. 再次聚合。
  6. 输出分析结果。

在传统 Hadoop MapReduce 执行模型中，复杂处理可能需要串联多个作业。

而作业之间通常通过文件系统中的物化中间结果衔接。

这意味着可能出现多轮磁盘读写。

对于复杂的迭代计算，这些开销尤为明显。

二、迭代算法不够友好

国王问：

“什么叫迭代计算？”

架构师回答：

“例如某些机器学习算法，需要对同一批数据反复计算几十轮。”

“如果每次都需要重新构建任务、读取中间结果，成本就可能很高。”

“我们希望复用计算过程中已经得到的数据。”

三、Spark 的出现

架构师继续说道：

“Spark 引入了更灵活的执行模型。”

“它支持基于 DAG（有向无环图）的任务执行，以及对数据进行缓存和复用。”

“对于合适的工作负载，它可以减少不必要的中间数据物化与重复读取。”

“但不要误以为 Spark 全部在内存里计算。”

“Spark 同样可能发生磁盘溢写、Shuffle 和数据落盘。”

“它也不是在所有情况下都比 MapReduce 快。”

“真正的优势取决于任务结构、资源、数据格式、缓存策略和执行计划。”

国王终于明白。

“Hadoop 为帝国建立了分布式存储和批处理的基础。”

“而 Spark 则进一步改进了许多复杂计算任务的执行方式。”

第十四幕：首席架构师考核——八道面试题

多年后，一名年轻的 Java 后端工程师来到 Hadoop 帝国求职。

考官将八道题摆在他的面前。

尾声：一道来自东方的火光

深夜。

Spring 王国的国王站在最高的瞭望塔上。

他已经见识过 MySQL 的事务能力、Redis 的高速缓存、RabbitMQ 的消息缓冲，也终于理解了 Hadoop 的分布式存储与计算体系。

然而，他还有最后一个疑问。

“架构师，Hadoop 已经能够把计算分散到一千台机器。”

“那为什么还有新的计算引擎不断出现？”

架构师没有回答。

他只是拿出了一份来自东方的密报。

密报上写着：

“某研究团队需要反复分析上百 TB 的数据。”

“他们使用传统多阶段 MapReduce 作业，每轮都要协调大量任务和中间结果。”

“而另一支军团，竟然能够把多个计算阶段组织成一张 DAG，并根据需要复用数据。”

国王抬起头。

“那支军团叫什么？”

架构师缓缓说道：
