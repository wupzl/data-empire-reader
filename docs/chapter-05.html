第一幕：七十二次计算，帝国等待了三天

数据大陆，冬季。

Hadoop 帝国中央计算大厅。

一百台服务器正在日夜不停地工作。

这次任务来自帝国财政大臣。

“陛下，我们希望建立一个用户消费行为分析模型。”

“需要分析过去五年的交易记录，识别不同用户群体的消费特征。”

国王 Java 问：

“数据有多少？”

“二十 TB。”

“计算多少次？”

“需要进行七十二轮迭代。”

国王十分淡定。

“二十 TB 而已，我们不是已经有 Hadoop 了吗？”

首席架构师点头。

“确实可以使用 MapReduce。”

“但是，陛下，这次任务与之前不同。”

“之前我们统计词频，主要执行一次 Map 和 Reduce。”

“而现在，我们需要对数据进行反复计算。”

“每一轮的结果，都可能成为下一轮的输入。”

国王挥手。

“那就让 MapReduce 运行七十二次。”

架构师叹了口气。

“问题恰恰在这里。”

一、MapReduce 的多阶段执行代价

在经典 Hadoop MapReduce 模型中，多个独立作业之间通常通过 HDFS 等持久化存储传递结果。

例如：

HDFS 原始数据
      ↓
MapReduce Job 1
      ↓
HDFS 中间结果
      ↓
MapReduce Job 2
      ↓
HDFS 中间结果
      ↓
MapReduce Job 3
      ↓
   最终结果

国王突然意识到一个问题。

“也就是说，计算过程中可能发生大量磁盘读写？”

“正是。”

“而且每轮作业还存在任务初始化、调度、资源申请等开销。”

“对于迭代算法，这些开销会反复出现。”

“但我们能不能把下一轮要用的数据留在内存中？”

大厅突然安静。

一位身披蓝色披风的年轻统帅走了进来。

“当然可以。”

“不过，陛下，我们不仅要考虑内存。”

“还要重新设计整个分布式计算执行模型。”

“你是谁？”

“Spark。”

第二幕：RDD——不再只是一个普通数组

Spark 统帅来到地图前。

“陛下，首先需要认识我的核心抽象之一。”

“RDD。”

国王问：

“这是一个 Java List 吗？”

Spark 摇头。

“它们看起来有些相似，但本质不同。”

RDD（Resilient Distributed Dataset），即弹性分布式数据集。

我们把这个名字拆开理解。

一、Distributed：分布式

“陛下，假设我们有一亿条订单。”

“普通 Java List 通常位于一个 JVM 所管理的数据空间中。”

“而 RDD 可以把数据逻辑上划分为多个 Partition，由不同 Executor 处理。”

RDD 分区与并行处理

RDD：一亿条订单

分区 0

分区 1

分区 2

分区 3

Executor 1

执行分区任务

Executor 2

执行分区任务

简化示例：一个 Executor 可以在资源允许时并行运行多个 Task；Partition 与 Executor 不是永久一对一绑定关系。

“国王，RDD 是一个分布式数据集的逻辑抽象，而不是必须在创建时就把全部数据装进内存。”

二、Resilient：弹性与容错

国王问：

“如果一台 Executor 突然宕机，它负责的分区数据不就丢失了吗？”

Spark 微微一笑。

“RDD 的重要设计之一，是记录计算依赖关系。”

“这个关系叫作 Lineage。”

例如：

原始日志 RDD
     ↓ filter
有效日志 RDD
     ↓ map
用户金额 RDD
     ↓ reduceByKey
用户消费总额 RDD

“如果某个分区丢失，Spark 在满足条件时可以沿着依赖关系重新计算它。”

“这意味着，对于很多确定性计算，我们不必在每个步骤都立即把数据完整持久化。”

国王点头。

“这就是 Resilient。”

“是的。”

“但容错并不是免费的。如果依赖链很长，重新计算的代价也可能很大。”

“因此，我们还需要 Cache、Persist 和 Checkpoint。”

三、RDD 的不可变性

Spark 继续说道：

“还有一个关键特点。”

“RDD 不可变。”

国王问：

“那如何修改其中的数据？”

“我们不会原地修改 RDD。”

“而是通过 Transformation 生成新的 RDD。”

例如：

numbers = sc.parallelize([1, 2, 3, 4])doubled = numbers.map(lambda x: x * 2)

numbers 仍然表示原始数据集。

doubled 是新的 RDD。

“不可变设计让依赖追踪和失败后的重算更加容易组织。”

第三幕：Lazy Evaluation——国王下达命令，士兵却没有行动

第二天，国王决定亲自使用 Spark。

他写下一段 PySpark 代码。

rdd = sc.parallelize([1, 2, 3, 4, 5])result = (    rdd    .map(lambda x: x * 2)    .filter(lambda x: x > 5))print("计算已经完成！")

国王等待了一会儿。

却没有看到他期待的计算输出。

他愤怒地问：

“我已经调用了 map 和 filter，为什么 Spark 没有立即完成整个任务？”

Spark 回答：

“陛下，因为它们是 Transformation。”

一、Transformation：描述计算

常见 RDD Transformation：

  • map
  • filter
  • flatMap
  • mapPartitions
  • reduceByKey
  • join
  • distinct

“这些操作主要是在构建新的 RDD 及其依赖关系。”

“它们通常不会立即触发整个分布式作业执行。”

二、Action：触发计算

Spark 在代码后面补上一行：

print(result.collect())

这一次，计算开始执行。

输出：

[6, 8, 10]

Spark 说道：

“collect() 是 Action。”

“它会触发计算，并把结果收集到 Driver。”

“不过，如果结果巨大，直接 collect 可能把 Driver 内存撑爆。”

“这也是为什么生产环境中，不能随意对海量 RDD 使用 collect。”

国王若有所思。

“所以 map 和 filter 更像是制定作战计划。”

“Action 才是正式下达开战命令？”

“很形象。”

三、为什么要惰性执行？

“陛下，假设我们需要经过五步计算。”

“如果每一步都立即执行并物化结果，可能引入大量不必要的数据处理。”

“而惰性执行让 Spark 可以在触发 Action 时，根据依赖关系组织任务。”

“对于能够流水线执行的窄依赖操作，多个步骤可以合并在一个 Stage 内执行。”

“而在 DataFrame 与 Spark SQL 层面，Catalyst 还可以进一步优化逻辑执行计划。”

记忆：Transformation 构建计算关系，Action 触发实际计算。

第四幕：DAG 战争——Spark 如何指挥一千台机器？

Spark 在地上画出一幅作战地图。

“陛下，DAG 的全称是 Directed Acyclic Graph。”

“有向无环图。”

“您可以把它理解为一张带有方向、且不包含依赖环路的计算关系图。”

例如：

读取订单
    ↓
过滤有效订单
    ↓
提取 userId 和 amount
    ↓
按 userId 分组聚合
    ↓
按金额排序
    ↓
保存结果

“这条数据处理流水线并不是每一步都必须单独启动一轮全新的分布式作业。”

“Spark 会分析依赖，划分 Stage，再将 Stage 拆成 Task。”

一、Job、Stage、Task

架构师要求 Spark 用最简单的语言解释三个概念。

Spark 回答：

Job：通常由一个 Action 触发的计算作业。

Stage：根据计算依赖与 Shuffle 边界划分出的任务阶段。

Task：一个 Stage 内针对某个数据分区执行的最小调度工作单元。

例如：

Job：统计用户消费金额

Stage 0：
  Task 0 → Partition 0
  Task 1 → Partition 1
  Task 2 → Partition 2
  Task 3 → Partition 3

Shuffle

Stage 1：
  Task 0 → Partition 0
  Task 1 → Partition 1

结果输出

“陛下，多个 Task 可以被调度到不同 Executor 并行执行。”

“但 Stage 之间存在必要的依赖约束。”

二、窄依赖与宽依赖

国王问：

“究竟是什么决定了 Stage 如何拆分？”

Spark 答道：

“首先需要理解两种依赖。”

窄依赖（Narrow Dependency）

例如：

rdd.map(lambda x: x * 2)

通常一个子分区只依赖有限数量的父分区，不需要全局重新分配数据。

宽依赖（Wide Dependency）

例如：

pairs.reduceByKey(lambda a, b: a + b)

同一个 Key 的数据可能存在于多个父分区。

为了聚合，需要跨分区交换数据。

这种 Shuffle 依赖通常构成 Stage 边界。

窄依赖与宽依赖

窄依赖

每个子分区通常依赖少量父分区

宽依赖

子分区可能依赖多个父分区的数据

国王恍然大悟。

“所以 Shuffle 不仅昂贵，还会影响整个作业的阶段划分。”

“没错。”

“这也是 Spark 性能调优的重要切入点。”

第五幕：Cache 与 Persist——为什么内存不是越多越好？

Spark 帝国取得了第一次胜利。

但是第三天，监控平台突然报警。

“陛下！Executor 内存即将耗尽！”

国王愣住了。

“不是说 Spark 擅长内存计算吗？”

“为什么反而出现内存不足？”

Spark 回答：

“因为内存是有限的资源。”

“能够使用内存，不等于应该把所有数据全部放进内存。”

一、没有缓存时会发生什么？

假设我们有一批日志，需要进行两种分析。

logs = spark.read.parquet("/data/logs")valid = logs.filter("status = 200")count = valid.count()users = valid.select("user_id").distinct().count()

国王问：

“这里的 valid 不是已经生成了吗？”

“为什么第二次分析可能又要读取原始数据？”

Spark 解释：

“DataFrame 的执行也是惰性的。”

“如果没有缓存或其他可复用机制，多个 Action 可能重复计算相同的数据处理链。”

二、Cache：存储可复用的结果

Spark 增加了一行：

valid = logs.filter("status = 200").cache()valid.count()  # 首次执行，填充缓存valid.select("user_id").distinct().count()

“第一次 Action 触发计算并填充缓存。”

“后续 Action 有机会复用已经缓存的数据。”

“但缓存不是调用 cache() 后立即将所有数据完整加载进内存。”

“缓存数据也可能因为内存不足而被淘汰，或者根据持久化策略存储到磁盘。”

三、Persist：选择不同存储策略

Spark 展示几种常见策略。

策略 主要特点
MEMORY_ONLY 尽量在内存中保存
MEMORY_AND_DISK 内存不足时可使用磁盘
DISK_ONLY 保存在磁盘
MEMORY_ONLY_2 保留两个副本，提高容错能力

“具体支持哪些存储级别，以及默认行为，取决于 Spark API 和版本。”

“例如 PySpark RDD 与 DataFrame 的默认持久化行为不能不加区分地混为一谈。”

国王问：

“那我把所有 DataFrame 都缓存，不就能加速了吗？”

Spark 摇头。

“完全不是。”

“缓存需要占用存储资源。”

“如果数据只使用一次，缓存可能没有收益，反而增加计算和内存压力。”

“如果缓存对象太多，还可能挤占 Shuffle 和执行内存。”

“所以真正需要缓存的，通常是计算代价高、预计会被反复使用的数据。”

四、Checkpoint：截断过长的依赖链

架构师又问：

“如果一个 RDD 的 Lineage 已经有几百层，发生故障后重新计算岂不是很昂贵？”

Spark 点头。

“这就需要考虑 Checkpoint。”

“Checkpoint 可以把数据物化到可靠存储，并使后续恢复不必一直追溯完整的上游依赖链。”

“它与 Cache 的主要目标并不相同。”

  • Cache/Persist：重点是数据复用和性能。
  • Checkpoint：重点是截断依赖、简化恢复路径。

“实际使用中，Checkpoint 同样有 I/O 成本，必须谨慎安排。”

第六幕：Catalyst——能够重写作战计划的军师

几个月之后。

Spring 王国需要统计某个月的销售额。

国王编写了一条 Spark SQL：

SELECT
    user_id,
    SUM(amount) AS total_amount
FROM orders
WHERE status = 'PAID'
  AND order_date >= '2027-01-01'
  AND order_date < '2027-02-01'
GROUP BY user_id;

国王问：

“这条 SQL 会一字不差地按照我写的顺序执行吗？”

Spark 笑了。

“陛下，您现在见到的是我的首席军师。”

“Catalyst。”

一、Catalyst 的任务

Catalyst 是 Spark SQL 的查询优化框架。

它会参与解析 SQL、分析语义、优化逻辑计划和选择物理执行方案。

Spark SQL 查询计划演化

二、谓词下推 Predicate Pushdown

假设我们有一百 TB 的 Parquet 文件。

但只需要查询某个月的订单。

如果先读取所有数据再过滤，代价非常高。

Catalyst 和数据源读取层会尝试把过滤条件尽量下推。

让存储读取阶段就过滤不需要的数据。

“不过，具体能下推到什么程度，取决于数据源和表达式的支持情况。”

“不是所有 WHERE 条件都能完全下推。”

三、列裁剪 Column Pruning

国王又问：

“如果 orders 有五十个字段，但我只需要 user_id 和 amount 呢？”

Spark 回答：

“我们可以尝试只读取必要字段。”

“对于 Parquet、ORC 等列式文件格式，这尤其有价值。”

因为无需读取所有列的数据。

四、Tungsten：执行层面的优化

Catalyst 主要负责查询计划优化。

Tungsten 则代表 Spark 在底层执行效率方面的一系列优化工作，包括更加紧凑的内存表示、减少部分对象开销以及代码生成等机制。

Spark 说道：

“陛下，请记住。”

“Catalyst 与 Tungsten 并不是两个互相排斥的查询引擎。”

“前者偏向查询计划优化，后者偏向高效执行相关技术。”

“现代 Spark SQL 的高性能来自多个层面的共同作用。”

第七幕：Join 之战——两张亿级表如何连接？

财政大臣又提出一道难题。

“陛下，我们有两张表。”

第一张：

orders

包含一亿条订单。

第二张：

users

包含一百万个用户。

“我们想将订单关联用户信息，再统计不同地区的销售额。”

SQL 如下：

SELECT
    u.city,
    SUM(o.amount)
FROM orders o
JOIN users u
    ON o.user_id = u.id
GROUP BY u.city;

国王问：

“Spark 会怎么执行 Join？”

架构师回答：

“主要取决于数据规模、Join 类型、数据分布、统计信息和配置。”

“我们先讨论两种典型策略。”

一、Broadcast Hash Join：把小表送到每一座城

假设一边的数据经过过滤和压缩后只有 5 MB。

而另一边有 100 GB。

Spark 可以考虑把小表广播给参与计算的 Executor。

“这样，大表不必仅仅为了这个 Join 而全部按照连接键重新洗牌。”

Broadcast Join 简化结构

执行节点 大表数据 小表数据
Executor 1 本节点处理的分区 广播副本
Executor 2 本节点处理的分区 广播副本
Executor 3 本节点处理的分区 广播副本

“但广播小表也消耗 Driver、网络和 Executor 内存资源。”

“如果小表并不小，强行广播可能造成内存压力甚至任务失败。”

二、Sort Merge Join：双方重新分区并排序

当两边数据都比较大，而且连接条件适合时，Spark 可能采用 Sort Merge Join。

典型过程：

双方根据 Join Key 进行 Shuffle。

相同 Key 被分配到对应分区。

各分区内进行排序。

然后执行归并连接。

“它通常适合较大规模的等值 Join。”

“但是 Shuffle、排序和数据倾斜都可能产生较高成本。”

三、AQE：战斗过程中调整策略

国王继续问：

“假设 Spark 在任务开始前估计 users 表有 100 MB。”

“但实际运行时，经过过滤只有 2 MB。”

“能不能临时改变计划？”

Spark 答道：

“这就是 AQE。”

AQE（Adaptive Query Execution），自适应查询执行。

它可以利用运行时获得的统计信息，对部分物理执行计划进行调整。

例如：

  • 合并较小的 Shuffle 分区。
  • 在适合时调整 Join 策略。
  • 对支持的倾斜 Join 场景进行优化。

Spark 相关优化依赖准确的统计信息、运行时数据与具体配置；即使提供了 Join Hint，也不能保证所有情况下都采用指定策略。

第八幕：数据倾斜再现——最强大的计算军团，也无法逃脱热点

战争持续了数日。

Spark 帝国的计算节点大部分已经完成任务。

可最后一个 Task 却迟迟无法结束。

国王愤怒地问：

“我们不是已经有了 AQE 吗？”

“为什么还有数据倾斜？”

Spark 回答：

“AQE 可以优化部分倾斜场景，但不是所有数据倾斜都能自动解决。”

一、热点 Key

假设平台有一千万条订单。

其中 30% 的订单属于同一个商家。

如果按照 merchant_id 分组：

df.groupBy("merchant_id").sum("amount")

这个热点商家可能让对应分区承担大量工作。

尤其是在 Join 等操作中，如果热点 Key 两侧都有大量记录，甚至可能产生远超输入规模的中间结果。

二、为什么增加分区数不一定有用？

国王说：

“那就把分区数量从 200 改成 2000！”

Spark 摇头。

“如果同一个 Key 按 Hash 规则始终进入一个分区，那么单纯增加分区数量并不能把它拆开。”

“不过，分区数量过少导致的普通负载不均衡，确实可能通过调整并行度改善。”

三、热点加盐

对于可拆分聚合，可以考虑把热点 Key 拆成多个子 Key。

例如：

merchant_1001_0
merchant_1001_1
merchant_1001_2
merchant_1001_3

第一阶段分别聚合。

第二阶段再合并到：

merchant_1001

“但加盐必须保持业务语义正确。”

“并不是所有 Join 都能简单加盐。”

“对于复杂场景，最好先借助 Spark UI 和执行计划确认倾斜位置，再设计优化策略。”

第九幕：OOM 之夜——为什么 128GB 内存仍然不够？

深夜。

Spark 帝国最昂贵的一台服务器突然发出警报。

java.lang.OutOfMemoryError:
Java heap space

国王震惊。

“我们给它配了 128GB 内存！”

“为什么还是 OOM？”

Spark 冷静地回答：

“陛下，机器物理内存、Executor 可用内存与某个 Task 真正能够使用的内存，并不是同一个概念。”

“而且 OOM 可能发生在不同位置。”

一、Driver OOM

例如：

all_orders = df.collect()

如果结果集非常大，全部收集到 Driver，就可能导致 Driver 内存不足。

二、Executor OOM

常见原因：

  • 单个分区过大。
  • Shuffle 聚合数据结构占用大量内存。
  • 广播表过大。
  • 缓存过多。
  • 用户自定义函数创建大量对象。
  • 数据倾斜导致少数 Task 负载过高。

三、容器内存超限

“陛下，Spark 还可能因为堆外内存、Python Worker 内存等消耗，使整个容器超过资源限制。”

“这类故障未必会表现为 Java heap space。”

“有时任务会因 Container 被资源管理器终止而失败。”

四、正确排查流程

架构师制定了一套排查方案。

首先定位故障发生在 Driver 还是 Executor。

然后检查 Spark UI 中的 Stage、Task、Shuffle Read、Shuffle Write、Spill、GC、失败原因等指标。

接着排查是否存在数据倾斜、异常大分区、错误广播或不合理缓存。

最后再决定是否调整分区、Join 策略、缓存方案以及资源配置。

“陛下，第一反应不应该永远是增加内存。”

“增加内存有时只是掩盖根本问题。”

第十幕：真正的工程实践——用 Spark 统计一亿条订单

国王终于提出一个现实问题。

“我们学了这么多原理。”

“现在，如果真的有一亿条订单，究竟应该怎么做？”

架构师拿出一份 PySpark 程序。

第一步：读取 Parquet 数据

from pyspark.sql import SparkSessionfrom pyspark.sql.functions import (    col, sum as spark_sum, count)spark = SparkSession.builder \    .appName("OrderAnalytics") \    .getOrCreate()orders = spark.read.parquet("/data/orders")

“这里使用 Parquet，而不是直接在 Driver 中读取一亿条记录构造成 List。”

“Parquet 是列式文件格式，比较适合许多批量分析任务。”

第二步：过滤有效订单

valid_orders = orders.filter(    (col("status") == "PAID") &    (col("amount") > 0))

“这里的过滤操作不会立即触发整个计算。”

第三步：按用户聚合

user_stats = valid_orders.groupBy("user_id").agg(    spark_sum("amount").alias("total_amount"),    count("*").alias("order_count"))

“这里涉及按照 user_id 分组。”

“通常会产生需要关注的 Shuffle。”

第四步：写入结果

user_stats.write \    .mode("overwrite") \    .parquet("/output/user_stats")

“写入操作触发计算。”

“如果路径和权限正确，Spark 会组织并行任务，把结果写入目标存储。”

“但实际生产环境还需要考虑分区数、输出文件数量、写入幂等、任务重试和目录替换语义。”

第五步：检查执行计划

user_stats.explain("formatted")

架构师说道：

“不要只看代码长什么样。”

“要看 Spark 准备如何执行它。”

例如是否存在：

Scan parquet
    ↓
Filter
    ↓
HashAggregate (partial)
    ↓
Exchange (Shuffle)
    ↓
HashAggregate (final)
    ↓
Write

“这只是可能的典型计划示意。真实输出取决于具体 Spark 版本、数据类型、统计信息及配置。”

国王点头。

“所以 Spark 调优与 MySQL 调优有一个共同点。”

“不能只盯着 SQL 或代码。”

“还必须理解执行计划。”
