数据大陆，凌晨三点。

Spring 王国的皇宫仍然灯火通明。

首席架构师站在巨大的作战地图前，神情凝重。

“陛下，明日上午十点，帝国将发放一批限量优惠券。”

国王 Java 放下手中的奏章。

“数量多少？”

“一万张。”

“参与人数呢？”

“预计一百万人。”

国王笑了。

“我们已经部署了十台 Spring Boot 服务器，还修建了 Redis 要塞。区区一百万人，有什么可怕？”

架构师没有回答。

参与用户

100万

假设某一秒有十万个请求同时抵达，每个请求都需要判断用户资格、检查库存并创建领取记录。

架构师在地图上画了三个巨大的圆圈。

第一道，网关限流。

第二道，Redis 原子校验。

第三道，消息队列异步履约。

“只有通过前两道防线的请求，才能进入后续订单创建流程。”

优惠券秒杀系统初步架构

10 万 QPS 的用户请求

Nginx / API Gateway

限流、身份校验、路由

Redis + Lua

检查库存、校验重复领取、预扣减

无资格 / 无库存

立即返回

“也就是说，Redis 承担了第一线的库存竞争？”

“没错。”

“真正重要的是原子性。”

第三幕：两名士兵与最后一张优惠券

架构师把国王带进 Redis 要塞。

仓库里只剩下一张优惠券。

库存官正在值班。

突然，两名士兵冲了进来。

“我要领取！”

“我也要领取！”

库存官执行了一段代码。

Integer stock = redisTemplate.opsForValue()
        .get("coupon:stock:1001");

if (stock > 0) {
    redisTemplate.opsForValue()
            .decrement("coupon:stock:1001");
}

张三读取库存。

结果为 1。

李四读取库存。

结果也为 1。

张三执行 DECR。

库存变为 0。

李四执行 DECR。

库存变为 -1。

两人都被认为通过了先前的库存判断。

国王猛地站了起来。

“Redis 不是单线程执行命令吗？为什么还是发生了超卖？”

架构师回答：

“陛下，您混淆了两个概念。”

“单条命令的原子性，不代表多条命令组成的业务操作具有原子性。”

Redis 的 GET 是一个命令。

DECR 是另一个命令。

其他客户端可以在两条命令之间执行操作。

因此：

GET → 判断 → DECR

不是一个不可分割的整体。

“那么，怎样才能保证它们不可分割？”

架构师微微一笑。

“我们需要 Redis 要塞的秘密武器。”

“Lua 脚本。”

第四幕：Lua 法典——让多个操作成为一个整体

“陛下，Redis 可以执行 Lua 脚本。”

“在传统 Redis 脚本执行模型中，一段脚本执行期间，不会有其他客户端命令插入其中执行。”

“因此，我们可以把库存检查、用户去重与库存扣减组织成一个原子执行单元。”

架构师拿出一份法典。

-- KEYS[1] = coupon:stock:1001
-- KEYS[2] = coupon:users:1001
-- ARGV[1] = userId

local stock = tonumber(
    redis.call('GET', KEYS[1])
)

if stock == nil or stock <= 0 then
    return 1  -- 库存不足
end

if redis.call(
    'SISMEMBER', KEYS[2], ARGV[1]
) == 1 then
    return 2  -- 已经领取
end

redis.call('DECR', KEYS[1])

redis.call(
    'SADD', KEYS[2], ARGV[1]
)

return 0  -- 成功

国王仔细观察。

“原来如此。”

“第一步，检查库存。”

“第二步，检查用户是否已经领取。”

“第三步，扣减库存。”

“第四步，记录用户。”

“由于这些命令通过 Lua 脚本连续执行，其他客户端不能在中间插入命令？”

“正确。”

不过，架构师提醒：

“Redis 脚本的原子执行不等于数据库事务那样的自动回滚。”

“如果脚本执行了一部分写操作之后出现运行错误，之前的写操作不会自动撤销。”

“所以脚本应尽量简单，预先校验数据类型，并避免执行过程中发生错误。”

他又补充：

“Redis Cluster 环境中，脚本访问的多个 Key 还必须满足同槽位约束。可以使用相同的 Hash Tag，例如 coupon:{1001}:stock 和 coupon:{1001}:users。”

国王点了点头。

“看来真正可靠的系统，细节远比概念重要。”

第五幕：分布式锁——一把钥匙真的能够解决所有问题吗？

第二天，王国的几位工程师提出了另一种方案。

“陛下，既然并发操作会发生冲突，我们为什么不使用锁？”

“只允许一个士兵进入库存仓库，其他士兵全部等待。”

国王觉得很有道理。

于是工程师写下：

synchronized (this) {
    deductStock();
}

架构师看了一眼，摇了摇头。

“这把锁只保护当前 Java 进程内的线程。”

“如果我们部署十台 Spring Boot 服务器，每台都有自己的 JVM，那么每台服务器各自拥有一把锁。”

“服务器 A 获得锁，并不能阻止服务器 B 的线程执行同样的代码。”

国王一惊。

“所以我们需要一把整个帝国都能看到的锁？”

“这就是分布式锁。”

一、Redis 分布式锁

架构师写下：

SET lock:coupon:1001 unique-token NX PX 10000

“这里有三个关键部分。”

  • NX：只有 Key 不存在时才能设置成功。
  • PX 10000：设置 10 秒的过期时间，降低锁永久残留的风险。
  • unique-token：每个锁持有者使用唯一标识。

“但是陛下，绝不能拿到锁后就直接调用 DEL 释放。”

“为什么？”

“因为锁可能在业务执行过程中已经过期。”

架构师讲了一个故事。

张三获得锁，过期时间 10 秒。

张三执行某个缓慢的数据库操作，耗时超过 10 秒。

锁自动过期。

李四获得了新的锁。

此时张三终于执行完成。

如果张三直接删除锁，就会误删李四的锁。

“所以释放锁时需要判断锁是否仍然属于自己。”

if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end

return 0

“这样，检查锁归属与删除锁也能在脚本中原子完成。”

二、Redisson 与锁续期

国王又问：

“如果业务时间无法预估，是不是很难设置过期时间？”

“是的。”

“Redisson 在适当配置下可以通过 Watchdog 看门狗机制，在锁持有者仍存活且满足续期条件时自动续期。”

“不过，一旦进程暂停、网络异常或续期失败，锁依然可能失效。”

“因此，分布式锁不能自动保证所有外部副作用都安全。对于需要严格防止过期持有者继续写入的场景，还可能需要 fencing token 等额外约束。”

国王若有所思。

“这么看来，分布式锁并不是万能药。”

架构师点头。

“对于优惠券库存竞争，我们通常优先考虑数据库条件更新或 Redis Lua 原子操作。”

“如果使用一把全局锁串行处理所有抢券请求，还可能把整个业务的吞吐量拖垮。”

面试核心：分布式锁的作用是协调多个进程对共享资源的访问，但不能取代数据库约束、幂等设计与最终的数据一致性检查。

第六幕：RabbitMQ 信使军团——为什么要让请求排队？

上午九点五十分。

Redis 要塞已经准备就绪。

然而架构师发现了新的问题。

“陛下，即使 Redis 可以在很短时间内完成资格校验，MySQL 仍然需要创建大量领取记录。”

“如果 Redis 通过一万个请求，这一万个请求仍然需要进入数据库。”

国王问：

“那我们让 Redis 直接写数据库？”

“不行。Redis 和 MySQL 是两个独立系统，不存在天然的跨系统原子事务。”

架构师指向地图上的信使军团。

“我们需要一个缓冲层。”

“RabbitMQ。”

RabbitMQ 的本质

“陛下，消息队列就像邮政系统。”

“生产者把信件交给邮局。”

“邮局暂时保存信件。”

“消费者从邮局取出信件并处理。”

在我们的业务中：

  • Producer：优惠券领取服务。
  • Exchange：根据路由规则将消息交给队列。
  • Queue：存放等待处理的领取任务。
  • Consumer：执行数据库持久化操作的履约服务。

架构师画出一个流程：

用户请求
    ↓
Redis Lua
    ↓
资格预占成功
    ↓
生成领取任务
    ↓
RabbitMQ
    ↓
Consumer 消费
    ↓
MySQL 创建领取记录
    ↓
更新履约状态

国王兴奋地说道：

“这样数据库就不会立即收到一万个请求！”

“是的。”

“但需要记住一句话。”

消息队列可以削峰填谷，却不能凭空提高消费者和数据库的处理能力。

削峰填谷的数学原理

架构师解释：

“假设某一秒有 10,000 个有效任务进入队列。”

“而数据库每秒只能稳定完成 1,000 个任务。”

“那么第一秒，理想情况下只能处理其中的 1,000 个，剩余约 9,000 个需要等待。”

“如果后续没有新任务，且处理速度始终保持 1,000 个/秒，这一批任务理论上需要约 10 秒才能处理完。”

“如果持续每秒进入 2,000 个任务，但每秒只能处理 1,000 个，那么队列积压会持续增长。”

ΔQ=λin−μout \Delta Q = \lambda_{\text{in}}-\mu_{\text{out}}

其中 λin\lambda_{\text{in}} 为进入速率，μout\mu_{\text{out}} 为处理速率。

消息积压模拟器

国王望着不断上升的数字。

“所以，如果消费者始终处理不过来，RabbitMQ 迟早也会出现问题。”

“正是如此。”

“我们需要监控队列深度、最老消息等待时间、消费吞吐量、失败重试情况，以及消息积压持续增长的速度。”

第七幕：最危险的陷阱——Redis 扣减成功，消息却丢了

战斗进行得十分顺利。

一名用户成功领取了优惠券。

Redis 库存从 100 变成 99。

随后，应用准备向 RabbitMQ 发送消息。

就在这一瞬间。

轰！

应用服务器突然崩溃。

Redis 已经完成预扣减。

RabbitMQ 却没有收到消息。

MySQL 也没有创建领取记录。

国王脸色苍白。

“库存少了一张，却没有人真正拿到优惠券？”

“是的。”

架构师沉声说道：

“这就是分布式系统最重要的难题之一。”

“跨系统操作的一致性。”

Redis、RabbitMQ、MySQL 分别是独立的系统。

Redis Lua 可以确保 Redis 内部操作的原子性。

MySQL 事务可以保证数据库事务的 ACID 性质。

RabbitMQ Publisher Confirm 可以帮助生产者确认消息是否被 Broker 接收。

但它们不能自动组成一个共同提交、共同回滚的事务。

解决方案一：可靠消息与补偿机制

架构师制定了一套改进方案。

每次用户领取优惠券时，生成唯一的 requestId。

整个流程围绕该请求编号跟踪状态。

如果后续履约失败，可能进入：

RETRY_PENDING
COMPENSATING
COMPENSATED

“陛下，我们可以使用生产者确认、持久化消息、消费者手动 ACK、失败重试、死信队列等机制降低消息丢失风险。”

“但是如果生产者在 Redis 预扣减后、发送消息前直接崩溃，仅仅开启 Publisher Confirm 仍然无能为力。”

“要覆盖这个故障窗口，必须另有可靠的预占记录和恢复来源。”

例如：

  • 在 Redis 中维护可恢复的预占状态和待发送任务，结合可靠持久化、恢复扫描与对账；但其安全性取决于 Redis 的持久化和故障恢复语义。
  • 改用数据库事务同时写业务预占记录和 Outbox 表，再异步投递消息。
  • 根据业务允许的延迟与一致性要求，使用专门的对账和补偿流程。

“Redis 原子扣减 + RabbitMQ 发送，并不天然构成一个可靠事务。”

国王问：

“那是不是采用 Outbox 最好？”

“未必。数据库 Outbox 具有更清晰的事务边界，但会把写入压力重新引入数据库。”

“系统设计永远需要权衡。”

第八幕：消息重复——同一张优惠券被发放两次

战争的第二天。

消息队列出现了一次网络抖动。

消费者成功写入 MySQL。

然而，它向 RabbitMQ 发送的 ACK 没有成功抵达。

Broker 无法确认消息已被处理，于是可能重新投递。

同一条消息又被消费者收到。

“陛下！同一个领取任务出现了两次！”

国王急忙问：

“难道 RabbitMQ 不保证消息只消费一次？”

架构师摇头。

“在常见的手动确认、至少一次投递模式下，RabbitMQ 允许重复投递。”

“我们必须让业务具备 幂等性。”

什么是幂等？

“陛下，假设您命令士兵关闭城门。”

“命令执行一次，城门关闭。”

“再执行一次，城门仍然关闭。”

“无论重复执行多少次，最终状态一样。”

“这就是幂等性的直观含义。”

不过，工程上的幂等还需要保证重复执行不会产生额外的业务副作用。

例如，重复发送短信、重复扣费、重复发券，都可能造成问题。

数据库唯一索引

对于一人只能领取同一种优惠券一次的业务，可以建立唯一约束。

CREATE TABLE coupon_claim (
    id BIGINT PRIMARY KEY,
    request_id VARCHAR(64) NOT NULL,
    user_id BIGINT NOT NULL,
    coupon_id BIGINT NOT NULL,
    status VARCHAR(32) NOT NULL,

    UNIQUE KEY uk_request (request_id),
    UNIQUE KEY uk_user_coupon (user_id, coupon_id)
);

架构师解释：

“uk_request 防止同一个业务请求被重复创建。”

“uk_user_coupon 防止同一个用户重复领取同一种优惠券。”

“这两个唯一约束解决的是不同问题。”

他继续说道：

“即使多个消费者同时处理重复消息，数据库也能在唯一索引约束下拒绝不符合规则的重复记录。”

“但消费者仍然需要在事务中正确处理唯一键冲突，并确认已有记录是否确实代表同一次成功履约。”

消费者应该先 ACK，还是先写数据库？

架构师向国王提出一道面试题。

“陛下，消费者收到消息后，应该先给 RabbitMQ 发送 ACK，还是先提交数据库事务？”

国王思考片刻。

“先 ACK，这样消息就不会重复了。”

“那么，如果 ACK 成功后，数据库写入失败呢？”

“消息丢了……”

“没错。”

“所以典型做法是先完成数据库事务，再 ACK。”

“如果数据库提交成功、ACK 失败，消息可能重复投递，但可以通过幂等机制安全处理。”

@RabbitListener(queues = "coupon.claim.queue")
public void handle(
        ClaimMessage message,
        Channel channel,
        Message amqpMessage) throws IOException {

    long tag = amqpMessage.getMessageProperties()
            .getDeliveryTag();

    try {
        claimService.fulfillIdempotently(message);
        channel.basicAck(tag, false);
    } catch (Exception ex) {
        // 此处必须区分可重试和不可重试错误。
        // 实际系统需配置有限重试、退避、死信队列等。
        channel.basicNack(tag, false, false);
    }
}

“需要注意，这只是示例。”

“fulfillIdempotently 必须保证数据库事务已经成功提交后才返回。”

“如果使用自动 ACK 模式，就不能照搬这段代码。”

“而且，把所有异常直接丢进死信队列，也不构成完整的重试方案。”

国王点头。

“我明白了。”

“我们无法简单地依靠一次网络确认，消灭所有重复消费。”

“所以业务本身必须容忍重复执行。”

第九幕：最后一道防线——限流、熔断与降级

战争进入第三天。

这次出现了更加危险的情况。

RabbitMQ 消费者处理速度下降。

MySQL 的写入延迟不断增加。

消息逐渐积压。

国王立刻下令：

“增加消费者！一百个不够就一千个！”

架构师急忙阻止。

“陛下，如果 MySQL 已经饱和，盲目增加消费者可能让数据库承受更高的并发压力。”

“那怎么办？”

“我们需要流量治理。”

限流：控制进入系统的流量

架构师建立了一座新关卡。

“假设系统经过压测，确定某个接口当前只能稳定处理 5,000 QPS。”

“那么当 10 万 QPS 到来时，我们需要在入口处限制请求量，而不是让所有请求全部进入后端。”

常见算法包括：

固定窗口：按固定时间段统计请求数量，实现简单，但边界附近可能出现突发流量。

滑动窗口：将时间窗口细分或使用滚动统计，流量控制相对平滑。

令牌桶：按照一定速率补充令牌，允许一定程度的突发请求。

漏桶：按照相对稳定的速率处理或放行请求，平滑输入流量。

熔断：阻止故障继续蔓延

“陛下，假设支付服务已经持续超时。”

“如果每个请求都继续调用支付服务，不断等待几十秒，那么调用方的线程、连接和其他资源也可能耗尽。”

“熔断器会根据一定时间窗口内的失败率、慢调用率等条件，暂时阻止一部分调用进入故障服务。”

“经过等待，再允许少量试探性请求，看服务是否恢复。”

国王问：

“这不就是直接把服务关闭？”

“不完全是。”

“熔断器通常具有关闭、打开、半开三种状态。”

状态 行为
Closed 正常放行调用并统计结果
Open 快速拒绝被熔断的调用
Half-Open 允许有限请求尝试恢复

降级：保住最重要的业务

架构师继续说道：

“假设我们的商品详情页有五个模块。”

“商品价格、库存、推荐商品、用户评论、营销广告。”

“如果推荐服务异常，我们可以暂时不显示个性化推荐。”

“但商品价格和购买资格等核心信息必须保持可靠。”

“这种优先保障核心功能、暂时舍弃非核心功能的策略，就叫降级。”

国王终于理解。

“系统稳定性并不意味着所有功能永远正常。”

“而是出现异常时，仍然能保护关键能力。”

“正是如此。”

第十幕：帝国的终极设计——高并发不只是速度

经过连续数日的战争，Spring 王国终于完成了第一次真正意义上的高并发改造。

不过，架构师拒绝为这次胜利举行庆典。

国王不解。

“为什么？”

“因为我们目前解决的主要是请求入口、库存竞争和异步履约。”

“真正上线生产环境，还需要回答更多问题。”

他在黑板上写下：

容量、正确性、可靠性、可观测性。

一、容量

  • 系统稳定 QPS 是多少？
  • 峰值流量能持续多久？
  • Redis、RabbitMQ 和 MySQL 分别能承受多少负载？
  • 队列最多可以积压多少消息？
  • 消费者恢复后需要多久才能清空积压？

二、正确性

  • 是否可能超卖？
  • 是否可能重复领取？
  • 库存预扣减失败是否能够恢复？
  • 多次补偿会不会重复增加库存？
  • 如何保证最终发放数量不超过活动配额？

三、可靠性

  • Redis 故障会怎样？
  • RabbitMQ 不可用时是否允许继续接受领取请求？
  • 消费者宕机后如何恢复？
  • MySQL 事务失败如何处理？
  • 重试次数超过上限后如何人工介入？

四、可观测性

  • 当前 QPS、错误率、P95、P99 分别是多少？
  • Redis Lua 执行时间有多长？
  • RabbitMQ 堆积了多少消息？
  • MySQL 慢查询和锁等待是否增长？
  • 每个领取请求能否通过 requestId 追踪完整状态？

架构师最后说道：

“陛下，如果系统只有高吞吐量，却不能保证数据正确，那么它依然是不合格的系统。”

“一个真正的高并发工程师，不能只会 Redis 和 RabbitMQ。”

“还必须理解它们背后的故障模型，以及业务究竟可以接受什么程度的一致性与延迟。”

第十一幕：来自面试官的七道诘问

数月之后。

一名年轻的 Java 工程师来到王国参加首席架构师考核。

考官将七道题放在他面前。

尾声：一亿条订单，压垮了 MySQL 城

三个月过去。

Spring 王国的秒杀系统终于稳定运行。

Redis 要塞守住了绝大多数高频请求。

RabbitMQ 信使军团不断传递领取任务。

MySQL 则负责保存最终的业务记录。

所有人都以为战争已经结束。

直到某天深夜。

数据库管理员满脸惊恐地冲入王宫。

“陛下！”

“MySQL 城出事了！”

“订单表已经突破一亿条记录！”

“查询越来越慢！”

“一条普通的分页 SQL，竟然要执行好几秒！”

国王猛然起身。

“索引呢？我们不是已经建立了 B+ 树索引吗？”

“建立了！”

“可有些 SQL 仍然扫描大量数据！”

管理员颤抖着呈上一条 SQL：

SELECT *
FROM orders
ORDER BY id
LIMIT 10000000, 20;

国王看向架构师。

“为什么只取二十条记录，却需要等待这么久？”

架构师凝视着那条 SQL，陷入了沉默。

良久之后，他缓缓开口。

“陛下……”

“我们终于遇到了另一个敌人。”

“它不是瞬间涌入的十万请求。”

“而是日积月累、不断膨胀的海量数据。”

“这一次，Redis 和 RabbitMQ 都不能直接解决问题。”

“帝国需要重新思考数据该如何组织、存储与查询。”

窗外，一场新的暴风雪正在席卷数据大陆。

一场更大规模的战争即将开始。
