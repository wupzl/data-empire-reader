第二幕：N+1 查询——一行代码引发的灾难

架构师让林澈打开分布式追踪系统。

他找到了一次耗时 620 毫秒的请求。

请求路径如下：

GET /api/orders?userId=1001
        ↓
OrderController
        ↓
OrderService
        ↓
查询 20 条订单
        ↓
循环查询商品信息
        ↓
循环查询用户等级
        ↓
循环查询优惠信息
        ↓
返回订单列表

国王问：

“问题在哪里？”

架构师没有回答，而是让林澈打开 SQL 日志。

林澈看到：

SELECT *
FROM orders
WHERE user_id = 1001
ORDER BY created_at DESC
LIMIT 20;

紧接着：

SELECT * FROM product WHERE id = ?;
SELECT * FROM product WHERE id = ?;
SELECT * FROM product WHERE id = ?;
...

然后：

SELECT * FROM coupon WHERE id = ?;
SELECT * FROM coupon WHERE id = ?;
...

林澈脸色逐渐苍白。

“每条订单，都单独查询了一次商品和优惠信息。”

架构师点头。

“这就是典型的 N+1 查询问题。”

一、问题的 Java 代码

List<OrderVO> result = new ArrayList<>();

for (Order order : orders) {
    Product product =
            productMapper.selectById(order.getProductId());

    Coupon coupon =
            couponMapper.selectById(order.getCouponId());

    result.add(toVO(order, product, coupon));
}

“陛下，假设第一页查询 20 条订单。”

“查询订单本身需要一次 SQL。”

“每条订单再查询商品、优惠信息，各需要一次。”

“总共可能执行：”

1+20+20=41 1+20+20=41

“如果每次数据库调用平均带来额外延迟，即使单条 SQL 不慢，累计起来也可能非常可观。”

二、批量查询与数据组装

架构师把商品、优惠两类查询都移出了订单循环。以下是示意片段，Mapper、VO 与空关联的业务规则需由项目提供。

List<Order> orders = orderMapper.selectByUserId(userId);
Set<Long> productIds = orders.stream()
        .map(Order::getProductId).filter(Objects::nonNull)
        .collect(Collectors.toSet());
Set<Long> couponIds = orders.stream()
        .map(Order::getCouponId).filter(Objects::nonNull)
        .collect(Collectors.toSet());

// 避免向 Mapper 传入空 IN 集合。
Map<Long, Product> products = productIds.isEmpty()
        ? Collections.emptyMap()
        : productMapper.selectByIds(productIds).stream()
                .collect(Collectors.toMap(Product::getId, Function.identity()));
Map<Long, Coupon> coupons = couponIds.isEmpty()
        ? Collections.emptyMap()
        : couponMapper.selectByIds(couponIds).stream()
                .collect(Collectors.toMap(Coupon::getId, Function.identity()));

List<OrderVO> result = orders.stream()
        .map(order -> toVO(order,
                products.get(order.getProductId()),
                coupons.get(order.getCouponId())))
        .collect(Collectors.toList());
同一页 20 条订单 额外查询方式 理想 SQL 次数
修改前 每条分别查询商品与优惠 1 + 20 + 20 = 41
修改后 商品、优惠各批量查一次 1 + 1 + 1 = 3

这是“两个非空集合均可一次查询完成”的理想计数，不是实测耗时。缺失关联不能静默忽略：toVO 需明确允许为空、使用历史快照还是返回业务错误。大量 ID 需要分批；也可按查询形态评估 JOIN、索引和冗余快照字段。

三、为什么代码审查没有发现？

林澈问：

“这段代码看起来很普通。”

“为什么当时没人注意到？”

架构师回答：

“因为功能测试通常只验证最终结果。”

“如果测试数据只有一条订单，N+1 问题根本不明显。”

“而生产环境可能有更多记录、更高并发和不同的数据库网络延迟。”

“所以，我们需要自动化性能回归测试。”

第三幕：性能基线——不能只问新版本有没有报错

林澈决定建立性能基线。

但他首先遇到了一个问题。

“老师，性能回归到底怎么判断？”

“如果旧版本 P99 是 120ms，新版本 125ms，算退化吗？”

“如果新版本偶然测出了 150ms 呢？”

架构师回答：

“性能测试本身存在波动。”

“我们不能只运行一次，然后机械比较两个数字。”

一、什么是性能基线？

基线不是一句“系统很快”。

它必须有明确的测试条件。

例如：

服务版本：order-service 2.6.0

测试接口：GET /api/orders

数据规模：订单表 5000 万行

请求模型：恒定到达率

目标吞吐：5000 QPS

持续时间：10 分钟

CPU / 内存：固定资源规格

数据库：固定数据集与配置

缓存：记录冷缓存与预热后的结果

关注指标：
  P50
  P95
  P99
  错误率
  实际吞吐
  DB SQL 次数
  连接池等待时间

“陛下，同一段代码在不同数据规模、缓存状态和硬件环境下，性能可能完全不同。”

“所以比较两个版本时，应尽可能控制测试环境变量。”

二、为什么不能只看平均响应时间？

架构师在黑板上写下：

99 个请求：10ms
1 个请求：1000ms

平均响应时间：

99×10+1000100=19.9ms \frac{99\times10+1000}{100}=19.9ms

“平均不到 20ms。”

“但仍然有一个请求耗费了一秒。”

“如果这类尾部延迟在高并发系统中频繁出现，用户体验会明显受损。”

“因此，P95、P99 和错误率通常非常重要。”

三、性能回归门禁

架构师制定了一份示例标准。

订单接口性能门禁 · 示例

成功率 达到既定业务目标
P99 不超过绝对 SLO
相对退化 超过阈值需复核
SQL 次数 防止列表查询突然变为 N+1
吞吐量 实际达到设定到达率
压测器状态 无不可接受的丢弃迭代

相对退化阈值必须结合测试噪声、业务风险及统计方法制定，不能仅靠任意固定百分比决定所有发布。

“例如 P99 退化超过 15% 时，可以触发复测或阻止自动发布。”

“但如果样本不足、测试环境不稳定或流量组成改变，仅凭这一数字就断言代码退化，也可能误判。”

国王点头。

“性能基线不仅是一个数字。”

“它是一套可以复现的实验。”

第四幕：CI/CD 城门——让代码在上线前接受审判

三天后。

林澈将性能回归加入了工程流水线。

高并发项目交付流水线

国王问：

“每次提交代码，都要进行十万 QPS 的完整压测？”

架构师摇头。

“那可能太昂贵，也太慢。”

“我们要分层。”

第一层：快速检查

在 Pull Request 阶段运行单元测试、静态检查、轻量集成测试。

对于核心算法，可以增加合适的微基准测试。

第二层：关键链路性能测试

对订单创建、库存扣减、热点查询等核心接口进行受控的性能回归。

第三层：周期性全链路压测

在隔离环境中，以更接近生产的流量模型和数据规模进行完整压测。

第四层：生产灰度观察

通过有限范围的真实流量，验证无法在测试环境中完全重现的行为。

架构师强调：

“不是所有性能测试都应该阻塞每一次小提交。”

“合理的工程体系需要平衡反馈速度、测试可信度和执行成本。”

第五幕：Testcontainers——为什么 Mock 全部通过，生产却失败？

林澈为订单服务编写了一百多个单元测试。

然而，在一次发布中，生产数据库突然报错：

Duplicate entry for key 'uk_request_id'

国王质问：

“我们不是测试过订单幂等了吗？”

林澈回答：

“测试过。”

“那为什么仍然出错？”

“因为测试中使用的是一个模拟 Repository。”

架构师打开测试代码。

when(orderRepository.existsByRequestId("req-1001"))
        .thenReturn(false);

“你只证明了 Mock 按预期返回 false。”

“并没有证明数据库能够在并发情况下正确执行唯一约束。”

一、Mock 与真实依赖有什么区别？

架构师解释：

“Mock 非常适合验证业务逻辑、分支处理和组件交互。”

“但当我们需要测试数据库事务、索引、锁行为或消息系统交互时，模拟对象可能无法复现真实依赖的语义。”

“例如下面这段逻辑。”

if (!repository.existsByRequestId(requestId)) {
    repository.insert(order);
}

“两个并发线程仍然可能都看到不存在。”

“最后能否保证只插入一条，关键还取决于数据库唯一约束和事务实现。”

二、Testcontainers：为测试启动真实基础设施

“我们可以使用 Testcontainers，在测试期间启动隔离的 MySQL 等容器。”

示例：

@Testcontainers
@SpringBootTest
class OrderRepositoryIT {

    @Container
    @ServiceConnection
    static MySQLContainer<?> mysql =
            new MySQLContainer<>("mysql:8.4");

    @Autowired
    private OrderRepository repository;

    @Test
    void duplicateRequestIdShouldBeRejected() {
        repository.insert(
            new Order("req-1001", 1001L)
        );

        assertThrows(
            DataIntegrityViolationException.class,
            () -> repository.insert(
                new Order("req-1001", 1002L)
            )
        );
    }
}

架构师说道：

“这里是假设项目使用兼容的 Spring Boot、Spring Data 与 Testcontainers 依赖，并且 OrderRepository 的异常转换行为符合示例。”

“测试数据库还需要执行与生产兼容的 Schema Migration。”

“最好不要让测试中的表结构和生产表结构分别靠人工维护。”

三、测试时应该怎样划分？

林澈终于整理出规则。

单元测试验证业务逻辑。

集成测试验证数据库、Redis、消息队列等真实依赖的关键语义。

并发测试验证竞态条件。

压力测试验证容量和延迟。

故障注入验证恢复行为。

“很好。”架构师说道。

“测试不是越多越好，而是要覆盖真正可能导致事故的假设。”

第六幕：金丝雀军团——让百分之一的用户先踏入新城

性能回归体系建成后，林澈再次准备发布新版本。

这一次，他提出：

“先发布给百分之一的用户。”

国王问：

“为什么是百分之一？”

“因为即使测试全部通过，也不能保证新版本在真实流量下完全没有问题。”

架构师点头。

“这就是金丝雀发布（Canary Release）的思想。”

一、一次发布，为什么不能直接替换全部实例？

假设旧版本有一百台服务器。

新版本修改了订单查询逻辑。

如果一次性把一百台全部替换，那么一个隐藏的性能问题可能立即影响全部用户。

金丝雀发布则让新旧版本暂时共存。

线上流量
    ↓
Gateway / Service Mesh
    ├── 99% → order-service v2.6
    └──  1% → order-service v2.7

架构师说道：

“不过，陛下，真实 Kubernetes Deployment 的 Pod 数量比例，不一定严格等于用户请求流量比例。”

“如果希望准确控制请求百分比，通常需要合适的流量路由机制，例如网关、Ingress Controller 或 Service Mesh 的相关能力。”

模拟金丝雀发布

三、金丝雀到底观察什么？

验收项 需要保留的证据

数据管道 消费进度、重复与丢失检查、恢复后对账结果

一、SLI、SLO、SLA

“陛下，这三个概念容易混淆。”

SLI（Service Level Indicator）：衡量服务表现的指标，例如成功请求比例。

SLO（Service Level Objective）：对 SLI 设定的目标，例如一个自然月内成功率达到 99.9%。

SLA（Service Level Agreement）：向客户等相关方承诺的服务协议，可能包含违约责任。

“并不是每个内部 SLO 都自动成为具有合同约束的 SLA。”

二、什么是错误预算？

假设一个月有 1,000 万次属于 SLO 统计范围的请求。

目标成功率：

99.9% 99.9\%

允许不满足成功条件的比例：

1−0.999=0.001 1-0.999=0.001

允许失败的请求数量：

10000000×0.001=10000 10000000\times0.001=10000

“因此，对于这个请求成功率 SLO，错误预算为一万次不成功请求。”

“这并不意味着我们希望发生一万次失败。”

“而是为衡量稳定性消耗提供明确的尺度。”

交互实验：计算错误预算

SLO 错误预算计算器

“但不是说只要错误预算没耗尽，就可以随意冒险。”

“具体发布政策必须考虑业务重要性、故障严重程度和组织约定。”

“如果短时间内出现高 Burn Rate，即使周期总预算尚未耗尽，也应该快速响应。”

“实际生产中可以设计多窗口告警，避免既错过重大故障，又因偶发噪声频繁触发。”

五、把 Burn Rate 算清楚

对于请求成功率 SLO：

Burn Rate=观察窗口内失败请求数/观察窗口内请求数1−目标成功率 \text{Burn Rate}=\frac{\text{观察窗口内失败请求数}/\text{观察窗口内请求数}}{1-\text{目标成功率}}

例如目标成功率 99.9%，允许错误率 0.1%；若某观察窗口的错误率为 0.5%，Burn Rate 为 5 倍。这不是“本周期预算已经花掉 5%”。观察窗口必须明确；请求量变化时，不能只凭倍数预测月度预算何时耗尽。

长窗口用于确认持续消耗，短窗口用于确认问题仍在发生，阈值与样本量按业务制定。参考 Google SRE 的 SLO 告警说明。
