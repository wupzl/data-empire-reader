第二幕：第一份代码——一场注定发生的超卖

林澈很快写出第一版数据库表。

CREATE TABLE product_stock (
    product_id BIGINT PRIMARY KEY,
    available INT NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    CHECK (available >= 0)

CREATE TABLE orders (
    id BIGINT PRIMARY KEY,

    status VARCHAR(32) NOT NULL,

    UNIQUE KEY uk_request (request_id)
);

架构师看了一眼。

“不错。库存不能为负，订单请求也需要唯一标识。”

林澈写道：

public void buy(long productId) {
    int stock = stockMapper.selectStock(productId);

    if (stock <= 0) {
        throw new SoldOutException();
    }

    stockMapper.decrease(productId);
}

国王问：

“这段代码有问题吗？”

林澈回答：

“单线程运行正常。”

架构师笑了。

“那我们用两个并发线程测试。”

库存只剩一件

并发超卖实验

国王猛地拍桌。

“这是典型的竞态条件！”

架构师点头。

“所以第一步，不是加 Redis。”

“而是先用 MySQL 自己提供的原子更新能力保证正确性。”

用条件更新保护库存

UPDATE product_stock
SET available = available - 1
WHERE product_id = ?
  AND available > 0;

“这条 UPDATE 的检查与修改由数据库以一条语句完成。”

“如果影响行数为 1，说明本次成功扣减。”

“如果为 0，说明没有符合条件的库存记录。”

“这比把库存读出来、在 Java 代码中判断、再无条件 UPDATE 更可靠。”

把库存与订单放入同一个事务

@Service
public class OrderService {

    private final StockMapper stockMapper;
    private final OrderMapper orderMapper;

    public OrderService(
            StockMapper stockMapper,
            OrderMapper orderMapper) {
        this.stockMapper = stockMapper;
        this.orderMapper = orderMapper;
    }

    @Transactional
    public void createOrder(CreateOrderCommand cmd) {
        int changed = stockMapper.decreaseIfAvailable(
                cmd.productId());

        if (changed != 1) {
            throw new SoldOutException();
        }

        orderMapper.insert(cmd);
    }
}

架构师提醒：

“这段代码依赖 Spring 事务代理正常生效，并假设两个 Mapper 操作参与同一个数据库事务。”

“数据库插入失败时，事务回滚，前面的库存扣减也要回滚。”

“如果发生唯一键冲突，还需要明确重复请求应该返回原结果还是业务错误。”

“不要简单地把所有异常吞掉，然后继续提交事务。”

林澈松了一口气。

“至少现在不会因为 Java 层面的并发判断而超卖了。”

第四幕：Redis 要塞重建——把无效请求挡在数据库之外

架构师召见 Redis 将军。

“此次战争，你的任务不是替代 MySQL 的所有事务。”

“而是在大规模秒杀入口，快速完成资格与库存预占。”

Redis Lua 原子预占

-- KEYS[1]: coupon:{1001}:stock
-- KEYS[2]: coupon:{1001}:users
-- ARGV[1]: userId

local stock = tonumber(redis.call('GET', KEYS[1]))

if stock == nil or stock <= 0 then
    return 1
end

if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return 2
end

redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])

return 0

架构师说道：

“这能够在 Redis 内部原子地执行库存检查、重复领取检查与预扣减。”

“但 Lua 原子性不等于跨 Redis、消息队列、MySQL 的完整事务。”

“现在，真正危险的地方来了。”

“哪里？”

Redis 预扣成功
       ↓
应用进程崩溃

履约消息还没可靠保存

第五幕：可靠消息之战——跨系统事务没有魔法

架构师向国王提出两个不同的技术路线。

路线 A：数据库事务 + Outbox

“如果我们更关注实现边界清晰、可证明的一致性，可以先让 MySQL 处理权威库存预占，并在同一数据库事务中写入 Outbox。”

用户请求
    ↓
MySQL 事务
    ├── 条件扣减库存
    ├── 写入订单记录
    └── 写入 Outbox
    ↓
提交成功
    ↓
Outbox 发布器
    ↓
Kafka / RabbitMQ
    ↓
后续异步业务

优点是事务边界清楚。

业务状态与待发布事件可以原子提交。

缺点是所有成功的入口写入仍然需要经过 MySQL，因此数据库必须能够承担实际写入吞吐。

路线 B：Redis 预占 + 可恢复的异步履约

“如果秒杀入口规模极大，我们希望大部分无效请求在 Redis 被拒绝，那么可以考虑 Redis 预占。”

“但需要配套设计可靠任务记录、消息投递确认、恢复扫描与补偿对账。”

例如：

用户请求
    ↓
Redis 原子预占并记录预占状态
    ↓
可靠的履约任务转移
    ↓
消息队列
    ↓
消费者幂等写 MySQL
    ↓
履约成功 / 失败补偿
    ↓
定期对账

架构师特别强调：

“这里的‘可靠任务转移’不是一句话就能实现的。”

“需要明确 Redis 的持久化与故障恢复能力、任务状态记录格式、哪些状态必须恢复、消息发布前崩溃如何扫描，以及补偿如何避免重复返还库存。”

“如果这些机制不完善，宁愿采用简单而正确的数据库方案。”

两种路线怎么选？

维度 MySQL + Outbox Redis 预占 + 异步履约
一致性边界 较清晰 跨系统故障窗口更多
成功请求入口写入压力 较高 可以将部分工作移到异步链路
实现复杂度 相对可控 通常更高
失败恢复 依托数据库事务与 Outbox 需要预占状态恢复与补偿
适合情况 数据库容量足够、正确性优先 经过压测证明需要更高入口吞吐

国王终于意识到：

“性能优化不能依靠牺牲正确性换取漂亮的 QPS。”

“正是。”

第六幕：消息队列——数据库不应该承担所有后续工作

经过一周的讨论，工程委员会决定采用分层方案。

对于抢购活动，入口负责资格判断与预占。

对于通知、积分、运营事件等后续任务，则使用消息队列解耦。

一、拆分同步链路与异步链路

架构师重新划分。

订单核心事务与异步事件

路径 核心步骤 边界
同步核心事务 条件扣减库存、创建订单、写入 Outbox 同一数据库事务保护核心事实
异步派生任务 短信、积分、用户画像、实时统计 事件可靠发布，消费端幂等与重试

异步任务不应被误画为必须依次完成的同步步骤。不同派生任务可以独立消费同一业务事件。

二、消费者必须幂等

林澈写出订单事件消费逻辑。

@Transactional
public void handle(OrderCreatedEvent event) {
    if (processedMapper.exists(event.eventId())) {
        return;
    }

    pointsMapper.addPoints(
        event.userId(),
        event.points()
    );

    processedMapper.insert(event.eventId());
}

架构师看了一眼。

“这还不够严谨。”

“为什么？”

“两个消费者可能同时执行 exists，结果都发现未处理。”

“然后它们都发放积分。”

林澈愣住。

“那我们应该依赖数据库唯一约束？”

“正确。”

架构师修改方案：

CREATE TABLE processed_event (
    event_id VARCHAR(64) PRIMARY KEY,
    processed_at DATETIME NOT NULL
);

然后将“抢占事件处理权”和“发放积分”放进同一事务。

@Transactional
public void handle(OrderCreatedEvent event) {
    int inserted = processedMapper.insertIfAbsent(
        event.eventId()
    );

    if (inserted == 0) {
        return;
    }

    pointsMapper.addPoints(
        event.userId(),
        event.points()
    );
}

“这里假设 insertIfAbsent 由数据库唯一约束实现原子去重，并且积分更新与去重记录参加同一个本地事务。”

“如果积分发放涉及外部服务，那就不是这个本地事务能直接保证的事情了。”

“因此，真实设计还要根据副作用的所在系统选择相应的幂等或协调方案。”

三、为什么先完成事务，再确认消息？

架构师继续解释：

“如果消费者先 ACK，之后数据库事务失败，消息可能无法重新投递。”

“如果数据库提交成功之后再 ACK，虽然可能重复投递，但可以通过幂等去重。”

“对于业务任务，通常更容易接受至少一次投递，并在业务层保证重复处理安全。”

“不过，重试必须有上限或可控的退避策略。”

“不能让一个永久失败的消息无限占用消费资源。”

第七幕：WebSocket 军团——百万连接不等于百万线程

又过了一个月。

交易功能终于稳定。

但天穹直播平台的产品经理提出了新要求。

“陛下，用户进入直播间后，要实时收到弹幕、点赞数量与订单成交提示。”

国王看向林澈。

“怎么实现？”

林澈回答：

“WebSocket。”

“很好。”

“但如果有一百万条连接呢？”

林澈犹豫了一下。

“需要一百万个线程？”

Netty 将军立即走上前。

“不需要。”

一、事件驱动的连接管理

Netty 展开一张图纸。

100 万用户
     ↓
入口负载均衡
     ↓
WebSocket Gateway 集群
     ├── Gateway A：维护部分连接
     ├── Gateway B：维护部分连接
     ├── Gateway C：维护部分连接
     └── ...

“使用非阻塞 I/O 与事件循环，一个线程可以管理多个 Channel。”

“但这不代表连接没有成本。”

“每条连接仍然需要一定的内核与应用资源。”

“消息发送时，还需要足够的网络带宽。”

二、怎样向一个直播间广播消息？

Netty 将军继续解释。

“如果用户向房间 1001 发送弹幕，不能简单要求每台 Gateway 都扫描全部连接。”

“需要维护房间与连接的订阅关系。”

例如：

Room 1001
  Gateway A：3000 个连接
  Gateway B：5000 个连接
  Gateway C：2000 个连接

“消息分发层将弹幕发送给持有房间订阅者的 Gateway。”

“每个 Gateway 再向本地连接广播。”

三、慢客户端保护

突然，一名工程师报告：

“某些用户的网络非常慢，WebSocket 待发送队列不断增长！”

架构师立刻下令：

“不能无限缓冲。”

“对于普通弹幕，可以考虑丢弃过时消息、进行批量与节流。”

“对于关键通知，则应该将可靠性建立在持久化事件、客户端确认和补拉机制上。”

“WebSocket 连接建立成功，不等于每条消息都已经可靠送达用户。”

交易系统开始每天产生数千万条订单和更多用户行为事件。

国王问：

“我们怎样让运营大屏实时展示成交金额？”

架构师带领林澈来到数据大陆的东部。

一、不要让实时看板直接重复扫描 MySQL

“陛下，我们不能为了更新大屏，每秒重新统计亿级订单表。”

“应该让新增的可信业务事件进入实时数据管道。”

二、Flink 为什么需要 Watermark？

林澈问：

“如果支付事件本身有时间戳，直接按照时间统计不就行了？”

Flink 统帅回答：

“因为事件可能乱序到达。”

“20:04:58 发生的支付事件，可能在 20:05:10 才到达。”

“Watermark 可以帮助事件时间窗口决定何时触发计算。”

“但它不能保证迟到事件永远不会出现。”

“因此，还需要明确迟到事件如何修正统计结果。”

三、为什么实时与离线必须对账？

架构师指向另一座城市。

“Spark 还会定期根据可信支付明细进行历史重算。”

“我们可以利用它核对 Flink 的实时结果。”

“因为实时计算没有抛出异常，并不意味着业务指标一定正确。”

“支付事件可能重复。”

“退款口径可能不同。”

“时间窗口可能错位。”

“订单级金额也可能在 Join 时被重复累计。”

“一个成熟的数据平台，必须能解释每一分钱来自哪一笔可信业务事实。”

第九幕：Kubernetes 调度中心——让工程真正部署起来

国王宣布：

“代码已经写完。”

“现在全部部署到 Kubernetes！”

架构师再次阻止。

“陛下，在进入 Kubernetes 之前，我们应该先保证本地开发与测试环境能够稳定运行。”

一、Docker Compose：本地集成环境

林澈准备了一份基础 Compose 配置。

services:
  mysql:
    image: mysql:8.4
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
      MYSQL_DATABASE: empire
    ports:
      - "127.0.0.1:3306:3306"
    volumes:
      - mysql-data:/var/lib/mysql

  redis:
    image: redis:7.4
    ports:
      - "127.0.0.1:6379:6379"

  order-service:
    build: ./order-service
    depends_on:
      - mysql
      - redis
    environment:
      SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/empire
      SPRING_DATA_REDIS_HOST: redis
    ports:
      - "127.0.0.1:8080:8080"

volumes:
  mysql-data:

架构师说道：

“这只是简化的本地开发骨架，不是完整可运行的生产配置。”

“它还需要应用数据库账户、初始化迁移、健康检查、凭据管理，以及服务就绪控制。”

“depends_on 的基本启动顺序，也不能代替数据库真正就绪的检查。”

“另外，不能把开发环境的数据库密码直接硬编码进生产仓库。”

二、Kubernetes 部署不是复制一个 YAML 就结束

架构师展示：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
    spec:
      containers:
        - name: app
          image: registry.example.com/order-service:1.0.0
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: "500m"
              memory: "512Mi"
            limits:
              memory: "1Gi"
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 5

“这里的镜像地址仅是示例。”

“应用还需要正确配置 Spring Boot Actuator、数据库凭据与相关探针端点。”

“而且，Readiness Probe 不应设计成每次都执行昂贵的数据库全链路查询，否则健康检查本身可能成为压力来源。”

三、Rolling Update 与优雅停机

国王问：

“新版本发布时，旧 Pod 直接杀掉不就行了？”

架构师摇头。

“如果旧 Pod 正在处理订单事务，突然终止可能导致请求结果不明确。”

“如果它持有 WebSocket 连接，还会导致大量客户端断线。”

“因此，需要合理设计停止接流量、处理在途请求、释放资源和客户端重连。”

“业务层还需要有幂等和状态查询能力，解决用户在服务切换期间遇到的结果不确定问题。”

第十幕：可观测性法庭——怎样知道系统到底出了什么问题？

系统终于完成集成。

架构师没有立刻宣布上线。

而是提出一个问题。

“林澈，假设用户说订单创建很慢，你怎样排查？”

林澈回答：

“看日志。”

“如果日志没有明显报错呢？”

“看 CPU。”

“如果 CPU 只有 30% 呢？”

林澈沉默。

架构师走到黑板前，写下三个词。

Metrics、Logs、Traces。

一、Metrics：知道哪里异常

例如：

http.server.requests
hikaricp.connections.active
hikaricp.connections.pending
jvm.memory.used

“通过 Micrometer、Prometheus 等工具，可以收集和观测相关指标。”

“监控时不仅要看平均值，还要看 P95、P99 和错误率。”

二、Logs：知道发生了什么

日志应该能够关联到具体请求。

traceId=abc123
orderId=9527
stage=DB_COMMIT
durationMs=320
result=SUCCESS

“但不能把银行卡信息、密码、凭据或其他敏感数据随意写入日志。”

三、Tracing：知道时间花在哪里

假设某次订单请求：

Gateway                 15ms
    ↓
OrderService            20ms
    ↓
等待数据库连接          280ms
    ↓
MySQL SQL                30ms
    ↓
响应                    10ms

国王看着时间线。

“原来 SQL 只花了 30 毫秒。”

“真正慢的是等待数据库连接。”

“正是。”

“如果我们只看 SQL 执行时间，可能误以为数据库完全没有问题。”

四、告警不能只看机器是否存活

架构师要求监控四类指标。

流量：QPS、事件输入速率。

延迟：P95、P99、队列等待时间。

错误：HTTP 错误率、业务失败率、消息重试。

饱和度：连接池、队列、线程池、CPU、磁盘与下游吞吐。

“对于实时链路，还需要看 Kafka Lag、Flink Watermark 进度、Checkpoint 和 Sink 写入状态。”

“监控必须反映用户体验，而不是仅证明所有进程都还活着。”

第十一幕：最后一次压测——十万 QPS 的真相

半年后。

帝国工程委员会重新召集所有人。

考官问：

“你们现在是否已经能够达到十万 QPS？”

林澈没有立即回答。

他打开了一份测试报告。

“考官，我们把流量拆成了三种。”

第一种：活动入口请求。

第二种：Redis 资格校验与库存预占。

第三种：订单持久化与异步履约。

“这三种吞吐量不能混为一谈。”

一、测试目标

假设某场优惠券活动：

总库存一万张。

峰值活动入口 100,000 QPS。

其中大部分用户没有资格、重复请求或已经遇到售罄状态。

最终能够获得预占资格的请求数量受到库存和业务规则限制。

“所以，十万入口 QPS，并不意味着数据库必须每秒创建十万笔成功订单。”

“但仍然需要应对大量入口判断、连接与限流请求。”

二、分层压测

终极压测 · 虚构验收记录

测试项目 示例结果
入口 API 峰值 100,000 QPS
入口校验 P99 85ms
库存超卖 未发现
重复领取 唯一约束验证通过
履约消费吞吐 2,000/s
消息恢复测试 按用例通过

全部数字为小说中的假设，不代表已经实际部署或测得相应性能。真实验收还需包含环境配置、统计窗口、请求分布、错误预算和故障覆盖范围。

国王问：

“为什么履约只有每秒两千？”

架构师回答：

“因为数据库最终持久化能力有其自身上限。”

“异步队列能够将入口峰值与下游处理速率解耦，但不能创造数据库容量。”

“如果活动的业务 SLA 要求一分钟内完成所有一万笔成功领取，消费者的可持续吞吐必须足以满足这个目标，并留有故障余量。”

“所以我们不仅检查 QPS，还检查从预占到最终结果的端到端延迟分布。”

三、如何证明没有超卖？

考官追问：

“你们说没有超卖，是因为监控显示零异常吗？”

林澈回答：

“不是。”

“我们会在并发测试和恢复测试后，核对权威库存与领取记录的不变量。”

例如：

已成功领取数≤活动总配额 \text{已成功领取数}\leq\text{活动总配额}

同时检查：

相同用户是否重复领取。

相同 requestId 是否重复产生业务结果。

预占成功但未履约的任务是否能够恢复或补偿。

补偿是否可能重复返还库存。

“还要验证服务在预占后崩溃、消息投递失败、消费成功但 ACK 丢失、数据库提交结果未知等故障窗口。”

考官终于点头。

“这才像真实的工程验收。”

半年后。

天穹直播平台终于通过了工程委员会的阶段验收。

王国已经不再只有一台 Spring Boot 服务器。

现在，它拥有入口网关、业务服务集群、缓存层、数据库事务、可靠消息系统、WebSocket 长连接服务，以及从 Kafka 到 Flink、ClickHouse 的实时分析链路。

但林澈知道，真正重要的变化并不在于组件数量。

而在于他终于能够回答那些以前无法回答的问题。

为什么库存不会超卖？

为什么重复消息不会重复发放积分？

为什么异步履约失败后仍然能够恢复？

为什么百万连接不需要百万个线程？

为什么增加消费者不一定能够消除消息积压？

为什么服务器 CPU 很低，接口却可能很慢？

为什么 Flink Checkpoint 成功，财务报表却仍然可能错误？

为什么十万入口 QPS 不等于十万订单事务 TPS？

又为什么一次成功的压测，不能证明系统永远不会发生故障？

国王 Java 看着年轻工程师。

“你现在认为，什么才是真正的高并发工程能力？”

林澈沉思了很久。

随后，他回答：

“不是知道多少中间件。”

“而是能在业务约束下设计系统，知道瓶颈在哪里，知道数据可能在哪一步出错，能够用代码保护正确性，用压测证明容量，用故障演练证明恢复能力。”

首席架构师终于露出笑容。

“很好。”

“但你现在只完成了工程的第一阶段。”

国王有些惊讶。

“还有下一阶段？”

架构师拿出一份新的报告。

这一次，报告中没有任何代码错误。

也没有任何数据库异常。

却有一项指标开始持续恶化。

线上系统的性能，正在随着每一次版本发布而逐渐下降。

“陛下，我们的工程现在能够运行。”

“接下来，要解决的是如何让它长期保持可靠。”

“一个人写出的高性能代码，如何在数百名工程师不断修改之后仍然保持正确？”

“我们需要建立容量回归测试、性能基线、灰度发布、自动回滚、混沌工程和工程质量门禁。”

“否则，再优秀的系统，也可能在不断迭代中慢慢崩溃。”
