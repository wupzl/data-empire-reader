上一章，Spring 王国终于建立了千万级直播交易平台。Nginx 守卫入口，Netty 管理百万长连接，Redis 抵挡热点流量，Kafka 运输交易事件，Flink 持续计算，ClickHouse 为帝国提供实时分析。

所有服务器都正常运行。所有监控指标都显示健康。

然而，财政大臣呈上的两份财务报表，却差了整整两千七百万。

这一次，没有宕机，没有超时，没有异常日志。

数据帝国遭遇了比服务器崩溃更加危险的敌人：错误但看似合理的数据。

第一幕：消失的两千七百万

数据大陆，凌晨两点。

皇宫议事厅灯火通明。

国王 Java 坐在王座上，脸色铁青。

他的面前摆着三份报告。

昨日成交报表 · 虚构事故数据

统计项 金额
MySQL 财务口径 8.20 亿元
Flink 实时口径 8.47 亿元
差异 2,700 万元

三份不同系统生成的数据，如果统计口径、事件处理和时间边界不同，就可能产生这种无法直接比较的结果。

“为什么？”国王冷冷地问。

MySQL 总督率先站起。

“陛下，我这里保存的交易记录是完整的。”

Kafka 将军立即反驳。

“我这里的消息都正常送达了！”

Flink 统帅皱眉。

“我的 Checkpoint 持续成功，没有出现状态恢复异常。”

ClickHouse 城主说道：

“查询只用了几十毫秒，结果就是 8.47 亿。”

国王怒道：

“我不是问谁运行得快！”

“我问的是，谁算错了！”

所有人陷入沉默。

首席架构师缓缓站起。

“陛下，我想先问一个问题。”

“什么问题？”

“这三份报表中的‘成交金额’，究竟是什么意思？”

国王愣住了。

“成交金额还能有几个意思？”

架构师从桌上拿起一张订单。

“假设用户创建了一笔 100 元的订单。”

“支付成功后，退款 30 元。”

“这笔订单的成交金额是多少？”

“100 元？”

“如果我们统计的是支付成功时的累计支付金额，可以是 100 元。”

“但如果统计的是某种退款后净支付口径，可能就是 70 元。”

“如果订单先使用了 20 元优惠券，而商品原价是 120 元，又该怎么算？”

国王沉默。

架构师又问：

“如果一张订单包含三件商品，金额分别是 40、30、30 元，我们按订单统计还是按商品统计？”

“如果一笔支付跨越了午夜，我们按照下单日期、支付日期，还是结算日期归属？”

“如果支付事件重复出现呢？”

“如果退款在第二天才发生呢？”

“如果历史数据被重新修正呢？”

首席架构师终于说出了这场战争的真相。

数据系统最大的危险之一，不是算不出来，而是每个系统都准确地计算了不同的东西。

第二幕：第一场审判——指标究竟是什么？

首席架构师将财政官、交易官、运营官全部召集到大厅。

他在黑板上写下：

GMV、支付金额、退款金额、净支付金额。

“今天，我们先不讨论 Flink，不讨论 Spark，也不讨论 Kafka。”

“先把指标定义清楚。”

一、GMV 与实付金额不是天然同义词

架构师解释：

“GMV 常用来描述一定业务范围内的交易总额，但不同企业可能采用不同定义。”

“有的使用下单金额，有的使用支付成功金额，有的对取消、退款及优惠的处理不同。”

“因此，我们不能仅凭 GMV 这个名字，就断定一条 SQL 一定正确。”

国王点头。

“那应该怎么办？”

“建立指标契约。”

例如，帝国决定定义一项指标：

指标契约：成功支付金额

指标编码 paid_amount
统计对象 成功支付事实
时间维度 业务支付成功时间
金额单位 人民币分
去重标识 唯一支付业务事件标识
退款处理 不从该指标中直接扣减，另设退款指标
统计时区 Asia/Shanghai
数据修正 允许迟到事件修正与重算

这是本章设计的示例业务定义，不代表所有企业的财务或 GMV 口径。

架构师继续说道：

“如果要计算退款后净支付额，可以定义另一个指标。”

净支付额=成功支付额−成功退款额 \text{净支付额}=\text{成功支付额}-\text{成功退款额}

“但退款按退款发生日期归属，还是回溯冲减原支付日期，必须另外明确。”

“这两个口径可能产生不同的每日趋势，即使长期总额一样。”

二、为什么金额最好使用整数分？

一名工程师问：

“我们直接用 double 保存金额，不行吗？”

架构师回答：

“Java 的 double 基于二进制浮点数，不能精确表示所有十进制小数。”

例如：

System.out.println(0.1 + 0.2);

可能得到：

0.30000000000000004

“因此，对于精确金额运算，可以采用整数最小货币单位，或在 Java 中使用 BigDecimal，并明确精度与舍入规则。”

“在数仓中，金额字段也需要使用适当的整数或定点数类型，避免反复浮点累加造成误差。”

三、为什么要先定义指标，再建数据仓库？

国王问：

“是不是先把所有数据都搬进仓库，再慢慢研究指标？”

架构师摇头。

“原始数据当然可以先保留。”

“但如果业务要依赖这些指标做经营决策，就应该先明确统计契约。”

“否则，后续每一层都会复制和传播错误理解。”

这时，架构师在地图上标出一座巨大的新城。

城门刻着四个字母：

ODS、DWD、DWS、ADS。

第三幕：四层数据仓库——从原始卷宗到帝国报告

数据仓库之城位于数据大陆中央。

它不是一间巨大的仓库。

而是一套组织数据、加工数据、统一语义和服务分析需求的体系。

架构师带国王走进第一层。

一、ODS：原始数据的接待大厅

“ODS，Operational Data Store。”

“在我们采用的分层规范里，它主要承担原始业务数据的接入和留存。”

“例如订单表、支付表、退款表、用户表，以及 Kafka 事件。”

国王问：

“为什么不直接在 ODS 里把所有错误数据都清洗掉？”

架构师回答：

“因为原始数据本身具有审计和追溯价值。”

“如果过早丢弃信息，后来发现处理逻辑有误，就可能无法重新构建正确结果。”

ODS 中可能记录：

order_id
payment_id
payment_status
amount_cent
source_updated_at
ingest_time
source_operation
source_position

“其中源变更位置、采集时间和操作类型，可以帮助我们理解数据从哪里来、何时被采集，以及是否发生过更新或删除。”

“当然，保留原始数据也必须符合隐私、权限和数据生命周期要求。”

二、DWD：清洗后的明细事实

架构师带国王进入第二层。

这里的档案官正在做四件事。

第一，规范字段和类型。

第二，识别重复数据。

第三，处理业务事件语义。

第四，将原始记录转换为具有明确粒度的事实数据。

“DWD 通常称为 Data Warehouse Detail。”

“它不是简单复制一遍 ODS。”

“我们要在这里确定事实粒度和关键业务规则。”

例如支付事实表：

dwd_payment_success

payment_id
order_id
user_id
room_id
paid_amount_cent
paid_at
payment_channel

“每一行到底表示一笔支付成功事实，还是一次支付状态变更事件，需要从一开始就定义清楚。”

“否则在 DWS 做 SUM 时，很容易重复计算。”

三、DWS：汇总与公共指标

接下来是第三层。

DWS，Data Warehouse Summary 或 Service 等命名在不同企业中存在差异，这里采用汇总服务层的含义。

“陛下，DWD 保存明细事实，而 DWS 负责把重复使用的汇总逻辑沉淀下来。”

例如：

dws_room_payment_1d

stat_date
room_id
paid_amount_cent
payment_count
paying_user_count

“这里统计某直播间每天的成功支付金额、支付次数与去重支付用户数。”

“但要注意，支付金额可以直接加总，而跨天的独立支付用户数不一定能直接相加。”

“因为同一个用户可能连续两天支付。”

四、ADS：面向业务的应用报表

最后，架构师打开了第四层大门。

ADS，Application Data Service。

这里的结果直接服务运营、财务、BI 看板和业务决策。

例如：

ads_live_room_rank_today

rank
room_id
room_name
paid_amount_cent
conversion_rate

“这一层更接近具体业务需求。”

“直播排行榜、经营驾驶舱、活动复盘，都可以构建相应的数据应用结果。”

数据仓库四层体系

层次 角色 主要内容
ODS 原始接入 业务数据、变更日志、原始事件
DWD 明细事实 清洗、去重、标准化、明确粒度
DWS 公共汇总 按主题汇总，沉淀共享指标
ADS 应用服务 面向 BI、看板与业务报表

数据由接入走向加工与服务，各层保留清晰的职责与可追溯关系。

国王凝视着这座四层城市。

“我明白了。”

“原始数据进入 ODS。”

“DWD 将数据整理成可信的业务明细。”

“DWS 计算共享的汇总结果。”

“ADS 为具体应用提供数据。”

架构师点头。

“这是很好的入门理解。”

“但不能认为数据经过四层就天然正确。”

“每一层都必须有明确的输入、输出、质量检查与责任人。”

第四幕：事实表与维度表——帝国必须知道每一笔交易发生了什么

当国王走进 DWD 大厅时，发现档案官正在争吵。

一个人说：

“订单表应该包含用户名！”

另一个人说：

“还应该包含用户城市、商品类别、主播等级！”

第三个人说：

“干脆把所有字段都放到一张表里！”

架构师摇了摇头。

“诸位，我们需要先分清事实与维度。”

一、事实表：记录发生的业务

假设用户张三在直播间购买了一件商品。

支付 199 元。

这是一件业务事实。

我们可以记录：

payment_id = 50001
order_id = 10001
user_id = 20001
product_id = 30001
room_id = 40001
amount_cent = 19900
paid_at = 2027-01-01 20:05:00

“事实表通常记录业务过程中的事件、度量或状态。”

“例如支付成功事实、订单明细事实、商品曝光事实。”

二、维度表：描述事实发生的背景

国王问：

“那么用户所在城市、商品分类、主播等级呢？”

架构师回答：

“这些可以属于维度属性。”

例如：

dim_user
  user_id
  region
  register_channel

dim_product
  product_id
  category
  brand

dim_room
  room_id
  anchor_id
  room_category

“维度使我们能够回答‘按什么角度分析’。”

“事实则告诉我们‘发生了什么、产生了多少’。”

三、粒度 Grain：决定一行代表什么

架构师在黑板上写下一个词。

Grain，事实粒度。

“陛下，设计事实表的第一步，不应该是选字段。”

“而是明确一行代表什么。”

假设一个订单购买了三件商品：

订单 商品 金额
1001 A ¥50
1001 B ¥30
1001 C ¥20

如果事实表采用订单商品行粒度，那么这三行代表三条订单明细。

但如果再把一张订单级优惠记录直接 Join 到三条明细，可能造成优惠金额被重复加总。

国王猛然站起。

“这不是又算出假数据了吗？”

“正是。”

“多表 Join 时，如果两边粒度不匹配，可能产生行数膨胀。”

“在统计之前，要确认连接关系是一对一、一对多还是多对多。”

四、星型模型与雪花模型

星型模型：事实表位于中心

中心事实表 关联维度 描述内容
支付事实 用户维度 地区、注册渠道
支付事实 商品维度 品类、品牌
支付事实 直播间维度 主播、房间类别

逻辑关系：事实表通过维度键连接各维度。使用历史维度版本时，代理键与有效时间必须配套设计。

“星型模型通常把事实表放在中心，周围直接连接维度表。”

“雪花模型则进一步将部分维度规范化，形成更复杂的维度关联结构。”

星型模型往往更容易理解和查询，但可能存在维度属性冗余；雪花模型可能减少某些冗余，却增加 Join 和查询复杂性。

Kimball 维度建模体系对事实粒度、维度以及缓慢变化维度都有系统定义。

第五幕：时光档案——用户换了城市，历史报表应该改变吗？

国王以为事实表与维度表已经解决问题。

然而，历史档案管理员拿出一个案例。

“陛下，张三去年住在北京，今年搬到了上海。”

“如果我们分析去年不同城市的消费额，这笔订单应该算到北京还是上海？”

国王脱口而出：

“当然是北京！”

管理员问：

“可是 dim_user 里的城市已经更新成上海了。”

国王皱眉。

“那历史数据岂不是改变了？”

架构师回答：

“您终于遇到了 SCD。”

SCD：Slowly Changing Dimension，缓慢变化维度。

一、Type 1：直接覆盖历史

旧记录：

user_id = 1001
city = 北京

用户搬家后：

user_id = 1001
city = 上海

“这种策略保留最新属性，历史属性被覆盖。”

“它适合不需要保留历史版本，或者需要纠正错误属性的场景。”

二、Type 2：增加历史版本

“如果需要保留用户所属城市的历史，我们可以新建维度版本。”

代理键 用户 ID 城市 生效时间 失效时间
501 1001 北京 2025-01-01 2026-06-01
782 1001 上海 2026-06-01 9999-12-31

“当事实发生在 2025 年，就可以关联当时生效的北京版本。”

“当事实发生在 2027 年，就可以关联上海版本。”

“其中代理键用于区分同一业务用户的不同历史版本。”

这就是 SCD Type 2 的核心思想：变化时增加新行，而不是覆盖旧行。

三、为什么 Type 2 也不简单？

架构师继续问：

“如果用户的地址变更事件晚到了三天呢？”

“如果我们重新修订历史生效时间呢？”

“如果同一条事件重复同步呢？”

国王沉默。

“这些都需要通过版本区间、业务时间、变更顺序及幂等逻辑处理。”

“不能简单地对维度表执行 INSERT，就认为 SCD2 已经实现正确。”

第六幕：CDC 信使——MySQL 的每一次变化，如何传到数据仓库？

这一天，Kafka 将军来到皇宫。

“陛下，我们需要把 MySQL 的支付事实同步到数据仓库。”

国王说道：

“很简单，每隔一分钟执行一次 SQL。”

SELECT *
FROM payment
WHERE updated_at > :last_sync_time;

架构师没有立刻否定。

“这种增量轮询，在一些简单场景下确实能使用。”

“但它存在几个常见难点。”

“如果一条记录删除了，怎么发现？”

“如果更新时间精度不足，边界上的多条记录怎么处理？”

“如果事务还没提交，或者数据的更新顺序与时间字段不一致，怎么办？”

“如果数据库每次都要扫描大量记录，又该如何控制压力？”

国王问：

“还有更好的方式吗？”

“可以考虑 CDC。”

一、CDC：Change Data Capture

CDC 是变更数据捕获。

“它不是反复读取整个表，而是捕获数据源中发生的插入、更新和删除等变更。”

在常见的 MySQL 日志式 CDC 中，可以利用 Binlog 等机制获取数据库变更。

MySQL
  ↓
Binlog
  ↓
CDC Connector
  ↓

  ↓
Flink / Spark / 数仓

二、为什么需要快照加增量？

国王问：

“如果一张表已经有十亿条历史记录，CDC 开始运行后，难道只能拿到新变化？”

架构师回答：

“我们通常还需要初始化已有数据。”

“一类典型方案是先读取历史快照，并在过程中协调捕获后续增量变化。”

“这样能够构建初始表状态，再继续消费持续发生的更新。”

“但快照与增量之间如何衔接，必须由连接器的具体一致性机制保证。”

“不能随便先执行 SELECT *，再去读取当前 Binlog，否则两者之间可能出现数据缺口或重复。”

三、删除事件与撤回语义

架构师展示：

INSERT：新增支付记录
UPDATE：支付状态改变
DELETE：删除一条业务记录

“下游必须理解这些消息代表的是数据库行变化，还是已经解释好的业务事件。”

“比如支付表从 UNPAID 更新为 PAID，不代表每次更新这行记录都应该新增一次成交金额。”

“订单状态后续改变、补充备注，也不能再次加钱。”

四、CDC 与 Outbox 的区别

国王问：

“那我们之前设计的 Outbox，是不是没必要了？”

架构师回答：

“不是。”

“CDC 说明如何捕获数据变化。”

“Outbox 说明如何在业务数据库事务中可靠记录待发布的业务事件。”

“我们完全可以通过 CDC 将 Outbox 事件传递到 Kafka。”

“这样既利用数据库本地事务保证业务状态与事件记录同时提交，又利用变更捕获完成异步发布。”

“但消息重复、Schema 变更、历史回放和下游幂等仍需设计。”

第七幕：ETL 与 ELT——先加工再入库，还是先入库再加工？

数据仓库已经建成。

但帝国工程师分成了两个派系。

一个派系主张：

“数据必须先清洗，再进入分析仓库！”

另一个派系反驳：

“应该先保存数据，再利用数仓的计算能力进行转换！”

国王被吵得头疼。

架构师说道：

“这就是 ETL 与 ELT 的区别。”

ETL

Extract → Transform → Load。

抽取、转换、加载。

“数据从源系统抽取后，先经过转换处理，再加载到目标分析系统。”

ELT

Extract → Load → Transform。

抽取、加载、转换。

“数据先进入具备存储与计算能力的目标平台，再在平台内部完成转换。”

对比 ETL ELT
转换位置 通常在加载目标系统之前 通常在目标数据平台内部
原始数据保留 取决于架构设计 常结合原始数据留存
常见实践 外部数据集成和预处理 云数仓、湖仓内 SQL 转换
选择依据 数据安全、处理能力、成本、时延、治理要求 同左

“陛下，不要把 ETL 理解成旧技术、ELT 理解成必然先进的技术。”

“它们是不同的数据处理安排。”

“有些敏感数据在进入目标平台前，就需要完成脱敏和校验；有些大规模转换更适合利用目标平台的分布式计算能力。”

第八幕：湖仓王国——HDFS、Parquet、Iceberg 与计算引擎的分工

深夜。

国王走进最深处的仓库。

管理员告诉他：

“陛下，除了结构化订单数据，我们还有点击日志、图片元数据、模型训练样本、历史快照以及各种半结构化事件。”

“难道所有数据都应该放进 ClickHouse？”

架构师摇头。

“我们需要区分存储层、文件格式、表格式和计算引擎。”

一、数据湖

数据湖通常将大量不同类型的数据保存在能够扩展的存储基础设施上。

例如 HDFS 或对象存储。

“它可以存放原始日志、Parquet 文件、训练数据以及其他数据资产。”

“但如果缺少表管理、权限、元数据和质量治理，数据湖也可能变成难以理解的数据沼泽。”

二、Parquet 是什么？

“Parquet 是面向分析任务的列式文件格式。”

“它支持列裁剪、压缩，以及结合数据统计信息优化部分读取。”

“但单靠一堆 Parquet 文件，不能自动提供完整的事务表管理能力。”

三、Iceberg 又是什么？

架构师在黑板上写下：

Apache Iceberg：面向大型分析数据集的开放表格式。

“它不是替代 Spark 的计算引擎。”

“也不是一个与对象存储完全相同层级的存储服务。”

“Iceberg 通过表元数据和快照等机制管理底层数据文件，使多个兼容的计算引擎能够以表的方式访问分析数据。”

湖仓分层架构

层次 示例 职责
计算引擎 Spark / Flink / Trino 读取、计算、写入
表格式与元数据 Iceberg 表快照、Schema、分区元数据
文件格式 Parquet 列式编码与文件组织
存储介质 对象存储 / HDFS 保存数据文件与相关元数据

Iceberg 支持 Schema 与分区演进、快照查询等能力。计算引擎、表格式、文件格式与存储介质属于不同层次。

四、Time Travel：回到昨天的数据状态

国王问：

“如果数据工程师错误地覆盖了一张表，我们能恢复吗？”

架构师回答：

“如果采用了支持快照的表格式，且目标快照及相关文件仍然可用，就可能通过快照查询或回滚机制恢复。”

“这也是 Time Travel 的价值。”

“但不能将它等同于无限期备份。”

“历史快照与数据文件可能受到保留、清理和生命周期策略影响。”

“因此，关键数据仍然需要专门的备份与恢复设计。”

第九幕：两千七百万差异的真相

经过三天调查，架构师终于将所有证据带回皇宫。

“陛下，我们找到了问题。”

国王猛然起身。

“是谁算错了？”

“不是一个人。”

“是四个问题叠加。”

第一宗：重复支付事件

一部分支付成功消息重复投递。

Flink 的某条统计链路直接执行金额累加，没有完成业务事件级去重。

结果：重复增加了金额。

第二宗：退款口径不一致

MySQL 报表已经按某种净支付口径扣减退款。

而 Flink 大屏展示的是累计成功支付金额。

“这两项指标根本不是同一件事。”

第三宗：时间边界错误

一部分事件发生在北京时间凌晨，但被使用 UTC 自然日进行分组。

因此，某些订单被归到不同日期。

第四宗：订单行与商品行重复关联

一张订单有多件商品。

某个统计任务将订单级金额直接 Join 到商品明细行，再对订单金额求和。

于是，一笔订单的金额被重复累计。

国王闭上眼睛。

“所以 Kafka 没坏。”

“Flink 也没有明显宕机。”

“ClickHouse 只是很快地返回了错误口径的数据。”

架构师点头。

“这就是为什么可用性、性能和数据正确性必须分别验证。”

一、怎么进行对账？

架构师制定了三层对账方案。

第一层：数量对账。

源系统有多少笔支付成功事实？

DWD 有多少笔去重后的支付事实？

不同阶段数量差异来自哪里？

第二层：金额对账。

按统一统计口径、时间范围、币种和金额单位，比较源数据与派生结果。

第三层：明细差异定位。

如果汇总金额不一致，进一步根据支付 ID 找到缺失、重复或金额不一致的记录。

示意 SQL：

SELECT
    payment_id,
    COUNT(*) AS record_count
FROM dwd_payment_success
GROUP BY payment_id
HAVING COUNT(*) > 1;

“这可以发现部分重复记录，但不能独立证明整体数据正确。”

“因为缺失、错误状态、错误金额和错误时间，同样会导致结果不一致。”

二、如何防止对账任务自身出错？

架构师补充：

“我们需要保证双方使用的是可比较的数据版本或明确的统计截止点。”

“否则一边统计到 20:00，另一边只处理到 19:58，差异只是正常的异步延迟。”

“此外，金额必须采用一致的精度、币种、舍入方式和退款归属规则。”

交互实验：一次重复事件如何让报表失真？

数据口径与重复事件模拟器

国王看着模拟结果，久久没有说话。

“只改变几条处理规则，报表就会完全不同。”

“正是如此。”

“而在一亿条数据的规模下，这种错误可能被放大无数倍。”

一、数据质量的几个维度

维度 需要回答的问题
完整性 数据是否缺失？
唯一性 是否有不允许的重复记录？
有效性 字段是否满足业务规则？
一致性 不同系统的同口径数据是否一致？
及时性 数据是否在约定时间内到达？
准确性 数据是否正确反映真实业务？

架构师强调：

“准确性往往最难证明。”

“因为格式正确、字段非空、主键唯一，并不代表支付金额就一定正确。”

二、质量规则示例

-- 检查关键业务字段缺失
SELECT COUNT(*)
FROM dwd_payment_success
WHERE payment_id IS NULL
   OR paid_at IS NULL
   OR paid_amount_cent IS NULL;

-- 检查异常支付金额
SELECT COUNT(*)
FROM dwd_payment_success
WHERE paid_amount_cent <= 0;

“第二条规则是假设我们的成功支付事实不允许非正金额。”

“如果业务允许零元支付，就应该修改规则。”

“数据质量约束必须来源于真实业务定义，而不是无条件照搬模板。”

第十一幕：Java、Flink 与 Spark 的完整数仓工程

架构师终于展示了整个数据仓库的施工图。

“陛下，今天我们把之前学过的所有技术连接起来。”

企业级交易数仓架构

链路 数据路径 目标
权威事实接入 Spring Boot → MySQL → Outbox 发布 / CDC → Kafka 捕获订单、支付、退款事实
实时加工 Kafka → Flink → Redis / ClickHouse 清洗、去重、低延迟指标
历史加工 原始数据归档 → Iceberg / Parquet ↔ Spark ODS / DWD / DWS 历史存储、回溯与重算
服务与治理 加工结果 → ADS / BI / 报表服务 统一口径、质量校验与对账

实时加工与历史加工是两条配合的路径，不是将所有组件串成单条同步调用链。Outbox 事件与原始 CDC 的语义也需区分。

一、用 Flink 构建实时明细与指标

Flink 持续消费 Kafka 中可信的支付业务事件。

先完成事件解析和必要的业务去重。

再按事件时间生成支付明细或窗口汇总。

输出到支持相应写入语义的目标系统。

“如果我们的 Sink 只是普通的非事务写入，就需要结合业务唯一键、版本字段或补偿重算机制处理重试。”

“状态一致性与外部数据最终正确是两个不同层次的要求。”

二、用 Spark 重算历史结果

假设昨天的实时统计发生了错误。

我们仍然保留着完整的历史支付事实。

架构师写出：

from pyspark.sql import functions as F

# spark 为已初始化的 SparkSession；统一设置业务时区。
spark.conf.set("spark.sql.session.timeZone", "Asia/Shanghai")
payments = spark.read.parquet("/warehouse/dwd/payment_success")
daily = (
    payments
    .filter(F.col("paid_at") >= "2027-01-01")
    .filter(F.col("paid_at") < "2027-01-02")
    .groupBy("room_id")
    .agg(F.sum("paid_amount_cent").alias("paid_amount_cent"))
)
daily.write.mode("overwrite").parquet("/warehouse/rebuild/2027-01-01")

“这段代码只是展示批量汇总思路。”

“实际工程必须确认时间字段的类型与时区、DWD 已经正确去重，并使用安全的重算发布机制，避免覆盖生产读者正在访问的数据。”

“例如，可以先写入隔离版本，完成质量验证，再切换正式结果。”
