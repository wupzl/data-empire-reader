第一幕：一条 SQL，困住百亿条数据

数据大陆，凌晨两点。

Spring 王国的交易分析大厅内，运营总监正在准备第二天的经营会议。

他打开后台，选择了几个条件：

时间：过去三年。

地区：全国。

商品类别：电子产品。

统计指标：成交金额、支付用户数、平均订单金额。

然后点击“查询”。

五秒。

十秒。

三十秒。

屏幕依然在旋转。

最后，一行红色文字浮现。

Query timeout

“陛下！我们的分析系统又坏了！”

国王 Java 立即召集数据库总督。

“这次数据又对不上了？”

“不，陛下。”

“数据经过对账，完全符合我们制定的统计口径。”

“那为什么查询不出来？”

“因为我们现在有一百亿条交易明细。”

国王沉默了。

数据库总督将 SQL 投影在墙上。

SELECT
    province,
    category_id,
    SUM(paid_amount_cent) AS total_amount,
    COUNT(DISTINCT user_id) AS paying_users
FROM payment_detail
WHERE paid_at >= '2024-01-01'
  AND paid_at < '2027-01-01'
GROUP BY
    province,
    category_id

“陛下，我们需要扫描大量数据、执行分组聚合、维护去重状态，并对聚合结果排序。”

“现在您要求的是——从海量记录中提取统计规律。”

“这两种任务，需要不同的作战方式。”

他在地图上画出两个王国。

第二幕：OLTP 与 OLAP——两种完全不同的战争

架构师带国王走进第一座城市。

这里是 MySQL 的交易王国。

每个窗口前，都有一名管理员负责处理具体业务。

有人创建订单。

有人扣减库存。

有人查询账户。

有人修改支付状态。

“陛下，这类工作负载称为 OLTP。”

OLTP：Online Transaction Processing，在线事务处理。

架构师继续说道：

“OLTP 经常涉及较小范围的数据读写，需要高并发、低延迟，以及明确的事务一致性。”

接着，两人来到另一座城市。

这里没有一个个办理业务的窗口。

而是巨大的计算大厅。

一百名分析官同时阅读数十亿份记录。

他们想知道：

过去三年，哪类商品销售增长最快？

哪个省份的直播成交额最高？

不同用户群体的留存率如何？

营销活动的转化率是否提高？

“这类工作负载称为 OLAP。”

OLAP：Online Analytical Processing，在线分析处理。

两种系统的典型差异

维度 OLTP OLAP
主要目标 正确、高效地处理业务事务 高效完成数据分析
典型操作 点查、插入、更新、删除 扫描、过滤、Join、聚合
数据访问 通常访问少量记录 可能访问海量记录
存储设计 常采用行式存储 常采用列式存储
关注重点 事务、并发、索引、延迟 吞吐、压缩、并行分析
代表系统 MySQL、PostgreSQL ClickHouse、StarRocks

架构师提醒：

“这只是典型工作负载的对比，并不是绝对边界。”

“MySQL 也能进行分析查询，ClickHouse 和 StarRocks 也不只会执行简单汇总。”

“真正决定选型的，是数据规模、查询形态、更新需求、延迟目标和部署成本。”

国王问：

“那么，为什么列式数据库更适合很多分析任务？”

架构师笑了。

“这就是我们下一场战争的关键。”

第三幕：列式存储——为什么只读三列，就能节省大量工作？

国王走进 MySQL 档案馆。

馆内保存着一百亿份订单档案。

每份档案都包含二十个字段。

order_id
user_id
room_id
product_id
category_id
province
amount
status
paid_at
...

架构师问：

“陛下，如果我们只想统计成交总额，需要哪些字段？”

“amount。”

“如果按地区统计呢？”

“province 和 amount。”

“如果只涉及这两列，为什么要读取所有其他字段？”

国王恍然大悟。

“所以我们应该把同一列的数据放在一起？”

“正是。”

一、行式存储

行式存储通常把一行记录的字段组织在一起。

订单1：[ID, 用户, 金额] → 订单2：[ID, 用户, 金额]

同一行的字段相邻组织，更适合许多点查、整行读取和事务更新场景。

二、列式存储

列式存储则把同一列的值组织在一起。

ID 列：[1, 2]；用户列：[A, B]；金额列：[100, 200]

相同字段集中组织，分析时可以只读取所需列。

国王问：

“是不是列式存储只快在少读取了几列？”

架构师摇头。

“还有两个非常重要的原因。”

三、压缩效率

“同一列的数据通常具有相近类型与相似分布。”

例如：

province:
山东
山东
山东
北京
北京
北京

“这些值可能适合字典编码、游程编码等压缩方式。”

“而连续排列的整数、时间戳，也可能利用适当的编码减少存储空间。”

“数据变小，磁盘或网络需要传输的字节可能更少。”

ClickHouse 的列式存储设计结合压缩、块级元信息与按需读取，正是分析型查询的重要性能基础。

四、向量化执行

架构师又提出一个问题。

“假设我们需要计算一亿条记录的金额之和。”

传统直观思路是：

for (Order order : orders) {
    total += order.getAmount();
}

“而向量化执行可以将数据按批次组织，让算子对一批数据进行处理。”

“这样可以减少部分逐行执行和对象处理开销，更好地利用 CPU 缓存和指令执行能力。”

“不过，向量化不等于每个 SQL 运算都必然使用某种 SIMD 指令。”

“它是一组面向批量数据处理的执行优化思想。”

第四幕：MergeTree——ClickHouse 的真正秘密

数日后。

ClickHouse 城主终于来到王宫。

国王开门见山：

“听说你的查询速度很快。”

“是不是因为你有比 B+ 树更强大的索引？”

ClickHouse 城主笑了。

“陛下，我们的思路不完全一样。”

“MySQL InnoDB 的聚簇 B+ 树，适合大量事务型访问模式。”

“而 MergeTree 面向的是高吞吐写入、按排序键组织数据，以及高效的分析型扫描。”

“请允许我解释。”

一、Part：一批数据形成一座小仓库

当数据写入 MergeTree 表时，系统会形成数据 Part。

一个 Part 内部的数据按照排序键组织。

例如：

CREATE TABLE live_payment
(
    payment_id UInt64,
    room_id UInt64,
    user_id UInt64,
    paid_at DateTime,
    amount_cent Int64
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(paid_at)
ORDER BY (room_id, paid_at, payment_id);

架构师解释：

PARTITION BY 决定分区组织方式。

ORDER BY 决定 MergeTree 中数据的排序键。

“最需要记住的是，ClickHouse 的 ORDER BY 在这里不是查询语句中的排序。”

“它影响的是数据写入后的物理组织。”

二、Part 的不断合并

假设每次写入都产生一些数据 Part。

Part A：10 万行
Part B：12 万行
Part C：8 万行
Part D：15 万行

ClickHouse 会在后台根据合并策略，将部分小 Part 合并成更大的 Part。

MergeTree 的后台合并

三、为什么叫 MergeTree？

国王问：

“那它是不是一棵与 MySQL B+ 树一样的树？”

“不是。”

“MergeTree 的名字与有序数据 Part 的持续合并有关，不能简单把它理解成另一种 B+ 树。”

“它的主要查询加速机制之一，是排序键配合稀疏主索引。”

第五幕：稀疏主索引——为什么一百亿行不需要一百亿条索引？

架构师带国王来到一座巨大的索引大厅。

这里有一百亿条记录。

但是索引官却没有为每一行建立一条独立索引记录。

国王震惊。

“那怎么查找？”

ClickHouse 城主回答：

“我们使用 Granule。”

一、Granule 是什么？

“Granule 可以理解为 MergeTree 中索引与数据读取的重要粒度。”

“默认 index_granularity 常见配置是 8192 行，但实际 Granule 大小还可能受到字节大小等因素影响。”

“稀疏索引不需要为每一行保存一个主键入口，而是保存对应 Granule 的索引标记。”

假设有：

8192 行数据。

对应一个稀疏索引粒度。

如果一亿行在理想化情况下都按 8192 行划分：

1000000008192≈12207 \frac{100000000}{8192}\approx12207

“这只是数量级示意，实际每个 Part 都有自己的 Granule 与索引结构。”

国王问：

“是不是代表一次索引命中就能精确找到某一行？”

“并不是。”

“稀疏索引用于帮助排除不可能匹配的 Granule。”

“对于被保留下来的 Granule，仍需要读取必要列并执行进一步过滤。”

二、查询如何跳过数据？

假设表的排序键是：

ORDER BY (room_id, paid_at)

查询：

SELECT SUM(amount_cent)
FROM live_payment
WHERE room_id = 1001
  AND paid_at >= '2027-01-01'
  AND paid_at < '2027-02-01';

“由于数据按 room_id 和 paid_at 组织，相关查询有机会通过稀疏主索引跳过大量不相关 Granule。”

“这就是数据裁剪。”

“但如果查询条件与排序键毫无关系，仍可能读取更多数据。”

三、ClickHouse 的主键不是 MySQL 的主键

国王问：

“我们定义了主键，是不是自然保证 payment_id 唯一？”

架构师摇头。

“标准 MergeTree 的主键不负责像 MySQL 唯一约束那样拒绝重复业务记录。”

“其主要作用是辅助有序组织和数据跳过。”

“如果 Kafka 中相同支付事件重复出现，普通 MergeTree 表不会自动替我们完成严格的业务去重。”

“这是面试中必须明确的一点。”

交互实验：排序键如何影响扫描范围？

稀疏索引与 Granule 裁剪模拟

第六幕：Partition 与 ORDER BY——两把看似相同、实际不同的钥匙

第二天，数据库工程师提出了一个新的设计。

“陛下，我们有一百亿条数据。”

“既然分区能够减少扫描，我准备按照 user_id 分区。”

国王很满意。

“用户有一千万个，分成一千万个分区，定位不是很精准吗？”

ClickHouse 城主脸色瞬间变了。

“千万不要直接这样设计！”

一、Partition 主要解决什么问题？

架构师解释：

“ClickHouse MergeTree 的 Partition 可以帮助组织数据生命周期，并在查询条件匹配时进行分区裁剪。”

“例如按照月份分区。”

PARTITION BY toYYYYMM(paid_at)

“如果我们需要删除某个月已经过期的数据，就可以考虑分区级的数据管理操作。”

“如果查询只涉及最近一个月，也有机会排除其他月份。”

“但 Partition 不是越多越好。”

二、为什么过多分区很危险？

“陛下，MergeTree 的数据 Part 位于具体 Partition 内。”

“分区过多可能造成 Part 数量与元数据管理成本增长。”

“而且后台合并通常在分区内部进行，不会随意跨分区合并。”

“如果按一千万个用户分别分区，高基数分区键可能导致大量小 Part，增加写入和维护压力。”

ClickHouse 官方教程也强调，分区更应优先围绕生命周期和数据管理需求设计，而不是把高基数分区当成索引的替代品。

三、Partition 和 ORDER BY 的区别

国王要求架构师总结。

设计 主要职责 示例
PARTITION BY 将数据组织到不同逻辑分区，方便生命周期管理与裁剪 按月分区
ORDER BY 决定 Part 内数据排序，支持稀疏索引的数据跳过 (room_id, paid_at)
跳过索引 根据额外的块级元信息排除部分数据块 minmax、set、bloom filter 等

“陛下，要根据主要查询模式选择排序键。”

“假设大多数查询都带 room_id，然后按照时间范围过滤，(room_id, paid_at) 可能是一个合理的候选。”

“但如果大量查询只按照时间过滤、完全不指定 room_id，这个排序键就未必理想。”

四、跳过索引不是传统二级索引

架构师展示了一段示意 DDL。

CREATE TABLE user_events
(
    user_id UInt64,
    room_id UInt64,
    event_type LowCardinality(String),
    event_time DateTime,

    INDEX idx_event_type event_type
        TYPE set(100) GRANULARITY 4
)
ENGINE = MergeTree
ORDER BY (room_id, event_time);

“这个 set 跳过索引的效果取决于每个索引块中不同值的数量。”

“如果块内不同值过多，索引效果可能很差。”

“Bloom Filter 类索引也存在误判，通常无法保证每次都跳过所有不匹配数据。”

国王问：

“怎么知道索引到底有没有效果？”

“不要凭感觉。”

“通过 EXPLAIN、查询日志与实际读取数据量观察。”

“例如在支持相应语法的 ClickHouse 版本中：”

EXPLAIN indexes = 1
SELECT count()
FROM user_events
WHERE room_id = 1001
  AND event_time >= '2027-01-01';

“重点关注有多少 Part、Granule 被选择，以及实际读取了多少行、多少字节。”

第七幕：去重法庭——十亿用户中，到底有多少不同的人？

一场直播活动结束。

运营总监提出一个问题。

“陛下，今天究竟有多少独立用户访问了平台？”

数据库官员写下：

SELECT COUNT(DISTINCT user_id)
FROM user_events;

国王问：

“这不就解决了吗？”

架构师说道：

“逻辑上简单，但计算代价不一定小。”

“假设有一百亿条事件，其中包含五千万个不同用户。”

“精确去重通常需要维护足以区分这些用户的状态。”

“这可能消耗大量内存和计算资源。”

一、精确去重

ClickHouse 可以使用：

SELECT uniqExact(user_id)
FROM user_events;

“它适用于必须返回精确基数的场景。”

“但不同值数量越大，聚合状态通常也会越大。”

二、近似去重

“如果只是运营大屏，允许一定统计误差，我们可能采用近似去重算法。”

例如：

SELECT uniqCombined64(user_id)
FROM user_events;

“这是 ClickHouse 中可用于近似去重的函数之一。”

“HyperLogLog 则是近似基数估计领域的一种经典算法。”

“不同 ClickHouse uniq 函数采用的具体算法并不完全相同，不应该把它们统称为完全相同的 HLL 实现。”

ClickHouse 官方介绍对 uniqExact 和近似去重函数的状态规模与效率进行了对比。

三、Bitmap

国王问：

“如果我们的用户 ID 全部都是整数，还能怎么处理？”

架构师回答：

“Bitmap 是另一种值得了解的集合表示方式。”

“它可以支持集合基数、交集和并集等运算。”

“例如计算今天访问用户与昨天访问用户的交集。”

留存用户集合=U昨天∩U今天 \text{留存用户集合}=U_{\text{昨天}}\cap U_{\text{今天}}

“Bitmap 很适合某些用户集合分析，但其存储与性能效果取决于 ID 范围、基数和数据分布。”

“它不是所有去重场景的万能替代。”

四、如何选择？

去重策略对比

方法 结果性质 适合场景
uniqExact 精确 财务或严格对账所需的精确人数
uniqCombined64 近似 大规模运营看板
HLL 类结构 近似 可合并的大规模基数估计
Bitmap 视集合构建方式而定，可精确 整数 ID 集合、交并差分析

近似算法的误差和资源开销应按实际数据分布测试。不要将近似人数用于必须精确的财务结算。

五、一个容易忽略的陷阱

架构师问国王：

“昨天有 100 万独立用户。”

“今天也有 100 万独立用户。”

“两天合起来，一定有 200 万独立用户吗？”

国王立即回答：

“不一定，有些用户两天都来了。”

“正是。”

“不同时间窗口的去重人数，不能简单求和。”

“如果需要跨天精确去重，必须保留能够合并的集合信息或重新在对应范围内计算。”

第八幕：物化视图——为什么每次都从一百亿行重新计算？

此时，帝国最热门的查询是：

“每个直播间今天成交了多少钱？”

同样的查询，每分钟被调用成千上万次。

国王问：

“难道每次都必须从原始支付明细计算？”

架构师摇头。

“我们可以考虑预聚合。”

一、预聚合的思想

假设原始明细有一亿行。

最终只需要一万个直播间的成交额。

我们可以提前按照直播间汇总。

原始支付事件
      ↓
按 room_id 聚合
      ↓
一万条直播间统计
      ↓
实时大屏查询

“这样查询时只需要读取已经计算好的结果。”

“这就是空间换时间。”

二、ClickHouse 物化视图

架构师展示一个简化示例。

CREATE TABLE room_gmv_state
(
    room_id UInt64,
    stat_date Date,
    amount_state AggregateFunction(sum, Int64)
)
ENGINE = AggregatingMergeTree
ORDER BY (stat_date, room_id);

创建基于插入数据触发聚合的物化视图：

CREATE MATERIALIZED VIEW room_gmv_mv
TO room_gmv_state
AS
SELECT
    room_id,
    toDate(paid_at) AS stat_date,
    sumState(amount_cent) AS amount_state
FROM live_payment
GROUP BY room_id, stat_date;

查询聚合状态：

SELECT
    room_id,
    sumMerge(amount_state) AS gmv_cent
FROM room_gmv_state
WHERE stat_date = '2027-01-01'
GROUP BY room_id
ORDER BY gmv_cent DESC
LIMIT 100;

架构师解释：

“这个方案展示了增量插入与聚合状态合并的基本思路。”

“但如果上游重复插入支付事件，这个求和视图同样可能重复计数。”

“而如果原始支付记录后来被更新或删除，普通基于插入触发的增量物化视图也不能被简单理解为自动回滚之前的业务金额。”

“数据更新和修正策略必须单独设计。”

三、物化视图的代价

国王问：

“那我们把所有 SQL 都提前做成物化视图不就行了？”

架构师回答：

“物化视图要消耗存储空间。”

“也会增加写入或刷新开销。”

“此外，查询维度组合千变万化，不可能无限制地提前计算所有组合。”

“真正适合预聚合的，是高频、稳定、收益明确的查询。”

第九幕：StarRocks 挑战王座——频繁更新的实时分析

就在 ClickHouse 取得胜利时，一位新的挑战者来到王宫。

他穿着黑色盔甲，胸前刻着：

StarRocks。

“陛下，我同样擅长分析。”

“而且，在需要实时更新、多表关联和复杂 SQL 的场景中，我有另一套架构设计。”

国王问：

“你和 ClickHouse 到底有什么区别？”

StarRocks 回答：

“请先理解我的 Primary Key Table。”

一、实时更新是如何进入分析系统的？

例如某个订单：

order_id = 1001
status = CREATED

之后变成：

order_id = 1001
status = PAID

再后来：

order_id = 1001
status = REFUNDED

“对于持续接收 MySQL CDC 更新的系统，我们希望分析表能够高效反映最新订单状态。”

“StarRocks Primary Key Table 使用主键索引与删除标记等机制处理 Upsert 和 Delete，从而支持实时更新场景。”

“其内部不是简单地让每次查询自行合并所有历史版本。”

这是 StarRocks 主键表的重要设计特征。

二、MPP：大规模并行分析

StarRocks 继续说道：

“我使用 MPP，即 Massively Parallel Processing，大规模并行处理架构。”

“复杂 SQL 可以由多个执行节点协同处理。”

“同时，向量化执行、Cost-Based Optimizer 和物化视图优化也是重要组成部分。”

StarRocks 官方文档将实时分析、向量化计算、成本优化器和物化视图列为其核心能力。

三、是不是 StarRocks 一定比 ClickHouse 强？

国王直接问：

“如果我只选一个，到底选谁？”

架构师打断了两位统帅。

“不能只看宣传中的性能倍数。”

“必须根据业务负载来测试。”

选型维度 ClickHouse StarRocks
大规模追加写入与扫描聚合 具有成熟的 MergeTree 生态 同样具备列式与并行分析能力
高频行级更新 需选择合适表引擎与更新方案 Primary Key Table 是重要方案
复杂 Join 支持丰富的 Join 和执行优化 CBO 与 MPP Join 是重要设计
物化视图 具备多种物化与预聚合方案 支持同步、异步等物化视图能力
湖仓查询 具有相关集成能力 具有相关外部数据与湖仓查询能力
最终选择 取决于负载和运维约束 取决于负载和运维约束

“这张表只能作为评估维度。”

“不能据此直接判断同一份数据上谁的 P99 更低。”

“特别是在不同版本、部署架构和配置下，结论可能改变。”

四、物化视图自动改写

StarRocks 又展示了一项能力。

“当某个物化视图能够满足查询要求时，优化器可以尝试使用该物化视图改写执行计划。”

“这样，业务 SQL 不一定需要直接写出物化视图的表名。”

“但自动改写取决于语义匹配、刷新状态、优化器和具体特性限制。”

“对于异步刷新视图，还要明确允许多大数据延迟。”

StarRocks 官方资料也区分了普通视图和物化视图在存储、刷新成本、数据新鲜度和查询加速方面的差异。

第十幕：十亿行慢 SQL——真正的优化顺序

战争进入最关键的阶段。

帝国分析师提交了一条 SQL。

SELECT
    room_id,
    SUM(amount_cent) AS amount
FROM live_payment
WHERE paid_at >= '2027-01-01'
  AND paid_at < '2027-02-01'
GROUP BY room_id
ORDER BY amount DESC
LIMIT 100;

查询耗时十二秒。

国王立即问：

“要不要增加十倍 CPU？”

架构师回答：

“先判断查询到底耗费在哪里。”

他制定了一份排查流程。

第一步：检查查询是否扫描了过多数据

“首先看实际读取行数与字节数。”

“如果只查询一个月，却扫描了三年的数据，优先检查分区裁剪和排序键匹配情况。”

第二步：检查查询访问了多少列

“假设原表有六十列，而查询只需要 room_id、paid_at 和 amount_cent。”

“应观察底层扫描是否只读取必要列，以及是否存在额外的表达式和 Join 引入不必要数据。”

第三步：检查聚合状态

“如果 Group By 的 Key 具有极高基数，Hash 聚合可能需要大量内存。”

“如果还有精确去重，多维分组可能进一步放大状态规模。”

第四步：检查排序

“ORDER BY SUM(...) DESC LIMIT 100 可能只返回一百行。”

“但引擎仍然需要先完成足够范围内的聚合，才能知道哪一百个直播间金额最高。”

“不能只因为最终 LIMIT 100，就认为只会处理一百条记录。”

第五步：检查数据布局与 Part

“观察 Part 数量是否异常。”

“是否有过多小 Part？”

“后台 Merge 是否落后？”

“磁盘带宽、CPU、内存和并发查询是否互相争用？”

第六步：检查是否值得预聚合

“如果同一排行榜每秒被查询很多次，并且允许秒级统计延迟，可以考虑提前计算窗口汇总。”

“如果查询偶尔发生，且用户需要任意维度组合，就应评估预计算的收益是否值得维护成本。”

第十一幕：Java 后端如何设计分析 API？

国王终于问出了 Java 工程师最关心的问题。

“我们使用 Spring Boot。”

“如何把 ClickHouse 或 StarRocks 包装成生产系统中的分析服务？”

架构师拿出一份接口设计。

一、不要让前端直接拼任意 SQL

危险示例：

String sql = "SELECT * FROM " + tableName
           + " WHERE " + conditions;

“如果直接拼接用户输入，就可能造成 SQL 注入。”

“分析型 SQL 也需要严格控制表、维度、指标、筛选条件和排序字段。”

二、建立查询请求模型

public record AnalyticsQuery(
    LocalDate startDate,
    LocalDate endDate,
    List<String> dimensions,
    List<String> metrics,
    int limit
) {}

架构师说道：

“我们应定义允许的指标和维度白名单。”

“根据明确的规则生成 SQL。”

“动态标识符从固定映射中选择。”

“实际值通过驱动支持的参数绑定机制传入。”

三、查询保护

“陛下，如果任意用户都能发起扫描十年数据的分析查询，会发生什么？”

“分析集群可能被压垮。”

“所以需要查询治理。”

例如：

  • 用户级和租户级并发限制。
  • 最大时间范围与结果行数限制。
  • 查询超时与取消。
  • 对昂贵查询使用异步作业。
  • 对稳定热门指标使用结果缓存。
  • 对慢查询进行监控和归因。

四、不要把分析接口设计成无限分页

“假设前端要展示全国数千万用户的消费明细。”

“我们不能无条件允许：

LIMIT 10000000, 20

“应结合排序键和查询条件考虑游标分页、异步导出，或者限制交互式查询的数据范围。”

“对于大规模结果导出，最好使用独立任务和对象存储交付，而不是把所有数据塞进一次 HTTP 响应。”

五、简化的服务接口

@RestController
@RequestMapping("/api/analytics")
public class AnalyticsController {

    private final AnalyticsService service;

    public AnalyticsController(
            AnalyticsService service) {
        this.service = service;
    }

    @PostMapping("/query")
    public AnalyticsResult query(
            @RequestBody AnalyticsQuery request) {

        return service.execute(request);
    }
}

“这只是 Controller 的骨架。”

“生产环境还需要增加认证授权、输入校验、字段级访问控制、审计、超时和查询资源预算。”

“尤其不要允许普通运营用户通过任意维度组合读取不属于其权限范围的用户信息。”

第十二幕：五十亿条数据的最终验收

数周后，ClickHouse 与 StarRocks 两位统帅共同参加了帝国的性能评测。

国王提出要求：

“不要告诉我谁更先进。”

“给我一套能够验证的评测方案。”

架构师制定了五种查询。

OLAP 性能评测任务

Q1 指定直播间最近七天 GMV
Q2 过去一年商品类别排行榜
Q3 一亿事件的精确 UV
Q4 订单与用户、商品维度多表 Join
Q5 持续 CDC 更新下的低延迟查询

“测试时，两套系统要尽量使用可比较的硬件预算、数据口径、资源约束和查询并发。”

“同时应区分冷查询与热查询。”

“不能让一方提前缓存全部数据，另一方从冷存储读取，然后宣称前者快几十倍。”

“还需要观察写入吞吐、数据新鲜度、磁盘占用、内存、P95/P99，以及故障恢复能力。”

模拟性能实验：不同查询模式下的资源权衡

分析查询资源模型

国王看着不同查询类型的资源差异。

“现在我明白了。”

“数据量相同，查询方式不同，资源消耗可能完全不同。”

“因此不能仅仅说我们的数据库有一百亿行，就判断某条 SQL 应该快还是慢。”

架构师点头。

“正是如此。”

第十三幕：首席工程师的十道试炼

尾声：下一场战争——数据越多，越不能只靠查询

三个月后。

天穹直播平台的数据分析系统完成了新一轮改造。

ClickHouse 负责高吞吐日志分析和部分实时聚合。

另一组团队针对高频更新与复杂 Join 场景评估 StarRocks。

Flink 继续负责流式事件处理。

Spark 负责批量重算。

Iceberg 保存可追溯的历史分析数据。

MySQL 仍然作为交易事实的重要权威来源。

国王 Java 站在数据大陆最高的瞭望塔上。

“架构师，我们现在已经学会如何处理十万 QPS，如何存储 PB 级数据，如何实时计算，以及如何执行百亿行分析。”

“是不是终于能够毕业了？”

架构师微微摇头。

“陛下，我们只是学会了让系统处理更多数据。”

“但还有一个最危险的问题没有解决。”

“什么问题？”

“如果系统每天产生几十亿条事件，数据不断增长，存储成本持续增加。”

“如果每个业务团队都在建立自己的指标和模型。”

“如果不同计算任务重复扫描同一份数据。”

“如果高并发流量在某个时刻暴涨，而大量离线任务同时占用了计算资源。”

“如果企业既想让数据查询快，又想让资源成本可控。”

“我们就必须开始思考资源治理与成本工程。”

国王问：

“也就是说，下一场战争不是让系统更快？”

架构师回答：

“是让系统在满足性能、正确性和可用性的前提下，消耗更合理的资源。”

他在黑板上写下：

工程效率≠单纯追求最高吞吐量 \text{工程效率} \neq \text{单纯追求最高吞吐量}

“真正成熟的架构，还需要衡量单位请求成本、单位 TB 存储成本、计算资源利用率与业务收益。”

远方，一座巨大的调度中心缓缓升起。

无数计算任务正在争夺 CPU、内存、磁盘与网络。

一场关于成本与资源的战争，即将爆发。
