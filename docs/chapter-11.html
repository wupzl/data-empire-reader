第二幕：第一条资源法则——性能不是免费的

架构师带国王来到计算资源大厅。

这里排列着数千台服务器。

每台服务器都有 CPU、内存、磁盘和网卡。

国王问：

“资源不够，我们增加服务器。”

“现在资源太贵，我们减少服务器。”

“是不是就这么简单？”

架构师摇头。

“减少服务器可能导致延迟增加。”

“而增加服务器又可能产生资源浪费。”

“我们真正需要找到的是：在满足业务目标的条件下，合理分配资源。”

一、吞吐量与延迟

架构师画出一条曲线。

“陛下，假设某个服务随着请求量上升，吞吐量逐渐增加。”

“一开始，系统资源很充足。”

“新增请求可以得到及时处理。”

“但是随着某个瓶颈资源接近饱和，排队等待可能迅速增加。”

“此时，即使吞吐量没有显著提升，P99 也可能明显恶化。”

系统负载与响应时间：示意曲线

负载阶段 观察重点 可能表现
仍有余量 吞吐与延迟是否满足目标 延迟相对稳定
接近瓶颈 队列、连接等待、P99 等待时间可能快速上升
超过可持续容量 拒绝、超时、错误、积压 输入超过处理能力，系统失稳风险增加

这是定性示意，不给出通用利用率阈值。应通过阶梯压测确定实际拐点与容量余量。

二、Little's Law 再次登场

架构师拿出第一章的古老公式。

L=λW L=\lambda W

“陛下，还记得它吗？”

“系统内平均请求数等于长期平均吞吐率乘以平均停留时间。”

“假设系统稳定完成 2,000 QPS，平均请求停留 0.1 秒。”

L=2000×0.1=200 L=2000\times0.1=200

“系统内平均约有 200 个在途请求。”

“如果吞吐率不变，但平均停留时间增加到一秒：”

L=2000×1=2000 L=2000\times1=2000

“在稳态条件下，系统内平均在途请求数就变为 2,000。”

“但陛下，这里的 L 不是直接等于 Java 线程数。”

“因为请求可能处于排队、非阻塞 I/O 或其他等待状态。”

“同时，系统持续过载且队列不断增长时，不能随意用一个稳态公式预测无限增长过程。”

国王点头。

“所以请求变慢，本身也可能进一步加剧资源压力。”

“是的。”

第三幕：线程池——为什么更多士兵反而让王国更慢？

架构师带国王来到 Java 线程军团。

军团长拿出一份配置。

ThreadPoolExecutor executor =
    new ThreadPoolExecutor(
        32,
        256,
        60,
        TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(10000),
        new ThreadPoolExecutor.AbortPolicy()
    );

国王问：

“核心线程 32，最大线程 256，队列一万。”

“配置得不错吧？”

架构师说道：

“陛下，我们首先需要理解线程池的工作规则。”

一、ThreadPoolExecutor 的基本调度

对于上述配置，简化理解：

  1. 工作线程少于 corePoolSize 时，新任务通常可以创建核心线程。
  2. 核心线程达到配置数量后，优先尝试放入工作队列。
  3. 队列无法接收任务时，若线程数还未达到 maximumPoolSize，才尝试增加工作线程。
  4. 线程数和队列都达到限制后，执行拒绝策略。

“因此，在一个容量为一万的 LinkedBlockingQueue 尚未填满时，线程池可能长期只有 32 个核心工作线程，尽管 maximumPoolSize 设置了 256。”

国王大惊。

“也就是说，我设置了最大线程数 256，不代表高负载时会立即使用 256 个线程？”

“正是。”

二、大队列为何危险？

架构师继续解释：

“假设任务持续到来的速度高于线程池处理能力。”

“队列就会逐渐积压。”

“哪怕每个任务本身只需要几十毫秒，排队时间也可能增长到几秒甚至几十秒。”

“用户最终看到的是完整响应时间，而不是业务方法单独执行时间。”

三、拒绝策略

架构师展示常见策略。

策略 典型行为
AbortPolicy 抛出拒绝异常
CallerRunsPolicy 由提交任务的线程尝试执行任务
DiscardPolicy 丢弃被拒绝任务
DiscardOldestPolicy 尝试丢弃队列头部任务再提交

“陛下，选择拒绝策略必须结合业务语义。”

“不能让支付任务被静默丢弃。”

“而 CallerRunsPolicy 虽然可能对上游产生一定反压效果，但也可能阻塞 HTTP 请求线程或者消息消费线程。”

四、线程数应该如何估算？

国王问：

“那到底多少线程才合理？”

架构师说道：

“对于计算密集型任务，可以从可用 CPU 核数、任务计算比例和调度开销入手。”

“对于存在大量阻塞等待的任务，可能需要更多并发执行单元。”

“一条常见的粗略经验公式是：”

N≈NCPU(1+WC) N\approx N_{\text{CPU}} \left(1+\frac{W}{C}\right)

其中：

WW：任务等待时间。

CC：任务实际计算时间。

“但这只是特定假设下的容量估算启发式，不是可以无条件套用的定律。”

“最终还要考虑数据库连接池、外部服务限流和内存资源。”

五、Java 21 虚拟线程能解决吗？

国王突然想起来。

“我们可以使用 Virtual Thread！”

架构师点头。

“Java 21 虚拟线程可以显著降低大量阻塞式任务长期占用平台线程的成本，尤其适合大量等待型任务。”

“但虚拟线程不能把一台数据库的处理吞吐量变成无限大。”

“如果 MySQL 连接池只有 100 个连接，即使同时创建十万个虚拟线程，最终也仍然要面对连接池容量和下游吞吐约束。”

“对于 CPU 密集型任务，虚拟线程也不能创造额外 CPU 核心。”

线程池优化的目标不是让线程数量最大，而是让资源使用、任务排队和响应延迟保持可控。

第四幕：连接池之门——一千个线程争夺一百张通行证

夜幕降临。

MySQL 巨城入口出现了一条长队。

一千个 Java 工作线程同时等待数据库连接。

但城门只有一百张通行证。

国王问：

“为什么不将连接池直接增大到一千？”

数据库总督立即反对。

“陛下，每个数据库连接也会占用数据库资源。”

“更多连接不意味着更高的数据库吞吐。”

一、连接池的本质

“假设 HikariCP 最大连接数为 100。”

“那么应用实例最多通过这个连接池持有配置数量范围内的数据库连接。”

“请求借用连接时，如果可用连接不足，就可能等待。”

“等待超过配置时间，会出现连接获取超时。”

二、真正要监控什么？

架构师要求监控官记录：

  • 活跃连接数。
  • 空闲连接数。
  • 等待连接的线程数量。
  • 获取连接的等待时间。
  • 数据库事务执行时间。
  • 数据库 CPU、I/O、锁等待和慢查询。

“如果应用连接池长期满载，不一定代表应该扩容连接池。”

“可能是 SQL 慢。”

“可能是事务范围过大。”

“也可能是业务线程在持有连接期间等待第三方接口返回。”

三、长事务的危险

架构师找到一段代码。

@Transactional
public void createOrder(OrderRequest req) {
    orderRepository.save(buildOrder(req));

    paymentClient.requestPayment(req);

    notificationClient.sendMessage(req);
}

国王问：

“有什么问题？”

架构师回答：

“如果事务代理在这段方法里已经开启数据库事务，那么外部支付调用和通知调用可能被包含在事务生命周期内。”

“这会延长事务，甚至让数据库连接、锁等资源被不必要地持有。”

“因此，应该根据业务原子性边界，将外部调用与数据库事务合理拆分，利用 Outbox、异步任务或状态机处理跨系统流程。”

四、连接池容量不能只看单个实例

架构师又写了一行：

Java 实例数：100
每实例连接池上限：50
理论应用连接上限：5000

“陛下，如果数据库最多只适合承担远少于 5000 个活跃连接对应的实际负载，这个集群配置就需要重新考虑。”

“应用横向扩容时，数据库总连接上限也会随之上升。”

“这就是为什么必须进行端到端容量规划。”

第五幕：CPU 只有 30%，为什么 API 还是很慢？

第二天。

监控官带来一份奇怪的报告。

“陛下！某个服务的 CPU 使用率只有 30%。”

“但是 API P99 已经达到两秒。”

国王问：

“CPU 都没满，怎么可能成为性能问题？”

架构师说道：

“因为 CPU 使用率只是众多指标之一。”

一、CPU 低、请求慢的可能原因

第一种，等待数据库连接。

第二种，等待 MySQL 行锁。

第三种，等待网络 I/O。

第四种，等待外部 HTTP 服务。

第五种，线程池排队。

第六种，少数 CPU 核心局部热点或线程竞争。

第七种，频繁短暂停顿、内存分配或其他运行时问题。

“陛下，整体 CPU 30% 并不意味着每个 CPU 核心、每个工作线程和每个共享依赖都只有 30% 负载。”

二、CPU 利用率与吞吐量

架构师解释：

“如果 CPU 是主要瓶颈，增加 CPU 资源可能提高处理能力。”

“但如果请求主要在等待数据库，增加 CPU 往往帮助很小。”

“所以性能优化必须从实际瓶颈出发。”

三、四类资源瓶颈

CPU

计算密集、序列化、压缩、加密、GC、热点线程。

内存

Heap、直接内存、缓存、状态大小、OOM 与内存回收。

磁盘

吞吐量、随机 I/O、IOPS、延迟、队列与后台合并。

网络

带宽、RTT、丢包、连接数、重传与跨机数据交换。

架构师说道：

“例如 Spark Shuffle 很慢，可能并不是 CPU 算不过来，而是磁盘 Spill 和网络传输成为瓶颈。”

“Redis 延迟升高，也可能来自网络、慢命令、热点访问或服务器资源竞争。”

“要先定位，再优化。”

第六幕：实时军团与离线军团的资源争夺

Spring 王国的资源大厅里，两个军团爆发了一场争吵。

Flink 将军说：

“我的作业必须持续处理支付事件。”

“如果延迟超过五秒，直播大屏就会出现明显滞后。”

Spark 将军反驳：

“我的历史重算任务同样重要。”

“财务月底对账，必须完成全量计算。”

双方同时要求使用一批最昂贵的服务器。

国王十分头疼。

“难道不能让他们共享资源吗？”

架构师回答：

“可以，但必须考虑隔离和优先级。”

一、实时任务与离线任务的不同

Flink 实时作业通常长期运行。

它可能具有较严格的连续处理延迟和状态恢复要求。

Spark 离线作业通常有明确的计算批次。

一些任务可以延迟执行，也可能在不同时间段需要大量资源。

“所以我们可以根据业务 SLA，划分资源池。”

二、资源隔离

架构师提出：

实时资源池
    Flink 核心任务
    低延迟在线统计
    关键数据管道

离线资源池
    Spark 历史重算
    ETL 批处理
    模型特征加工

共享弹性资源池
    可延迟计算
    弹性扩容任务

“这不是说实时和离线永远不能共享机器。”

“而是共享时要有优先级、资源上限和抢占规则，避免一个低优先级任务破坏核心在线 SLA。”

三、为什么单纯提高资源利用率可能是错的？

国王问：

“如果我们让每台服务器 CPU 都达到 95%，是不是资源利用率就非常好了？”

架构师摇头。

“资源利用率高，不一定表示系统效率最优。”

“如果某个实时服务需要保留突发容量，而我们把空闲资源全部交给无法及时中断的离线任务，流量高峰到来时就可能没有足够的资源恢复余量。”

“因此，适当的冗余容量本身具有可用性价值。”

第七幕：Kubernetes 弹性军团——让服务器随流量增减

架构师带国王来到 Kubernetes 调度中心。

国王问：

“能不能让系统自动增加或者减少服务实例？”

“可以。”

“但我们要区分几种不同的扩容机制。”

一、HPA：扩缩 Pod 数量

HPA，Horizontal Pod Autoscaler。

它可以根据 CPU、内存或其他受支持的指标调整工作负载副本数量。

例如：

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  minReplicas: 4
  maxReplicas: 40
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60

架构师说道：

“这个示例表示基于 CPU 使用率目标调整副本数量。”

“注意，这里的 CPU 利用率百分比，通常是相对于容器配置的 CPU Request 来计算，而不是简单地按宿主机总 CPU 核数计算。”

“HPA 是周期性控制循环，不是请求一增加就瞬间完成扩容。”

二、KEDA：基于事件驱动指标扩容

国王问：

“如果 Kafka Lag 持续上涨，但 CPU 并不高呢？”

架构师答道：

“可以考虑 KEDA。”

“KEDA 能够利用支持的事件源指标，驱动 Kubernetes 工作负载扩缩容。”

“例如使用 Kafka 消费积压指标来决定某些消费者部署需要多少副本。”

“但这不意味着 Kafka Lag 高就一定该扩容。”

“如果瓶颈在下游 MySQL，增加消费者可能进一步扩大压力。”

三、节点扩容

“如果 HPA 把 Pod 副本数增加到 40，但 Kubernetes 集群没有足够的计算资源，新 Pod 可能无法调度。”

“这时，还需要节点级的容量管理机制。”

“某些环境会使用 Cluster Autoscaler、Karpenter 或云平台提供的其他节点自动供给方案。”

“但新增节点也需要时间。”

四、扩容速度也是一种资源

国王问：

“如果新节点需要一分钟才能准备好，而流量十秒内就冲上来了，怎么办？”

架构师回答：

“这就是为什么大促需要提前预热与容量准备。”

“自动扩缩容适合处理很多负载变化，但不能代替峰值容量规划。”

第八幕：PB 级存储——为什么有些数据应该离开昂贵的城堡？

三个月后。

数据仓库管理员走进皇宫。

“陛下，存储费用仍然很高。”

“可是我们已经优化压缩率了。”

管理员回答：

“问题不是只有压缩率。”

“我们把五年前的日志和昨天的日志放在同一种高性能存储中。”

“但五年前的日志可能几个月都没有人查询一次。”

架构师点头。

“这就是冷热分层的问题。”

一、热数据

热数据通常具有较高访问频率或低延迟要求。

例如：

  • 最近数日的实时交易统计。
  • 正在使用的业务缓存。
  • 高频 OLAP 聚合数据。

“它可能需要较高性能的存储和计算资源。”

二、温数据

温数据访问频率较低，但仍然需要合理的查询性能。

例如历史数月的交易明细、近期审计记录。

“可以根据具体工作负载选择更便宜的存储层或降低计算资源配置。”

三、冷数据

冷数据可能长时间不被访问。

例如多年前的历史日志。

“它可以采用更低成本的归档存储策略。”

“但这可能带来更长的数据恢复和读取时间，以及额外的取回费用。”

数据生命周期与分层存储

数据层 示例时间范围 访问方式
热数据 最近 7 天 低延迟查询、高频计算
温数据 第 8–90 天 常规分析、历史回溯
冷数据 超过 90 天 低频查询、归档恢复

时间范围仅为教学示例；分层应结合访问模式、留存要求、恢复目标和成本确定。

四、为什么不能随意删除历史数据？

国王问：

“既然冷数据很少访问，直接删除岂不是最便宜？”

架构师摇头。

“我们需要考虑法律与合规要求、交易审计、故障回溯、模型训练以及数据重算。”

“但也不能以‘以后可能有用’为理由无限期保存所有敏感数据。”

“必须制定明确的数据保留和删除策略。”

五、存储成本不仅是每 TB 的价格

架构师写下一份成本公式。

Cstorage=Ccapacity+Crequests+Cretrieval+Ctransfer+Coperations C_{\text{storage}} = C_{\text{capacity}} + C_{\text{requests}} + C_{\text{retrieval}} + C_{\text{transfer}} + C_{\text{operations}}

“冷存储容量单价可能更低，但数据恢复、读取、请求操作和跨区域传输也可能产生费用。”

“如果一份冷数据每天都被读取，所谓的便宜存储未必划算。”

第九幕：FinOps——每百万请求到底花多少钱？

国王终于召见财政大臣。

“我们现在知道应该如何节省服务器和存储成本。”

“可怎样衡量优化是否真的有效？”

架构师说道：

“我们需要建立单位成本模型。”

“这也是 FinOps 中的重要思想：将技术资源消耗与具体的业务价值联系起来。”

FinOps Foundation 的 Unit Economics 能力强调，通过每请求、每交易、每存储单位等指标，理解技术资源消耗与业务产出的关系。

一、每百万请求成本

假设某业务一个月的可归属基础设施成本为 100 万元。

这个月成功处理了 500 亿次 API 请求。

则：

Cmillion=100000050000000000×1000000 C_{\text{million}} = \frac{1000000}{50000000000}\times1000000

=20 元/百万请求 =20\text{ 元/百万请求}

“这意味着每百万次请求对应约 20 元的这部分基础设施成本。”

“但如果我们没有计入网络传输、数据库、缓存、可观测性以及共享资源费用，就不能称之为完整成本。”

二、每笔交易成本

“有些业务更适合观察每笔成功交易的成本。”

例如：

支付系统。

优惠券履约系统。

订单创建系统。

“因为单纯提高请求数量可能让每百万请求成本看起来下降，但并不意味着产生了更多真实业务价值。”

三、每 TB 计算成本

“对于 Spark 离线任务，可以记录处理数据规模、执行时长、CPU 时间、内存资源和云账单。”

“但每 TB 成本并不能单独衡量任务是否高效。”

“因为扫描一 TB 原始日志，与执行涉及大规模 Join 和排序的一 TB 分析任务，计算难度可能完全不同。”

四、单位成本的交互实验

单位请求成本模拟

国王问：

“如果成本下降了 40%，但 P99 从 200 毫秒变成 5 秒，这算优化成功吗？”

架构师回答：

“通常不能只凭成本数字宣布成功。”

“还必须检查业务规定的服务等级目标有没有被破坏。”

“成熟的成本治理，是在性能、可靠性、正确性与费用之间找到满足约束的方案。”

第十幕：压测法庭——如何发现系统的真正极限？

帝国财政危机逐渐缓解。

国王决定举办一次真正的全链路容量测试。

“架构师，这次我们不再只测试 QPS。”

“我要知道整个系统的承载极限。”

架构师拿出了五种测试。

一、基线测试

在正常负载下建立性能基线。

记录吞吐量、P50、P95、P99、错误率、资源利用率与单位成本。

二、阶梯加压

按照逐步增长的请求速率进行测试。

例如：

1000 QPS
    ↓
2000 QPS
    ↓
4000 QPS
    ↓
6000 QPS
    ↓
8000 QPS

“每个阶段都观察是否达到稳态，以及延迟和错误率是否恶化。”

三、突发流量测试

突然提升请求速率。

验证限流、排队、缓存、线程池以及弹性伸缩能否合理应对。

四、长时间稳定性测试

持续运行数小时甚至更长时间。

检查内存泄漏、连接泄漏、Kafka 积压、Flink Checkpoint、磁盘增长等问题。

五、故障注入测试

让部分服务实例不可用，验证系统是否仍能满足核心业务的降级或恢复目标。

“但陛下，故障演练需要严格隔离和控制影响范围，不能无防护地破坏真实生产数据。”

六、开放模型与封闭模型

架构师又提出一个更加深入的问题。

“如果压测工具只有一百个并发用户，每个用户都必须等前一个请求返回后，才发送下一次请求，会怎样？”

国王思考片刻。

“服务器变慢以后，每个用户发请求也会变慢。”

“是的。”

“这叫封闭负载模型的一种典型行为。”

“如果我们希望模拟外部请求按照固定速率到达，而不随着服务器延迟自动减少，就需要考虑开放负载模型。”

“不同负载模型会影响压测结果。”

“因此，报告高并发吞吐量时，必须说明压测工具、请求发送模型与响应时间统计方式。”

第十一幕：Java 工程实战——建立一套可控的高并发服务

经过一系列资源优化，架构师决定亲自改造订单服务。

原本的代码十分简单：

@PostMapping("/orders")
public Order create(@RequestBody OrderRequest req) {
    return orderService.create(req);
}

国王问：

“这有什么问题？代码很正常。”

架构师点头。

“代码本身没有必然问题。”

“但在高负载下，我们需要明确这条请求链路能够使用多少资源。”

一、数据库连接池必须有上限

例如配置 HikariCP：

spring:
  datasource:
    hikari:
      maximum-pool-size: 30
      minimum-idle: 10
      connection-timeout: 3000

“这是一组示例值，绝非所有 Java 项目的最佳配置。”

“应根据应用实例数量、数据库容量、事务执行时间和压测结果决定。”

二、异步任务不能无限排队

对于可异步执行的普通业务任务，可以设计有界线程池。

@Bean
public ThreadPoolTaskExecutor businessExecutor() {
    ThreadPoolTaskExecutor executor =
            new ThreadPoolTaskExecutor();

    executor.setCorePoolSize(16);
    executor.setMaxPoolSize(32);
    executor.setQueueCapacity(500);

    executor.setThreadNamePrefix("biz-");
    executor.setRejectedExecutionHandler(
        new ThreadPoolExecutor.AbortPolicy()
    );

    executor.initialize();
    return executor;
}

“但需要明确，这种线程池只适合与其业务语义匹配的任务。”

“如果任务必须保证在进程宕机后继续执行，仅提交到内存线程池并不够。”

“那类任务应考虑持久化、可靠消息和补偿机制。”

三、超时预算必须贯穿整个请求

假设 API 总延迟预算为 500ms。

架构师提出：

Gateway 与前置处理
          ↓
业务校验
          ↓
数据库事务
          ↓
响应序列化

“我们不能让每个下游调用都独立设置 5 秒超时，而整条 API 又要求 500ms 返回。”

“需要设计端到端 Deadline，并合理分配各阶段时间预算。”

“超时并不意味着底层操作一定被成功取消。”

“尤其涉及数据库提交和支付操作时，超时后必须明确结果可能未知，不能直接无条件重试非幂等操作。”

四、限流必须与容量相匹配

国王问：

“如果数据库只能处理每秒 3000 次写入，但 Gateway 每秒允许 10000 次创建订单，会怎样？”

架构师回答：

“请求仍然可能在连接池、线程池或数据库入口排队。”

“所以限流阈值要综合下游真实处理能力。”

“分布式限流还需要考虑全局限额与实例本地限额的关系。”

三个月后。

财政大臣再次来到皇宫。

这一次，他带来的账单明显变薄了。

对低负载时段的无状态 API 实例进行合理缩容。

优化 Kafka 数据保留策略。

为历史数据建立冷热分层。

改进 ClickHouse 批量写入与查询模型。

减少重复的预聚合计算。

同时保留关键系统的容量余量和故障恢复能力。

国王大喜。
