### 一、四个不能混淆的指标

| 指标 | 本章假设 | 含义 |
| --- | --- | --- |
| 日活跃用户 DAU | 1,000 万 | 一天内访问过平台的去重用户数 |
| 峰值在线连接 | 100 万 | 某时刻保持在线的用户或连接 |
| 峰值 API 吞吐 | 10 万/秒 | 需要实际处理的接口请求速率 |
| 业务事件吞吐 | 20 万/秒 | 点赞、评论、曝光、支付等事件总量 |

这些是不同统计口径，不能直接互换。数字均为本章虚构的系统设计假设，并非真实平台生产数据。

架构师解释：

“一个用户可以在直播间停留两小时。”

“期间 WebSocket 一直保持连接，但不代表他每秒都在发送 HTTP 请求。”

“同样，一个 HTTP 请求也可能产生多个内部事件。”

“我们不能拿 DAU 直接除以秒数，就得出真实的峰值 QPS。”

### 二、真正的容量估算

架构师在黑板上写下：

\[ \text{所需实例数} \approx \frac{\text{目标峰值吞吐}} {\text{单实例稳定吞吐}} \]

“假设某个无状态 API 服务经过压测，在满足既定 P99 和错误率目标时，每台实例能够稳定处理 2,000 QPS。”

“目标峰值是 100,000 QPS。”

那么理论最低实例数量：

\[ \frac{100000}{2000}=50 \]

“但是，陛下，50 台只是简化计算下的基础容量。”

“如果我们为单实例预留约 30% 的吞吐余量，把规划负载限制在压测稳定吞吐的 70% 左右：”

\[ N=\left\lceil\frac{100000}{2000\times0.7}\right\rceil=72 \]

“得到约 72 个实例。”

“这还没有单独计算可用区故障、实例启动时间、流量分布、依赖服务瓶颈和突发请求。”

“所以我们不能把 72 当作万能答案。”

## 第二幕：第一道城墙——Nginx 与网关的分工

帝国第一批服务器正式部署。

然而，架构师并没有让用户直接访问 Java 服务。

他先建立了一道入口防线。

“陛下，请允许我介绍 Nginx。”

“上一卷中，我们已经用它进行过负载均衡。”

“不错。”

“但在千万级系统中，我们必须进一步区分入口代理、业务网关和应用服务。”

### 一、为什么需要反向代理？

假设外部用户直接访问：

```text
10.0.0.11:8080
```

如果这台机器宕机，用户就无法正常访问。

而当后端服务器数量不断变化时，客户端也不应该自己维护全部服务器地址。

于是：

```text
客户端
  ↓
Nginx / 入口负载均衡
  ↓
Spring Boot 服务集群
```

Nginx 可以负责 TLS 终止、反向代理、流量分发和相关连接管理等工作，具体能力取决于配置与部署方式。

### 二、API Gateway 负责什么？

“陛下，入口反向代理之后，我们还可以引入 API Gateway。”

例如：

Spring Cloud Gateway。

它可以统一处理路由、认证前置校验、限流、请求追踪信息传播以及部分跨域策略。

但架构师强调：

“不要把全部业务逻辑都塞进 Gateway。”

“复杂的交易校验、库存扣减和支付状态转换，仍然应该归属于对应业务服务。”

“而且网关自身也需要多实例部署，否则它可能成为新的单点。”

### 三、服务发现与动态扩容

国王问：

“假设我们凌晨只有 20 台服务器，晚上活动要增加到 100 台，Nginx 怎样知道新增服务器？”

架构师回答：

“可以利用服务发现、容器编排或者动态上游配置机制。”

“例如，在 Kubernetes 中，可以通过 Service 与相关负载均衡机制向后端实例路由。”

“同时，还要根据实例就绪状态决定是否接收流量。”

“进程启动成功，不等于服务已经可以正常接收业务请求。”

“如果新实例尚未完成数据库连接、缓存预热或其他初始化，就把大量用户请求送进去，可能引发新的故障。”

## 第三幕：百万长连接——为什么十万 QPS 不等于百万线程？

天穹直播平台开始内测。

第一天，就有一百万名用户同时进入直播间。

监控官冲进王宫。

“陛下！系统需要维持一百万条长连接！”

“我们是不是需要一百万个 Java 线程？”

国王猛地站起来。

“那内存岂不是要爆炸？”

架构师摇头。

“陛下，一条长连接并不必然需要一个长期独占的线程。”

“这是事件驱动网络编程的重要意义。”

### 一、阻塞式线程模型的局限

考虑一个极简的阻塞式服务器。

```text
Socket socket = serverSocket.accept();

InputStream in = socket.getInputStream();

int data = in.read();
```

当线程执行阻塞读取时，如果没有数据到达，线程可能处于等待状态。

如果采用一个连接长期绑定一个平台线程的简单模型，连接数上升会造成大量线程资源占用。

“但现代高并发网络服务器通常不会如此直接地为每条连接永久分配一个线程。”

### 二、NIO 与事件循环

架构师带国王来到 Netty 军团。

“陛下，NIO 可以利用非阻塞通道、Selector 等机制管理多个连接。”

“一个事件循环线程可以关注许多 Channel 的 I/O 事件。”

当某条连接变为可读时，框架调用相应处理逻辑。

当某条连接暂时没有事件时，不需要为它一直占用一个专属执行线程。

### 事件驱动长连接模型

大量客户端连接

Netty EventLoop

监听 Channel 的读写与其他相关事件

连接 A

连接 B

连接 C

示意：实际 Netty 通常拥有多个 EventLoop 线程，并将 Channel 分配给相应 EventLoop。

国王问：

“这样就能随意管理一百万条连接？”

“仍然不能。”

“每条 TCP 连接都需要一定的内核和应用资源。”

“WebSocket 连接还会涉及协议状态、缓冲区、心跳、认证状态等开销。”

“文件描述符上限、内核参数、网络带宽、TLS 成本、连接分布和消息发送速率都需要评估。”

### 三、WebSocket 与 SSE 怎么选？

架构师拿出两份协议卷宗。

| 比较    | WebSocket       | SSE                  |
| ----- | --------------- | -------------------- |
| 通信方向  | 双向              | 服务器到客户端单向            |
| 典型用途  | 聊天、弹幕、实时互动      | 通知、状态更新、AI 流式输出      |
| 浏览器支持 | WebSocket API   | EventSource API      |
| 底层模型  | 建立 WebSocket 连接 | HTTP 响应持续推送          |
| 断线恢复  | 需要自行设计协议细节      | EventSource 支持自动重连机制 |

“如果直播间既需要用户持续发送弹幕，又需要服务器推送互动消息，WebSocket 通常比较自然。”

“如果只是把最新 GMV 或 AI 生成内容单向推送到客户端，SSE 也可能非常合适。”

“但无论哪种，都需要考虑心跳或保活策略、断线重连、消息序号和慢客户端处理。”

### 四、一百万连接到底需要多少内存？

架构师提出一个假设。

“如果我们粗略地假设，每个在线连接平均占用 20 KiB 的某类应用与连接管理资源。”

一百万连接：

\[ 1000000\times20\text{ KiB}\approx19.1\text{ GiB} \]

“这只是非常简化的容量示例。”

“真实内存还包括 JVM 堆、直接内存、Socket Buffer、TLS 状态和其他系统开销。”

“不同协议栈、内核配置和业务代码下，每连接内存占用可能差异很大。”

“所以连接密度必须通过压测测量，而不是完全依靠公式猜测。”

## 第四幕：消息广播战争——百万观众同时收到一条弹幕

直播系统正式开放。

某个超级主播拥有一百万名在线观众。

突然，一名用户发送了一条弹幕：

“今天的优惠券什么时候发？”

国王问：

“这条弹幕应该怎样送到一百万名观众面前？”

一名年轻工程师立刻回答：

“收到弹幕后，循环一百万次，依次调用用户的 WebSocket 连接！”

架构师的脸色变了。

“陛下，如果这样做，没有考虑广播任务分布、慢连接和网络出口压力，就可能让单个应用实例承担过多工作。”

### 一、不能把全部连接堆在一台机器上

假设一百万条 WebSocket 连接被分布在一百台接入服务器上。

平均每台管理一万条连接。

当某个直播间出现新弹幕时，可以将弹幕事件发布到房间消息分发层，再由持有相应连接的网关实例执行本地广播。

### 二、消息广播成本

架构师拿出一份新的计算。

“假设一条弹幕经过协议封装后，平均向每个观看用户发送 200 字节。”

“如果向一百万名观众各发送一份：”

\[ 1000000\times200=200000000\text{ B} \]

“约为 200 MB 的应用层消息数据，不计额外协议和网络开销。”

“如果这个直播间每秒有 100 条需要全员广播的弹幕呢？”

\[ 200\text{ MB}\times100=20\text{ GB/s} \]

国王脸色一变。

“每秒要发送二十 GB？”

“在这些假设下，是的。”

“而实际网络传输还会有额外开销。”

“这说明，用户可以发送 100 条弹幕，不代表系统应该把 100 条弹幕原样展示给所有在线观众。”

### 三、消息分级

架构师划分了三种消息。

强业务消息：支付状态、重要账户通知等，需要明确的可靠性与业务确认机制。

普通互动消息：弹幕、点赞、入场提示，可以按照产品要求采取批量、限频、采样、合并与优先级控制。

实时统计消息：例如在线人数、点赞总数和 GMV，可以定期推送最新快照，不必把每次计数变化都单独发送给所有用户。

“对于点赞数量，我们完全可以每隔一定时间汇总，再推送最新结果。”

“对于超级热门直播间的弹幕，还需要考虑展示节流、房间级限流及用户端承载能力。”

### 四、慢客户端问题

国王问：

“如果用户网络特别慢，服务器不停推送消息，会怎么样？”

架构师回答：

“如果无限制地往每条连接的发送队列中积累数据，就可能造成内存增长。”

“因此，要为连接设置可控的待发送数据上限。”

“对于可丢弃的互动类消息，可以考虑丢弃过期内容、合并快照或断开长期无法消费的连接。”

“对于必须可靠送达的业务通知，则应通过持久化通知记录、确认和补拉机制保证，不应该仅依赖 WebSocket 的一次发送。”

国王终于明白：

百万长连接的难点不仅是建立连接，更是如何以有限的资源持续、安全地管理消息流量。

## 第五幕：Redis 热点围城——缓存也会被击穿

凌晨一点。

商品服务突然发出警报。

一位超级主播正在介绍某件商品。

这一刻，上百万用户反复刷新商品详情。

大量请求指向同一个 Key：

```text
product:detail:1001
```

国王大笑。

“我们有 Redis！这种场景正适合缓存！”

架构师却并不乐观。

“陛下，Redis 可以减少数据库查询压力。”

“但高热点 Key 仍然需要考虑 Redis 节点负载、网络吞吐和缓存失效。”

### 一、缓存穿透

国王问：

“什么是缓存穿透？”

架构师讲起一个故事。

一群恶意访客不断查询根本不存在的商品：

```text
product:999999999
product:888888888
product:777777777
```

Redis 查不到。

MySQL 也查不到。

如果每个请求都继续查询数据库，大量不存在的数据请求就可能绕过缓存。

“这就是缓存穿透。”

常见防线包括合法性校验、缓存空值、布隆过滤器和限流。

### 二、缓存击穿

另一种情况：

一个超级热点商品一直存在 Redis 中。

突然，其缓存 TTL 到期。

数万请求同时发现缓存不存在。

于是，全部尝试查询 MySQL。

“这就是典型热点 Key 失效导致的缓存击穿。”

架构师写下：

```text
大量请求
    ↓
Redis 热点 Key 失效
    ↓
多个请求同时回源
    ↓
MySQL 压力急剧上升
```

可考虑单飞加载、短期重建锁、逻辑过期或预热等策略，但必须明确过期数据能否被业务接受。

### 三、缓存雪崩

“陛下，假设十万个商品缓存被统一设置了相同 TTL。”

“它们在同一时刻大规模失效。”

“这就可能引发缓存雪崩。”

“我们可以根据访问分布、缓存热度等设计过期策略，也可以在合适的 TTL 基础上加入随机抖动。”

“但更重要的是回源限流与降级保护。”

### 四、缓存一致性

国王问：

“如果 MySQL 中商品价格改了，Redis 还是旧价格怎么办？”

架构师回答：

“这就是缓存一致性问题。”

“常见 Cache-Aside 策略是在更新数据库事务成功后删除或失效相应缓存。”

“但仍需考虑并发读写、缓存回填竞态、删除失败和消息传播延迟。”

“另外，支付、订单结算时的价格与库存，不应无条件相信一个可能过期的商品展示缓存。”

“展示性能与交易正确性，应分别设计。”

## 第六幕：RabbitMQ 与 Kafka——两支消息军团如何分工？

国王突然提出疑问。

“我们现在既有 RabbitMQ，又有 Kafka。”

“它们不都是消息系统吗？”

“为什么不只保留一个？”

架构师回答：

“当然可以评估合并，但必须看业务需求。”

“它们不是简单的谁先进、谁落后。”

### 一、RabbitMQ：业务异步履约

例如：

优惠券领取成功后，进入异步履约。

订单提交后，触发后续处理。

某项业务任务失败后，需要有明确的重试和死信治理。

“RabbitMQ 在很多业务任务分发场景中十分合适。”

### 二、Kafka：事件流与数据管道

例如：

支付成功事件需要被多个独立系统订阅。

用户行为事件需要保留一段时间，供风控和分析消费。

Flink 需要在故障恢复时重放仍被保留的事件。

“Kafka 的分区日志、保留策略和独立消费组适合许多此类场景。”

Kafka 的分区日志和消费组模型，使同一个 Topic 可以被不同的逻辑订阅者独立读取。




### 三、不要机械地两个都上

国王问：

“那是不是所有大型项目都需要同时使用 RabbitMQ 和 Kafka？”

“不一定。”

“如果只有少量异步任务，RabbitMQ 可能足够。”

“如果已经有 Kafka，并且业务能够接受其消费、重试和故障治理方式，也可能统一在 Kafka 上。”

“引入两套消息基础设施意味着两套监控、容量管理、故障处理和运维成本。”

“技术选择必须服务于业务，而不是为了凑齐技术栈。”

## 第七幕：秒杀战争——十万请求争夺一万张优惠券

下午六点。

天穹直播平台准备发放一万张优惠券。

活动开始的一瞬间：

十万 QPS 到来。

国王问：

“这一场战争，我们已经在第二章打过了。”

架构师点头。

“是的，但这一次，我们要把它放进真实的大系统中。”

### 一、完整领取链路

```text
用户点击领取
      ↓
API Gateway
      ↓
身份校验、活动校验、限流
      ↓
Redis Lua
      ├─ 已领取 → 返回
      ├─ 库存不足 → 返回
      └─ 预占成功
              ↓
可靠记录履约任务
              ↓
消息队列
              ↓
Consumer
              ↓
MySQL 创建领取记录
              ↓
更新最终状态
              ↓
用户查询领取结果
```

架构师说道：

“这里有几个必须说清楚的工程问题。”

### 二、预占成功不等于最终领取成功

“Redis 返回预占成功，只能说明入口阶段的资格校验和预占操作完成。”

“如果数据库履约尚未完成，接口不应该直接声称优惠券已经最终发放成功。”

“可以返回一个请求编号和处理中状态。”

例如：

```text
{
  "requestId": "claim_9527",
  "status": "PROCESSING"
}
```

前端通过查询或事件通知获取最终状态。

### 三、Redis 与消息队列之间的可靠性

国王问：

“如果 Redis 已经扣减库存，但服务在消息发送前崩溃呢？”

架构师回答：

“这正是跨系统一致性的难点。”

“不能仅凭一段 Lua 脚本，就声称整个流程不会丢任务。”

“要么设计可靠、可恢复的预占任务记录与补偿机制，要么重新调整事务边界，例如使用数据库 Outbox。”

“最终方案取决于活动吞吐、允许的延迟、故障恢复要求与数据库写入容量。”

### 四、最终防线：数据库约束

架构师在 MySQL 中建立业务唯一约束。

```sql
CREATE TABLE coupon_claim (
    id BIGINT PRIMARY KEY,
    request_id VARCHAR(64) NOT NULL,
    user_id BIGINT NOT NULL,
    coupon_id BIGINT NOT NULL,
    status VARCHAR(32) NOT NULL,

    UNIQUE KEY uk_request (request_id),
    UNIQUE KEY uk_user_coupon (user_id, coupon_id)
);
```

“这样可以防止同一个领取请求重复创建，也能约束一人一券的业务规则。”

“不过，如果允许每个用户领取多张，约束就需要按照真实业务重新设计。”

“而数据库唯一索引也不能单独保证活动总库存不超额，还需要库存不变量的整体设计。”

## 第八幕：实时数据大脑——Flink 如何计算直播成交额？

优惠券战争结束后，订单开始大量产生。

支付服务持续收到可信支付结果。

这一次，架构师不再让 ClickHouse 或 MySQL 不断重新扫描全部订单。

他建立了一条数据管道。

## 交易与实时分析的双链路

### 一、为什么不能把交易正确性交给实时看板？

国王问：

“Flink 已经统计了成交额，为什么还需要 MySQL 交易库？”

架构师回答：

“因为两者的职责不同。”

“MySQL 保存订单和支付状态等权威业务事实。”

“Flink 处理事件，构建派生统计结果。”

“Redis 和 ClickHouse 中的 GMV 可以因异步处理而存在短暂延迟。”

“但这不应影响支付是否成功的最终判断。”

### 二、事件去重

架构师强调：

“消息系统可能重复投递。”

“同一支付事实如果出现重复事件，Flink 不应该简单地重复增加金额。”

“可以根据具有明确语义的支付事件 ID、订单状态版本等信息设计去重。”

“而且去重状态需要考虑生命周期。”

“如果 TTL 太短，较晚到达的重复事件可能绕过去重。”

### 三、退款和订单撤销

国王突然想到：

“如果用户支付 100 元，后来退款 100 元怎么办？”

架构师回答：

“首先要定义指标。”

“GMV、实付金额、净收入和退款后净额，不一定是同一个指标。”

“如果要统计净支付额，就需要正确处理退款事件。”

例如：

```text
支付成功：+100
退款成功：-100
净支付额：0
```

“但如果一笔订单部分退款两次，需要区分不同退款事件，防止重复扣减。”

“指标口径不明确，即使计算完全没有 Bug，报表也可能与财务对不上。”

## 第九幕：高可用战争——如果整个可用区突然失联？

大促进行到一半。

突然，数据中心某一片区域发生网络故障。

大量应用实例无法继续响应。

国王震惊。

“我们有一百台服务器！为什么还会受到这么严重的影响？”

架构师回答：

“陛下，如果这一百台都部署在同一个故障域，那么它们并不一定构成足够可靠的系统。”

### 一、多可用区部署

架构师拿出地图。

“我们可以将合适的业务服务分布到多个可用区。”

```text
           入口负载均衡
                ↓
     ┌──────────┴──────────┐
     ↓                     ↓
可用区 A                可用区 B
Java 实例集群           Java 实例集群
缓存/消息节点           缓存/消息节点
     └──────────┬──────────┘
                ↓
     具备故障恢复能力的数据层
```

“但必须注意，应用跨区部署不意味着数据库自动具备同等级别的容灾能力。”

“Redis、Kafka、MySQL 等有状态服务需要分别设计副本放置、故障切换与数据一致性。”

### 二、RTO 与 RPO

国王问：

“我们怎样衡量容灾能力？”

架构师写下两个指标。

RTO（Recovery Time Objective）：业务恢复时间目标。

RPO（Recovery Point Objective）：可接受的数据恢复点目标，通常体现为最多能够容忍多长时间的数据损失。

“例如，RTO 为 5 分钟，不意味着系统必然在 5 分钟恢复，而是要求架构与演练达到这个目标。”

“RPO 为 0 也不是随便增加两个异步副本就能保证的。”

### 三、限流、熔断与降级

当某个依赖服务出现故障，架构师下令：

“保护交易主链路！”

推荐服务暂时降级。

部分非关键统计更新允许延迟。

弹幕展示进行限频。

但支付、库存、订单状态等核心业务依然按照严格规则执行。

“陛下，降级不意味着可以牺牲交易正确性。”

“对于资金类操作，宁愿明确失败或者进入可追踪的待处理状态，也不能凭空宣称成功。”

### 四、自动扩容并不是瞬间完成

国王问：

“Kubernetes HPA 不是能够自动扩容吗？”

架构师回答：

“是的，但 HPA 通过周期性控制循环，根据资源或业务指标调整工作负载副本数量。”

“从发现负载变化，到新实例启动、预热、就绪、实际承接流量，需要一定过程。”

“对于已知的大促，往往还需要提前容量规划与预扩容，而不是全部依赖流量到来后的自动伸缩。”&#x20;




## 第十幕：可观测性——为什么系统没有报警，却已经影响用户？

大促结束前，国王看到监控大屏全部显示绿色。

CPU 正常。

内存正常。

服务器没有宕机。

国王满意地说道：

“系统运行得很好。”

但一名用户投诉：

“我领取优惠券以后，页面显示处理中，等了三分钟也没结果。”

架构师立即说道：

“陛下，服务器健康不代表业务健康。”

“我们需要完整的可观测性体系。”

### 一、Metrics：指标

指标帮助回答：

“问题影响有多大？”

例如：

- API QPS、错误率、P95、P99。
- JVM Heap 使用率与 GC 停顿。
- Tomcat 活跃线程与数据库连接池使用情况。
- Redis 请求延迟与缓存命中率。
- RabbitMQ 队列深度和消息等待时间。
- Kafka Consumer Lag。
- Flink 背压、Checkpoint 耗时和 Watermark 进度。

### 二、Logs：日志

日志帮助回答：

“发生了什么？”

例如：

```text
requestId=abc123
orderId=9527
couponId=1001
status=FULFILLMENT_RETRY
reason=DB_TIMEOUT
```

架构师强调：

“结构化日志要便于关联，但不应该随意记录密码、Token 或敏感个人信息。”

### 三、Tracing：分布式追踪

一条用户请求可能跨越多个服务。

```text
Gateway
   ↓
CouponService
   ↓
Redis Lua
   ↓
RabbitMQ
   ↓
FulfillmentConsumer
   ↓
MySQL
```

“如果使用分布式追踪，我们可以把请求路径中的多个 Span 关联起来。”

“异步消息跨越生产者和消费者时，需要正确传播 Trace Context，并合理使用上下文关联关系。”

“但不是说每一条高吞吐事件都必须以相同采样率保存完整 Trace。”

“否则观测系统本身也可能承受巨大成本。”

### 四、SLO：从机器指标转向用户体验

架构师写下：

> 99.9% 的关键 API 请求在指定统计周期内满足成功与延迟目标。

“这是一种示意性的服务等级目标。”

“真实系统需要明确什么算成功、统计窗口多长、是否排除某些请求，以及延迟门槛是多少。”

“例如支付请求返回 200，并不一定表示支付最终成功；业务指标必须对应真实用户结果。”

### 五、事故复盘

国王问：

“每次故障都要写报告吗？”

架构师回答：

“重要事故应该留下可执行的复盘结果。”

“包括时间线、影响范围、直接原因、深层原因、有效与无效的处置措施，以及后续需要验证的改进项。”

“不能只写一句‘服务器压力过大，已经扩容’就结束。”

## 第十一幕：四十分钟的系统设计面试

数周后。

帝国举行首席工程师考核。

主考官向年轻工程师提出一道题：

“Nginx、Redis、RabbitMQ、Kafka、Flink、ClickHouse、MySQL、Kubernetes……”

考官打断了他。

年轻工程师答不上来。

首席架构师走到他面前。

“系统设计考察的不是组件名称的数量。”

“而是你能否从需求推导出架构，再说明关键权衡。”

### 一场面试，应该怎样分配时间？

### 40 分钟系统设计作答节奏

| 时间 | 阶段 | 需要讲清楚的内容 |

## 第十二幕：最终验收——一次针对整个帝国的故障演练

天穹直播平台上线前最后一天。

国王下令进行完整压测。

这一次，架构师没有只检查 QPS。

他准备了四场战争。

### 第一场：峰值流量

模拟高峰期的 API 请求、长连接建立、商品查询与交易写入。

记录不同负载下的吞吐量、P99 和错误率。

同时观察数据库和缓存是否存在共享瓶颈。

### 第二场：单实例故障

随机停止若干无状态应用实例。

检查请求是否能够切换至其他健康实例。

对于长连接服务，还要验证客户端重连、房间重新订阅和消息补拉。

### 第三场：消息积压

人为降低消费者处理速率。

观察 RabbitMQ 与 Kafka 的积压增长、限流策略和恢复速度。

确保没有无界队列吞噬内存，也没有无限重试导致故障扩大。

### 第四场：数据库与状态恢复

模拟数据库主节点不可用、Flink Task 故障和 Sink 写入异常。

验证交易状态正确性、Checkpoint 恢复、事件重复处理以及最终对账结果。

架构师告诉国王：

“压测时，必须避免真实付款、真实通知和其他不可逆业务副作用。”

“故障演练应在隔离环境或具备严格防护的受控范围内进行。”

最终，帝国得到了一份容量和故障报告。

## 尾声：一场新的战争——当数据变得无法信任

三个月后。

天穹直播平台已经成为数据大陆最大的商业系统之一。

每日产生数十亿条用户行为事件。

Kafka 的事件长河不断流淌。

Flink 持续计算实时指标。

ClickHouse 保存交易与行为的分析结果。

MySQL 维护在线交易。

HDFS 和其他存储系统保存海量历史数据。

国王 Java 原以为，帝国已经征服了高并发与大数据。

直到某天清晨。

财政大臣带来两份报表。

第一份来自 MySQL。

昨日实付金额：

8.20 亿元。

第二份来自实时分析系统。

昨日实付金额：

8.47 亿元。

国王脸色一变。

“相差两千七百万？”

“是的，陛下。”

“Kafka 没有明显积压。”

“Flink Checkpoint 正常。”

“ClickHouse 查询很快。”

“所有服务器看起来都很健康。”

“可数据，就是对不上。”

架构师接过报表。

他看到了几条可疑的支付事件。

同一笔支付，被重复发送了两次。

另一些退款事件延迟了几个小时才到达。

部分订单状态发生过变更。

而不同报表对“成交金额”的定义也不完全一致。

架构师沉默了片刻。

随后，他在黑板上写下了一句话：

> 系统跑得快，只说明计算效率；结果算得对，才说明数据可信。

“如何避免重复数据和脏数据？”

国王望向地图的最后一片未知区域。
