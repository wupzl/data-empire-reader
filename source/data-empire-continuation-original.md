## 第二幕：第一场审判——指标究竟是什么？

首席架构师将财政官、交易官、运营官全部召集到大厅。

他在黑板上写下：

GMV、支付金额、退款金额、净支付金额。

“今天，我们先不讨论 Flink，不讨论 Spark，也不讨论 Kafka。”

“先把指标定义清楚。”

### 一、GMV 与实付金额不是天然同义词

架构师解释：

“GMV 常用来描述一定业务范围内的交易总额，但不同企业可能采用不同定义。”

“有的使用下单金额，有的使用支付成功金额，有的对取消、退款及优惠的处理不同。”

“因此，我们不能仅凭 GMV 这个名字，就断定一条 SQL 一定正确。”

国王点头。

“那应该怎么办？”

“建立指标契约。”

例如，帝国决定定义一项指标：

### 指标契约：成功支付金额

| 指标编码 | `paid_amount`     |
| ---- | ----------------- |
| 统计对象 | 成功支付事实            |
| 时间维度 | 业务支付成功时间          |
| 金额单位 | 人民币分              |
| 去重标识 | 唯一支付业务事件标识        |
| 退款处理 | 不从该指标中直接扣减，另设退款指标 |
| 统计时区 | Asia/Shanghai     |
| 数据修正 | 允许迟到事件修正与重算       |

这是本章设计的示例业务定义，不代表所有企业的财务或 GMV 口径。

架构师继续说道：

“如果要计算退款后净支付额，可以定义另一个指标。”

\\[ \text{净支付额}=\text{成功支付额}-\text{成功退款额} \\]

“但退款按退款发生日期归属，还是回溯冲减原支付日期，必须另外明确。”

“这两个口径可能产生不同的每日趋势，即使长期总额一样。”

### 二、为什么金额最好使用整数分？

一名工程师问：

“我们直接用 double 保存金额，不行吗？”

架构师回答：

“Java 的 double 基于二进制浮点数，不能精确表示所有十进制小数。”

例如：

```
System.out.println(0.1 + 0.2);
```

可能得到：

```
0.30000000000000004
```

“因此，对于精确金额运算，可以采用整数最小货币单位，或在 Java 中使用 BigDecimal，并明确精度与舍入规则。”

“在数仓中，金额字段也需要使用适当的整数或定点数类型，避免反复浮点累加造成误差。”

### 三、为什么要先定义指标，再建数据仓库？

国王问：

“是不是先把所有数据都搬进仓库，再慢慢研究指标？”

架构师摇头。

“原始数据当然可以先保留。”

“但如果业务要依赖这些指标做经营决策，就应该先明确统计契约。”

“否则，后续每一层都会复制和传播错误理解。”

这时，架构师在地图上标出一座巨大的新城。

城门刻着四个字母：

ODS、DWD、DWS、ADS。

## 第三幕：四层数据仓库——从原始卷宗到帝国报告

数据仓库之城位于数据大陆中央。

它不是一间巨大的仓库。

而是一套组织数据、加工数据、统一语义和服务分析需求的体系。

架构师带国王走进第一层。

### 一、ODS：原始数据的接待大厅

“ODS，Operational Data Store。”

“在我们采用的分层规范里，它主要承担原始业务数据的接入和留存。”

“例如订单表、支付表、退款表、用户表，以及 Kafka 事件。”

国王问：

“为什么不直接在 ODS 里把所有错误数据都清洗掉？”

架构师回答：

“因为原始数据本身具有审计和追溯价值。”

“如果过早丢弃信息，后来发现处理逻辑有误，就可能无法重新构建正确结果。”

ODS 中可能记录：

```
order_id
payment_id
payment_status
amount_cent
source_updated_at
ingest_time
source_operation
source_position
```

“其中源变更位置、采集时间和操作类型，可以帮助我们理解数据从哪里来、何时被采集，以及是否发生过更新或删除。”

“当然，保留原始数据也必须符合隐私、权限和数据生命周期要求。”

### 二、DWD：清洗后的明细事实

架构师带国王进入第二层。

这里的档案官正在做四件事。

第一，规范字段和类型。

第二，识别重复数据。

第三，处理业务事件语义。

第四，将原始记录转换为具有明确粒度的事实数据。

“DWD 通常称为 Data Warehouse Detail。”

“它不是简单复制一遍 ODS。”

“我们要在这里确定事实粒度和关键业务规则。”

例如支付事实表：

```
dwd_payment_success

payment_id
order_id
user_id
room_id
paid_amount_cent
paid_at
payment_channel
```

“每一行到底表示一笔支付成功事实，还是一次支付状态变更事件，需要从一开始就定义清楚。”

“否则在 DWS 做 SUM 时，很容易重复计算。”

### 三、DWS：汇总与公共指标

接下来是第三层。

DWS，Data Warehouse Summary 或 Service 等命名在不同企业中存在差异，这里采用汇总服务层的含义。

“陛下，DWD 保存明细事实，而 DWS 负责把重复使用的汇总逻辑沉淀下来。”

例如：

```
dws_room_payment_1d

stat_date
room_id
paid_amount_cent
payment_count
paying_user_count
```

“这里统计某直播间每天的成功支付金额、支付次数与去重支付用户数。”

“但要注意，支付金额可以直接加总，而跨天的独立支付用户数不一定能直接相加。”

“因为同一个用户可能连续两天支付。”

### 四、ADS：面向业务的应用报表

最后，架构师打开了第四层大门。

ADS，Application Data Service。

这里的结果直接服务运营、财务、BI 看板和业务决策。

例如：

```
ads_live_room_rank_today

rank
room_id
room_name
paid_amount_cent
conversion_rate
```

“这一层更接近具体业务需求。”

“直播排行榜、经营驾驶舱、活动复盘，都可以构建相应的数据应用结果。”

## 数据仓库四层体系

### ODS

原始接入层

业务数据、变更日志、原始事件

### DWD

明细事实层

清洗、去重、标准化、明确粒度

### DWS

公共汇总层

按主题汇总，沉淀共享指标

### ADS

应用服务层

报表、看板、经营分析与业务接口

ODS/DWD/DWS/ADS 是常见的数仓分层约定，而不是所有数仓产品强制采用的唯一标准。不同组织还可能引入 DIM、STG、DM 等层。

国王凝视着这座四层城市。

“我明白了。”

“原始数据进入 ODS。”

“DWD 将数据整理成可信的业务明细。”

“DWS 计算共享的汇总结果。”

“ADS 为具体应用提供数据。”

架构师点头。

“这是很好的入门理解。”

“但不能认为数据经过四层就天然正确。”

“每一层都必须有明确的输入、输出、质量检查与责任人。”

## 第四幕：事实表与维度表——帝国必须知道每一笔交易发生了什么

当国王走进 DWD 大厅时，发现档案官正在争吵。

一个人说：

“订单表应该包含用户名！”

另一个人说：

“还应该包含用户城市、商品类别、主播等级！”

第三个人说：

“干脆把所有字段都放到一张表里！”

架构师摇了摇头。

“诸位，我们需要先分清事实与维度。”

### 一、事实表：记录发生的业务

假设用户张三在直播间购买了一件商品。

支付 199 元。

这是一件业务事实。

我们可以记录：

```
payment_id = 50001
order_id = 10001
user_id = 20001
product_id = 30001
room_id = 40001
amount_cent = 19900
paid_at = 2027-01-01 20:05:00
```

“事实表通常记录业务过程中的事件、度量或状态。”

“例如支付成功事实、订单明细事实、商品曝光事实。”

### 二、维度表：描述事实发生的背景

国王问：

“那么用户所在城市、商品分类、主播等级呢？”

架构师回答：

“这些可以属于维度属性。”

例如：

```
dim_user
  user_id
  region
  register_channel

dim_product
  product_id
  category
  brand

dim_room
  room_id
  anchor_id
  room_category
```

“维度使我们能够回答‘按什么角度分析’。”

“事实则告诉我们‘发生了什么、产生了多少’。”

### 三、粒度 Grain：决定一行代表什么

架构师在黑板上写下一个词。

Grain，事实粒度。

“陛下，设计事实表的第一步，不应该是选字段。”

“而是明确一行代表什么。”

假设一个订单购买了三件商品：

| 订单   | 商品 | 金额  |
| ---- | -- | --- |
| 1001 | A  | ¥50 |
| 1001 | B  | ¥30 |
| 1001 | C  | ¥20 |

如果事实表采用订单商品行粒度，那么这三行代表三条订单明细。

但如果再把一张订单级优惠记录直接 Join 到三条明细，可能造成优惠金额被重复加总。

国王猛然站起。

“这不是又算出假数据了吗？”

“正是。”

“多表 Join 时，如果两边粒度不匹配，可能产生行数膨胀。”

“在统计之前，要确认连接关系是一对一、一对多还是多对多。”

### 四、星型模型与雪花模型

### 星型模型：事实表位于中心

逻辑模型示意。维度表可能使用代理键，事实表中的具体键设计需与维度版本策略配套。

“星型模型通常把事实表放在中心，周围直接连接维度表。”

“雪花模型则进一步将部分维度规范化，形成更复杂的维度关联结构。”

星型模型往往更容易理解和查询，但可能存在维度属性冗余；雪花模型可能减少某些冗余，却增加 Join 和查询复杂性。

## 第五幕：时光档案——用户换了城市，历史报表应该改变吗？

国王以为事实表与维度表已经解决问题。

然而，历史档案管理员拿出一个案例。

“陛下，张三去年住在北京，今年搬到了上海。”

“如果我们分析去年不同城市的消费额，这笔订单应该算到北京还是上海？”

国王脱口而出：

“当然是北京！”

管理员问：

“可是 dim_user 里的城市已经更新成上海了。”

国王皱眉。

“那历史数据岂不是改变了？”

架构师回答：

“您终于遇到了 SCD。”

SCD：Slowly Changing Dimension，缓慢变化维度。

### 一、Type 1：直接覆盖历史

旧记录：

```
user_id = 1001
city = 北京
```

用户搬家后：

```
user_id = 1001
city = 上海
```

“这种策略保留最新属性，历史属性被覆盖。”

“它适合不需要保留历史版本，或者需要纠正错误属性的场景。”

### 二、Type 2：增加历史版本

“如果需要保留用户所属城市的历史，我们可以新建维度版本。”

| 代理键 | 用户 ID | 城市 | 生效时间       | 失效时间       |
| --- | ----- | -- | ---------- | ---------- |
| 501 | 1001  | 北京 | 2025-01-01 | 2026-06-01 |
| 782 | 1001  | 上海 | 2026-06-01 | 9999-12-31 |

“当事实发生在 2025 年，就可以关联当时生效的北京版本。”

“当事实发生在 2027 年，就可以关联上海版本。”

“其中代理键用于区分同一业务用户的不同历史版本。”

这就是 SCD Type 2 的核心思想：变化时增加新行，而不是覆盖旧行。

## 第六幕：CDC 信使——MySQL 的每一次变化，如何传到数据仓库？

这一天，Kafka 将军来到皇宫。

“陛下，我们需要把 MySQL 的支付事实同步到数据仓库。”

国王说道：

“很简单，每隔一分钟执行一次 SQL。”

```
SELECT *
FROM payment
WHERE updated_at > :last_sync_time;
```

架构师没有立刻否定。

“这种增量轮询，在一些简单场景下确实能使用。”

“但它存在几个常见难点。”

“如果一条记录删除了，怎么发现？”

“如果更新时间精度不足，边界上的多条记录怎么处理？”

“如果事务还没提交，或者数据的更新顺序与时间字段不一致，怎么办？”

“如果数据库每次都要扫描大量记录，又该如何控制压力？”

国王问：

“还有更好的方式吗？”

“可以考虑 CDC。”

### 一、CDC：Change Data Capture

CDC 是变更数据捕获。

“它不是反复读取整个表，而是捕获数据源中发生的插入、更新和删除等变更。”

在常见的 MySQL 日志式 CDC 中，可以利用 Binlog 等机制获取数据库变更。

```
MySQL
  ↓
Binlog
  ↓
CDC Connector
  ↓
Kafka
  ↓
Flink / Spark / 数仓
```

### 二、为什么需要快照加增量？

国王问：

“如果一张表已经有十亿条历史记录，CDC 开始运行后，难道只能拿到新变化？”

架构师回答：

“我们通常还需要初始化已有数据。”

“一类典型方案是先读取历史快照，并在过程中协调捕获后续增量变化。”

“这样能够构建初始表状态，再继续消费持续发生的更新。”

“但快照与增量之间如何衔接，必须由连接器的具体一致性机制保证。”

“不能随便先执行 `SELECT *`，再去读取当前 Binlog，否则两者之间可能出现数据缺口或重复。”

### 三、删除事件与撤回语义

架构师展示：

```
INSERT：新增支付记录
UPDATE：支付状态改变
DELETE：删除一条业务记录
```

“下游必须理解这些消息代表的是数据库行变化，还是已经解释好的业务事件。”

“比如支付表从 `UNPAID` 更新为 `PAID`，不代表每次更新这行记录都应该新增一次成交金额。”

“订单状态后续改变、补充备注，也不能再次加钱。”

### 四、CDC 与 Outbox 的区别

国王问：

“那我们之前设计的 Outbox，是不是没必要了？”

架构师回答：

“不是。”

“CDC 说明如何捕获数据变化。”

“Outbox 说明如何在业务数据库事务中可靠记录待发布的业务事件。”

## 第七幕：ETL 与 ELT——先加工再入库，还是先入库再加工？

数据仓库已经建成。

但帝国工程师分成了两个派系。

一个派系主张：

“数据必须先清洗，再进入分析仓库！”

另一个派系反驳：

“应该先保存数据，再利用数仓的计算能力进行转换！”

国王被吵得头疼。

架构师说道：

“这就是 ETL 与 ELT 的区别。”

### ETL

Extract → Transform → Load。

抽取、转换、加载。

“数据从源系统抽取后，先经过转换处理，再加载到目标分析系统。”

### ELT

Extract → Load → Transform。

抽取、加载、转换。

“数据先进入具备存储与计算能力的目标平台，再在平台内部完成转换。”

| 对比     | ETL                  | ELT            |
| ------ | -------------------- | -------------- |
| 转换位置   | 通常在加载目标系统之前          | 通常在目标数据平台内部    |
| 原始数据保留 | 取决于架构设计              | 常结合原始数据留存      |
| 常见实践   | 外部数据集成和预处理           | 云数仓、湖仓内 SQL 转换 |
| 选择依据   | 数据安全、处理能力、成本、时延、治理要求 | 同左             |

“陛下，不要把 ETL 理解成旧技术、ELT 理解成必然先进的技术。”

“它们是不同的数据处理安排。”

“有些敏感数据在进入目标平台前，就需要完成脱敏和校验；有些大规模转换更适合利用目标平台的分布式计算能力。”

### 一、怎么进行对账？

架构师制定了三层对账方案。

第一层：数量对账。

源系统有多少笔支付成功事实？

DWD 有多少笔去重后的支付事实？

不同阶段数量差异来自哪里？

第二层：金额对账。

按统一统计口径、时间范围、币种和金额单位，比较源数据与派生结果。

第三层：明细差异定位。

如果汇总金额不一致，进一步根据支付 ID 找到缺失、重复或金额不一致的记录。

示意 SQL：

```
SELECT
    payment_id,
    COUNT(*) AS record_count
FROM dwd_payment_success
GROUP BY payment_id
HAVING COUNT(*) > 1;
```

“这可以发现部分重复记录，但不能独立证明整体数据正确。”

“因为缺失、错误状态、错误金额和错误时间，同样会导致结果不一致。”

### 二、如何防止对账任务自身出错？

“否则一边统计到 20:00，另一边只处理到 19:58，差异只是正常的异步延迟。”

“此外，金额必须采用一致的精度、币种、舍入方式和退款归属规则。”

ClickHouse 城主终于来到王宫。

“MySQL InnoDB 的聚簇 B+ 树，适合大量事务型访问模式。”

“而 MergeTree 面向的是高吞吐写入、按排序键组织数据，以及高效的分析型扫描。”

### 一、Part：一批数据形成一座小仓库

当数据写入 MergeTree 表时，系统会形成数据 Part。

一个 Part 内部的数据按照排序键组织。

例如：

```
CREATE TABLE live_payment
(
    payment_id UInt64,
    room_id UInt64,
    user_id UInt64,
    paid_at DateTime,
    amount_cent Int64
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(paid_at)
ORDER BY (room_id, paid_at, payment_id);
```

架构师解释：

`PARTITION BY` 决定分区组织方式。

`ORDER BY` 决定 MergeTree 中数据的排序键。

“最需要记住的是，ClickHouse 的 `ORDER BY` 在这里不是查询语句中的排序。”

“它影响的是数据写入后的物理组织。”

### 二、Part 的不断合并

假设每次写入都产生一些数据 Part。

```
Part A：10 万行
Part B：12 万行
Part C：8 万行
Part D：15 万行
```

ClickHouse 会在后台根据合并策略，将部分小 Part 合并成更大的 Part。

### MergeTree 的后台合并

Part A

Part B

Part C

Part D

A+B

C+D

更大的有序 Part

简化示意；实际 MergeTree 合并策略不保证按照图示步骤或时间立即合并。

“Part 在创建后采用不可变的组织方式。”

“后台合并会生成新的 Part，再逐步替换旧 Part。”

“因此，如果上游每条事件都单独 INSERT，就可能产生大量小 Part，给合并、元数据和查询带来压力。”

“批量写入通常更加合适。”

ClickHouse 官方文档也将不可变 Part、稀疏索引和后台合并列为 MergeTree 的关键设计。

### 一、Granule 是什么？

“Granule 可以理解为 MergeTree 中索引与数据读取的重要粒度。”

假设有：

8192 行数据。

对应一个稀疏索引粒度。

如果一亿行在理想化情况下都按 8192 行划分：

\\[ \frac{100000000}{8192}\approx12207 \\]

“并不是。”

“稀疏索引用于帮助排除不可能匹配的 Granule。”

“对于被保留下来的 Granule，仍需要读取必要列并执行进一步过滤。”

## 第六幕：Partition 与 ORDER BY——两把看似相同、实际不同的钥匙

第二天，数据库工程师提出了一个新的设计。

### 一、Partition 主要解决什么问题？

架构师解释：

“ClickHouse MergeTree 的 Partition 可以帮助组织数据生命周期，并在查询条件匹配时进行分区裁剪。”

“例如按照月份分区。”

```
PARTITION BY toYYYYMM(paid_at)
```

“如果我们需要删除某个月已经过期的数据，就可以考虑分区级的数据管理操作。”

“如果查询只涉及最近一个月，也有机会排除其他月份。”

“但 Partition 不是越多越好。”

### 二、为什么过多分区很危险？

“陛下，MergeTree 的数据 Part 位于具体 Partition 内。”

“分区过多可能造成 Part 数量与元数据管理成本增长。”

“而且后台合并通常在分区内部进行，不会随意跨分区合并。”

“如果按一千万个用户分别分区，高基数分区键可能导致大量小 Part，增加写入和维护压力。”

ClickHouse 官方教程也强调，分区更应优先围绕生命周期和数据管理需求设计，而不是把高基数分区当成索引的替代品。

### 三、Partition 和 ORDER BY 的区别

国王要求架构师总结。

| 设计             | 主要职责                      | 示例                        |
| -------------- | ------------------------- | ------------------------- |
| `PARTITION BY` | 将数据组织到不同逻辑分区，方便生命周期管理与裁剪  | 按月分区                      |
| `ORDER BY`     | 决定 Part 内数据排序，支持稀疏索引的数据跳过 | `(room_id, paid_at)`      |
| 跳过索引           | 根据额外的块级元信息排除部分数据块         | minmax、set、bloom filter 等 |

“陛下，要根据主要查询模式选择排序键。”

“假设大多数查询都带 `room_id`，然后按照时间范围过滤，`(room_id, paid_at)` 可能是一个合理的候选。”

“但如果大量查询只按照时间过滤、完全不指定 room_id，这个排序键就未必理想。”

### 四、跳过索引不是传统二级索引

架构师展示了一段示意 DDL。

```
CREATE TABLE user_events
(
    user_id UInt64,
    room_id UInt64,
    event_type LowCardinality(String),
    event_time DateTime,

    INDEX idx_event_type event_type
        TYPE set(100) GRANULARITY 4
)
ENGINE = MergeTree
ORDER BY (room_id, event_time);
```

“这个 `set` 跳过索引的效果取决于每个索引块中不同值的数量。”

“如果块内不同值过多，索引效果可能很差。”

“Bloom Filter 类索引也存在误判，通常无法保证每次都跳过所有不匹配数据。”

国王问：

“怎么知道索引到底有没有效果？”

“不要凭感觉。”

“通过 EXPLAIN、查询日志与实际读取数据量观察。”

“例如在支持相应语法的 ClickHouse 版本中：”

```
EXPLAIN indexes = 1
SELECT count()
FROM user_events
WHERE room_id = 1001
  AND event_time >= '2027-01-01';
```

“重点关注有多少 Part、Granule 被选择，以及实际读取了多少行、多少字节。”

## 第八幕：物化视图——为什么每次都从一百亿行重新计算？

此时，帝国最热门的查询是：

### 一、预聚合的思想

假设原始明细有一亿行。

最终只需要一万个直播间的成交额。

我们可以提前按照直播间汇总。

```
原始支付事件
      ↓
按 room_id 聚合
      ↓
一万条直播间统计
      ↓
实时大屏查询
```

“这样查询时只需要读取已经计算好的结果。”

“这就是空间换时间。”

### 二、ClickHouse 物化视图

架构师展示一个简化示例。

```
CREATE TABLE room_gmv_state
(
    room_id UInt64,
    stat_date Date,
    amount_state AggregateFunction(sum, Int64)
)
ENGINE = AggregatingMergeTree
ORDER BY (stat_date, room_id);
```

创建基于插入数据触发聚合的物化视图：

```
CREATE MATERIALIZED VIEW room_gmv_mv
TO room_gmv_state
AS
SELECT
    room_id,
    toDate(paid_at) AS stat_date,
    sumState(amount_cent) AS amount_state
FROM live_payment
GROUP BY room_id, stat_date;
```

查询聚合状态：

```
SELECT
    room_id,
    sumMerge(amount_state) AS gmv_cent
FROM room_gmv_state
WHERE stat_date = '2027-01-01'
GROUP BY room_id
ORDER BY gmv_cent DESC
LIMIT 100;
```

架构师解释：

“这个方案展示了增量插入与聚合状态合并的基本思路。”

“但如果上游重复插入支付事件，这个求和视图同样可能重复计数。”

“而如果原始支付记录后来被更新或删除，普通基于插入触发的增量物化视图也不能被简单理解为自动回滚之前的业务金额。”

“数据更新和修正策略必须单独设计。”

### 三、物化视图的代价

国王问：

“那我们把所有 SQL 都提前做成物化视图不就行了？”

架构师回答：

“物化视图要消耗存储空间。”

“也会增加写入或刷新开销。”

## 第十幕：十亿行慢 SQL——真正的优化顺序

战争进入最关键的阶段。

帝国分析师提交了一条 SQL。

```
SELECT
    room_id,
    SUM(amount_cent) AS amount
FROM live_payment
WHERE paid_at >= '2027-01-01'
  AND paid_at < '2027-02-01'
GROUP BY room_id
ORDER BY amount DESC
LIMIT 100;
```

查询耗时十二秒。

国王立即问：

“要不要增加十倍 CPU？”

架构师回答：

“先判断查询到底耗费在哪里。”

他制定了一份排查流程。

### 第一步：检查查询是否扫描了过多数据

“首先看实际读取行数与字节数。”

“如果只查询一个月，却扫描了三年的数据，优先检查分区裁剪和排序键匹配情况。”

### 第二步：检查查询访问了多少列

“假设原表有六十列，而查询只需要 `room_id`、`paid_at` 和 `amount_cent`。”

“应观察底层扫描是否只读取必要列，以及是否存在额外的表达式和 Join 引入不必要数据。”

### 第三步：检查聚合状态

“如果 Group By 的 Key 具有极高基数，Hash 聚合可能需要大量内存。”

“如果还有精确去重，多维分组可能进一步放大状态规模。”

### 第四步：检查排序

“`ORDER BY SUM(...) DESC LIMIT 100` 可能只返回一百行。”

“但引擎仍然需要先完成足够范围内的聚合，才能知道哪一百个直播间金额最高。”

“不能只因为最终 LIMIT 100，就认为只会处理一百条记录。”

### 第五步：检查数据布局与 Part

“观察 Part 数量是否异常。”

“是否有过多小 Part？”

“后台 Merge 是否落后？”

“磁盘带宽、CPU、内存和并发查询是否互相争用？”

### 第六步：检查是否值得预聚合

“如果同一排行榜每秒被查询很多次，并且允许秒级统计延迟，可以考虑提前计算窗口汇总。”

“如果查询偶尔发生，且用户需要任意维度组合，就应评估预计算的收益是否值得维护成本。”

- 对稳定热门指标使用结果缓存。
- 对慢查询进行监控和归因。

### 四、不要把分析接口设计成无限分页

“假设前端要展示全国数千万用户的消费明细。”

“我们不能无条件允许：

```

```

“对于大规模结果导出，最好使用独立任务和对象存储交付，而不是把所有数据塞进一次 HTTP 响应。”

```
@RestController
@RequestMapping("/api/analytics")
public class AnalyticsController {

    private final AnalyticsService service;

    public AnalyticsController(
            AnalyticsService service) {
        this.service = service;
    }

    @PostMapping("/query")

        return service.execute(request);
    }
}
```

“这只是 Controller 的骨架。”

“尤其不要允许普通运营用户通过任意维度组合读取不属于其权限范围的用户信息。”

“系统内平均请求数等于长期平均吞吐率乘以平均停留时间。”

“假设系统稳定完成 2,000 QPS，平均请求停留 0.1 秒。”

\\[ L=2000\times0.1=200 \\]

“系统内平均约有 200 个在途请求。”

“如果吞吐率不变，但平均停留时间增加到一秒：”

\\[ L=2000\times1=2000 \\]

“在稳态条件下，系统内平均在途请求数就变为 2,000。”

“但陛下，这里的 L 不是直接等于 Java 线程数。”

“因为请求可能处于排队、非阻塞 I/O 或其他等待状态。”

“同时，系统持续过载且队列不断增长时，不能随意用一个稳态公式预测无限增长过程。”

国王点头。

“所以请求变慢，本身也可能进一步加剧资源压力。”

“是的。”

## 第三幕：线程池——为什么更多士兵反而让王国更慢？

架构师带国王来到 Java 线程军团。

军团长拿出一份配置。

```
ThreadPoolExecutor executor =
    new ThreadPoolExecutor(
        32,
        256,
        60,
        TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(10000),
        new ThreadPoolExecutor.AbortPolicy()
    );
```

国王问：

“核心线程 32，最大线程 256，队列一万。”

“配置得不错吧？”

架构师说道：

“陛下，我们首先需要理解线程池的工作规则。”

### 一、ThreadPoolExecutor 的基本调度

对于上述配置，简化理解：

1. 工作线程少于 `corePoolSize` 时，新任务通常可以创建核心线程。
2. 核心线程达到配置数量后，优先尝试放入工作队列。
3. 队列无法接收任务时，若线程数还未达到 `maximumPoolSize`，才尝试增加工作线程。
4. 线程数和队列都达到限制后，执行拒绝策略。

“因此，在一个容量为一万的 LinkedBlockingQueue 尚未填满时，线程池可能长期只有 32 个核心工作线程，尽管 maximumPoolSize 设置了 256。”

国王大惊。

“也就是说，我设置了最大线程数 256，不代表高负载时会立即使用 256 个线程？”

“正是。”

### 二、大队列为何危险？

架构师继续解释：

“假设任务持续到来的速度高于线程池处理能力。”

“队列就会逐渐积压。”

“哪怕每个任务本身只需要几十毫秒，排队时间也可能增长到几秒甚至几十秒。”

“用户最终看到的是完整响应时间，而不是业务方法单独执行时间。”

### 三、拒绝策略

架构师展示常见策略。

| 策略                  | 典型行为           |
| ------------------- | -------------- |
| AbortPolicy         | 抛出拒绝异常         |
| CallerRunsPolicy    | 由提交任务的线程尝试执行任务 |
| DiscardPolicy       | 丢弃被拒绝任务        |
| DiscardOldestPolicy | 尝试丢弃队列头部任务再提交  |

“陛下，选择拒绝策略必须结合业务语义。”

“不能让支付任务被静默丢弃。”

“而 CallerRunsPolicy 虽然可能对上游产生一定反压效果，但也可能阻塞 HTTP 请求线程或者消息消费线程。”

### 四、线程数应该如何估算？

国王问：

“那到底多少线程才合理？”

架构师说道：

“对于计算密集型任务，可以从可用 CPU 核数、任务计算比例和调度开销入手。”

“对于存在大量阻塞等待的任务，可能需要更多并发执行单元。”

“一条常见的粗略经验公式是：”

\\[ N\approx N\_{\text{CPU}} \left(1+\frac{W}{C}\right) \\]

其中：

\\(W\\)：任务等待时间。

\\(C\\)：任务实际计算时间。

“但这只是特定假设下的容量估算启发式，不是可以无条件套用的定律。”

“最终还要考虑数据库连接池、外部服务限流和内存资源。”

### 五、Java 21 虚拟线程能解决吗？

国王突然想起来。

“我们可以使用 Virtual Thread！”

架构师点头。

“Java 21 虚拟线程可以显著降低大量阻塞式任务长期占用平台线程的成本，尤其适合大量等待型任务。”

“但虚拟线程不能把一台数据库的处理吞吐量变成无限大。”

“如果 MySQL 连接池只有 100 个连接，即使同时创建十万个虚拟线程，最终也仍然要面对连接池容量和下游吞吐约束。”

“对于 CPU 密集型任务，虚拟线程也不能创造额外 CPU 核心。”

> 线程池优化的目标不是让线程数量最大，而是让资源使用、任务排队和响应延迟保持可控。

## 第四幕：连接池之门——一千个线程争夺一百张通行证

夜幕降临。

MySQL 巨城入口出现了一条长队。

一千个 Java 工作线程同时等待数据库连接。

但城门只有一百张通行证。

国王问：

“为什么不将连接池直接增大到一千？”

数据库总督立即反对。

“陛下，每个数据库连接也会占用数据库资源。”

“更多连接不意味着更高的数据库吞吐。”

### 一、连接池的本质

“假设 HikariCP 最大连接数为 100。”

“那么应用实例最多通过这个连接池持有配置数量范围内的数据库连接。”

“请求借用连接时，如果可用连接不足，就可能等待。”

“等待超过配置时间，会出现连接获取超时。”

### 二、真正要监控什么？

架构师要求监控官记录：

- 活跃连接数。
- 空闲连接数。
- 等待连接的线程数量。
- 获取连接的等待时间。
- 数据库事务执行时间。
- 数据库 CPU、I/O、锁等待和慢查询。

“如果应用连接池长期满载，不一定代表应该扩容连接池。”

“可能是 SQL 慢。”

“可能是事务范围过大。”

“也可能是业务线程在持有连接期间等待第三方接口返回。”

### 三、长事务的危险

架构师找到一段代码。

```
@Transactional
public void createOrder(OrderRequest req) {
    orderRepository.save(buildOrder(req));

    paymentClient.requestPayment(req);

    notificationClient.sendMessage(req);
}
```

国王问：

“有什么问题？”

架构师回答：

“如果事务代理在这段方法里已经开启数据库事务，那么外部支付调用和通知调用可能被包含在事务生命周期内。”

“这会延长事务，甚至让数据库连接、锁等资源被不必要地持有。”

“因此，应该根据业务原子性边界，将外部调用与数据库事务合理拆分，利用 Outbox、异步任务或状态机处理跨系统流程。”

### 四、连接池容量不能只看单个实例

架构师又写了一行：

```
Java 实例数：100
每实例连接池上限：50
理论应用连接上限：5000
```

“陛下，如果数据库最多只适合承担远少于 5000 个活跃连接对应的实际负载，这个集群配置就需要重新考虑。”

“应用横向扩容时，数据库总连接上限也会随之上升。”

“这就是为什么必须进行端到端容量规划。”

## 第五幕：CPU 只有 30%，为什么 API 还是很慢？

第二天。

监控官带来一份奇怪的报告。

“陛下！某个服务的 CPU 使用率只有 30%。”

“但是 API P99 已经达到两秒。”

国王问：

“CPU 都没满，怎么可能成为性能问题？”

架构师说道：

“因为 CPU 使用率只是众多指标之一。”

### 一、CPU 低、请求慢的可能原因

第一种，等待数据库连接。

第二种，等待 MySQL 行锁。

第三种，等待网络 I/O。

第四种，等待外部 HTTP 服务。

第五种，线程池排队。

第六种，少数 CPU 核心局部热点或线程竞争。

第七种，频繁短暂停顿、内存分配或其他运行时问题。

“陛下，整体 CPU 30% 并不意味着每个 CPU 核心、每个工作线程和每个共享依赖都只有 30% 负载。”

### 二、CPU 利用率与吞吐量

架构师解释：

“如果 CPU 是主要瓶颈，增加 CPU 资源可能提高处理能力。”

“但如果请求主要在等待数据库，增加 CPU 往往帮助很小。”

“所以性能优化必须从实际瓶颈出发。”

### 三、四类资源瓶颈

CPU

计算密集、序列化、压缩、加密、GC、热点线程。

内存

Heap、直接内存、缓存、状态大小、OOM 与内存回收。

磁盘

吞吐量、随机 I/O、IOPS、延迟、队列与后台合并。

网络

带宽、RTT、丢包、连接数、重传与跨机数据交换。

架构师说道：

“例如 Spark Shuffle 很慢，可能并不是 CPU 算不过来，而是磁盘 Spill 和网络传输成为瓶颈。”

“Redis 延迟升高，也可能来自网络、慢命令、热点访问或服务器资源竞争。”

“要先定位，再优化。”

## 第六幕：实时军团与离线军团的资源争夺

Spring 王国的资源大厅里，两个军团爆发了一场争吵。

Flink 将军说：

“我的作业必须持续处理支付事件。”

“如果延迟超过五秒，直播大屏就会出现明显滞后。”

Spark 将军反驳：

“我的历史重算任务同样重要。”

“财务月底对账，必须完成全量计算。”

双方同时要求使用一批最昂贵的服务器。

国王十分头疼。

“难道不能让他们共享资源吗？”

架构师回答：

“可以，但必须考虑隔离和优先级。”

### 一、实时任务与离线任务的不同

Flink 实时作业通常长期运行。

它可能具有较严格的连续处理延迟和状态恢复要求。

Spark 离线作业通常有明确的计算批次。

一些任务可以延迟执行，也可能在不同时间段需要大量资源。

“所以我们可以根据业务 SLA，划分资源池。”

### 二、资源隔离

架构师提出：

```
实时资源池
    Flink 核心任务
    低延迟在线统计
    关键数据管道

离线资源池
    Spark 历史重算
    ETL 批处理
    模型特征加工

共享弹性资源池
    可延迟计算
    弹性扩容任务
```

“这不是说实时和离线永远不能共享机器。”

“而是共享时要有优先级、资源上限和抢占规则，避免一个低优先级任务破坏核心在线 SLA。”

### 三、为什么单纯提高资源利用率可能是错的？

国王问：

“如果我们让每台服务器 CPU 都达到 95%，是不是资源利用率就非常好了？”

架构师摇头。

“资源利用率高，不一定表示系统效率最优。”

“如果某个实时服务需要保留突发容量，而我们把空闲资源全部交给无法及时中断的离线任务，流量高峰到来时就可能没有足够的资源恢复余量。”

“因此，适当的冗余容量本身具有可用性价值。”

## 第七幕：Kubernetes 弹性军团——让服务器随流量增减

架构师带国王来到 Kubernetes 调度中心。

国王问：

“能不能让系统自动增加或者减少服务实例？”

“可以。”

“但我们要区分几种不同的扩容机制。”

### 一、HPA：扩缩 Pod 数量

HPA，Horizontal Pod Autoscaler。

它可以根据 CPU、内存或其他受支持的指标调整工作负载副本数量。

例如：

```
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  minReplicas: 4
  maxReplicas: 40
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
```

架构师说道：

“这个示例表示基于 CPU 使用率目标调整副本数量。”

“注意，这里的 CPU 利用率百分比，通常是相对于容器配置的 CPU Request 来计算，而不是简单地按宿主机总 CPU 核数计算。”

“HPA 是周期性控制循环，不是请求一增加就瞬间完成扩容。”&#x20;

### 二、KEDA：基于事件驱动指标扩容

国王问：

“如果 Kafka Lag 持续上涨，但 CPU 并不高呢？”

架构师答道：

“可以考虑 KEDA。”

“KEDA 能够利用支持的事件源指标，驱动 Kubernetes 工作负载扩缩容。”

“例如使用 Kafka 消费积压指标来决定某些消费者部署需要多少副本。”

“但这不意味着 Kafka Lag 高就一定该扩容。”

“如果瓶颈在下游 MySQL，增加消费者可能进一步扩大压力。”

### 三、节点扩容

“如果 HPA 把 Pod 副本数增加到 40，但 Kubernetes 集群没有足够的计算资源，新 Pod 可能无法调度。”

“这时，还需要节点级的容量管理机制。”

“某些环境会使用 Cluster Autoscaler、Karpenter 或云平台提供的其他节点自动供给方案。”

“但新增节点也需要时间。”

### 四、扩容速度也是一种资源

国王问：

“如果新节点需要一分钟才能准备好，而流量十秒内就冲上来了，怎么办？”

架构师回答：

“这就是为什么大促需要提前预热与容量准备。”

“自动扩缩容适合处理很多负载变化，但不能代替峰值容量规划。”

## 第八幕：PB 级存储——为什么有些数据应该离开昂贵的城堡？

三个月后。

数据仓库管理员走进皇宫。

“陛下，存储费用仍然很高。”

“可是我们已经优化压缩率了。”

管理员回答：

“问题不是只有压缩率。”

“我们把五年前的日志和昨天的日志放在同一种高性能存储中。”

架构师点头。

“这就是冷热分层的问题。”

### 一、热数据

热数据通常具有较高访问频率或低延迟要求。

例如：

- 最近数日的实时交易统计。
- 正在使用的业务缓存。
- 高频 OLAP 聚合数据。

“它可能需要较高性能的存储和计算资源。”

### 二、温数据

温数据访问频率较低，但仍然需要合理的查询性能。

例如历史数月的交易明细、近期审计记录。

“可以根据具体工作负载选择更便宜的存储层或降低计算资源配置。”

### 三、冷数据

冷数据可能长时间不被访问。

例如多年前的历史日志。

“它可以采用更低成本的归档存储策略。”

“但这可能带来更长的数据恢复和读取时间，以及额外的取回费用。”

### 数据生命周期与分层存储

热数据

最近 7 天

低延迟查询与高频计算

温数据

8—90 天

常规分析与历史回溯

冷数据

90 天以上

低频查询与归档恢复

时间范围仅为教学示例。真实分层依据查询模式、法规、数据恢复目标与存储成本确定。

### 四、为什么不能随意删除历史数据？

国王问：

“必须制定明确的数据保留和删除策略。”

### 五、存储成本不仅是每 TB 的价格

架构师写下一份成本公式。

\\[ C\_{\text{storage}} = C\_{\text{capacity}} + C\_{\text{requests}} + C\_{\text{retrieval}} + C\_{\text{transfer}} + C\_{\text{operations}} \\]

“如果一份冷数据每天都被读取，所谓的便宜存储未必划算。”

### 一、每百万请求成本

假设某业务一个月的可归属基础设施成本为 100 万元。

这个月成功处理了 500 亿次 API 请求。

则：

\\[ C\_{\text{million}} = \frac{1000000}{50000000000}\times1000000 \\]

\\[ =20\text{ 元/百万请求} \\]

“这意味着每百万次请求对应约 20 元的这部分基础设施成本。”

“但如果我们没有计入网络传输、数据库、缓存、可观测性以及共享资源费用，就不能称之为完整成本。”

### 二、每笔交易成本

“有些业务更适合观察每笔成功交易的成本。”

例如：

支付系统。

优惠券履约系统。

订单创建系统。

“因为单纯提高请求数量可能让每百万请求成本看起来下降，但并不意味着产生了更多真实业务价值。”

### 三、每 TB 计算成本

“对于 Spark 离线任务，可以记录处理数据规模、执行时长、CPU 时间、内存资源和云账单。”

“但每 TB 成本并不能单独衡量任务是否高效。”

“因为扫描一 TB 原始日志，与执行涉及大规模 Join 和排序的一 TB 分析任务，计算难度可能完全不同。”

提交成功
    ↓
Outbox 发布器
    ↓
Kafka / RabbitMQ
    ↓
后续异步业务
```

优点是事务边界清楚。

业务状态与待发布事件可以原子提交。

缺点是所有成功的入口写入仍然需要经过 MySQL，因此数据库必须能够承担实际写入吞吐。

### 路线 B：Redis 预占 + 可恢复的异步履约

“如果秒杀入口规模极大，我们希望大部分无效请求在 Redis 被拒绝，那么可以考虑 Redis 预占。”

“但需要配套设计可靠任务记录、消息投递确认、恢复扫描与补偿对账。”

例如：

```
用户请求
    ↓
Redis 原子预占并记录预占状态
    ↓
可靠的履约任务转移
    ↓
消息队列
    ↓
消费者幂等写 MySQL
    ↓
履约成功 / 失败补偿
    ↓
定期对账
```

架构师特别强调：

“这里的‘可靠任务转移’不是一句话就能实现的。”

“需要明确 Redis 的持久化与故障恢复能力、任务状态记录格式、哪些状态必须恢复、消息发布前崩溃如何扫描，以及补偿如何避免重复返还库存。”

“如果这些机制不完善，宁愿采用简单而正确的数据库方案。”

### 两种路线怎么选？

| 维度         | MySQL + Outbox  | Redis 预占 + 异步履约 |
| ---------- | --------------- | --------------- |
| 一致性边界      | 较清晰             | 跨系统故障窗口更多       |
| 成功请求入口写入压力 | 较高              | 可以将部分工作移到异步链路   |
| 实现复杂度      | 相对可控            | 通常更高            |
| 失败恢复       | 依托数据库事务与 Outbox | 需要预占状态恢复与补偿     |
| 适合情况       | 数据库容量足够、正确性优先   | 经过压测证明需要更高入口吞吐  |

国王终于意识到：

“性能优化不能依靠牺牲正确性换取漂亮的 QPS。”

“正是。”

### 二、消费者必须幂等

林澈写出订单事件消费逻辑。

```
@Transactional
public void handle(OrderCreatedEvent event) {
    if (processedMapper.exists(event.eventId())) {
        return;
    }

    pointsMapper.addPoints(
        event.userId(),
        event.points()
    );

    processedMapper.insert(event.eventId());
}
```

架构师看了一眼。

“这还不够严谨。”

“为什么？”

“两个消费者可能同时执行 `exists`，结果都发现未处理。”

“然后它们都发放积分。”

林澈愣住。

“那我们应该依赖数据库唯一约束？”

“正确。”

架构师修改方案：

```
CREATE TABLE processed_event (
    event_id VARCHAR(64) PRIMARY KEY,
    processed_at DATETIME NOT NULL
);
```

然后将“抢占事件处理权”和“发放积分”放进同一事务。

```
@Transactional
public void handle(OrderCreatedEvent event) {
    int inserted = processedMapper.insertIfAbsent(
        event.eventId()
    );

    if (inserted == 0) {
        return;
    }

    pointsMapper.addPoints(
        event.userId(),
        event.points()
    );
}
```

“这里假设 `insertIfAbsent` 由数据库唯一约束实现原子去重，并且积分更新与去重记录参加同一个本地事务。”

“如果积分发放涉及外部服务，那就不是这个本地事务能直接保证的事情了。”

“因此，真实设计还要根据副作用的所在系统选择相应的幂等或协调方案。”

### 三、为什么先完成事务，再确认消息？

架构师继续解释：

“如果消费者先 ACK，之后数据库事务失败，消息可能无法重新投递。”

“如果数据库提交成功之后再 ACK，虽然可能重复投递，但可以通过幂等去重。”

“对于业务任务，通常更容易接受至少一次投递，并在业务层保证重复处理安全。”

“不过，重试必须有上限或可控的退避策略。”

“不能让一个永久失败的消息无限占用消费资源。”

```

### 四、告警不能只看机器是否存活

延迟：P95、P99、队列等待时间。

错误：HTTP 错误率、业务失败率、消息重试。

饱和度：连接池、队列、线程池、CPU、磁盘与下游吞吐。

“对于实时链路，还需要看 Kafka Lag、Flink Watermark 进度、Checkpoint 和 Sink 写入状态。”

“监控必须反映用户体验，而不是仅证明所有进程都还活着。”

### 一、测试目标

假设某场优惠券活动：

总库存一万张。

峰值活动入口 100,000 QPS。

其中大部分用户没有资格、重复请求或已经遇到售罄状态。

最终能够获得预占资格的请求数量受到库存和业务规则限制。

“所以，十万入口 QPS，并不意味着数据库必须每秒创建十万笔成功订单。”

### 二、分层压测

## 终极压测 · 虚构验收记录

| 测试项目      | 示例结果        |
| --------- | ----------- |
| 入口 API 峰值 | 100,000 QPS |
| 入口校验 P99  | 85ms        |
| 库存超卖      | 未发现         |
| 重复领取      | 唯一约束验证通过    |
| 履约消费吞吐    | 2,000/s     |
| 消息恢复测试    | 按用例通过       |

全部数字为小说中的假设，不代表已经实际部署或测得相应性能。真实验收还需包含环境配置、统计窗口、请求分布、错误预算和故障覆盖范围。

“为什么履约只有每秒两千？”

“因为数据库最终持久化能力有其自身上限。”

“异步队列能够将入口峰值与下游处理速率解耦，但不能创造数据库容量。”

“如果活动的业务 SLA 要求一分钟内完成所有一万笔成功领取，消费者的可持续吞吐必须足以满足这个目标，并留有故障余量。”

“所以我们不仅检查 QPS，还检查从预占到最终结果的端到端延迟分布。”

现在，它拥有入口网关、业务服务集群、缓存层、数据库事务、可靠消息系统、WebSocket 长连接服务，以及从 Kafka 到 Flink、ClickHouse 的实时分析链路。

但林澈知道，真正重要的变化并不在于组件数量。

而在于他终于能够回答那些以前无法回答的问题。

为什么库存不会超卖？

为什么重复消息不会重复发放积分？

为什么异步履约失败后仍然能够恢复？

为什么百万连接不需要百万个线程？

为什么增加消费者不一定能够消除消息积压？

为什么服务器 CPU 很低，接口却可能很慢？

为什么 Flink Checkpoint 成功，财务报表却仍然可能错误？

为什么十万入口 QPS 不等于十万订单事务 TPS？

又为什么一次成功的压测，不能证明系统永远不会发生故障？

国王 Java 看着年轻工程师。

“你现在认为，什么才是真正的高并发工程能力？”

林澈沉思了很久。

随后，他回答：

“不是知道多少中间件。”

“而是能在业务约束下设计系统，知道瓶颈在哪里，知道数据可能在哪一步出错，能够用代码保护正确性，用压测证明容量，用故障演练证明恢复能力。”

首席架构师终于露出笑容。

“很好。”

“但你现在只完成了工程的第一阶段。”

国王有些惊讶。

“还有下一阶段？”

架构师拿出一份新的报告。

这一次，报告中没有任何代码错误。

也没有任何数据库异常。

却有一项指标开始持续恶化。

线上系统的性能，正在随着每一次版本发布而逐渐下降。

“陛下，我们的工程现在能够运行。”

“接下来，要解决的是如何让它长期保持可靠。”

“一个人写出的高性能代码，如何在数百名工程师不断修改之后仍然保持正确？”

“我们需要建立容量回归测试、性能基线、灰度发布、自动回滚、混沌工程和工程质量门禁。”

“否则，再优秀的系统，也可能在不断迭代中慢慢崩溃。”
