### 第二幕：什么是高并发？

国王召集了帝国所有工程师。

首席架构师拿出一张图纸。

“陛下，您需要先理解两个概念。”

“并发（Concurrency）与并行（Parallelism）。”

他在地上画出两座城门。

并发：一个守卫交替处理多个请求

通过调度交替推进多个任务，不代表它们在同一瞬间都在执行。

并行：多个守卫同时处理不同请求

多个处理核心真正同时执行任务。并发系统可以包含并行执行。

架构师解释道：

“假设一名士兵需要十秒钟处理一份公文。”

“如果十份公文接连送来，他可以在不同公文之间切换，这叫并发。”

“如果安排十名士兵，同时处理十份公文，这叫并行。”

### 第三幕：QPS、TPS 与 RT

架构师指向城门。

“陛下，假设一秒钟内，有 10,000 次查询抵达王国。”

“那么我们的查询吞吐量就是 10,000 QPS。”

QPS（Queries Per Second） 通常表示每秒查询请求数，Web 系统中也常被用来描述请求吞吐量，但不同监控系统对 query 的定义可能不同。

“如果每秒成功完成 3,000 笔交易呢？”

“那么在每笔交易被定义为一个业务事务的前提下，TPS 就是 3,000。”

TPS（Transactions Per Second） 表示每秒处理的事务数。

注意，一笔业务交易不一定等于一次 HTTP 请求，也不一定等于一次数据库事务。

国王又问：

“如果有些人等了很长时间才得到回应，我们又该如何衡量？”

“这就要看 RT。”

RT（Response Time） 是请求响应时间，也称延迟。

一名臣民请求查看商品：

- 20ms 返回：体验很好。
- 200ms 返回：通常仍然比较流畅。
- 2s 返回：可能已经明显感觉到等待。
- 10s 返回：用户可能直接放弃。

这些只是直观示例，实际性能目标取决于业务场景、网络与设备。

架构师补充：

“还有一个指标比平均响应时间更容易暴露问题。”

“叫作 P99。”

国王皱眉。

“什么意思？”

“假设我们记录了 10,000 个请求的响应时间并排序。”

“如果平均 RT 是 100ms，但 P99 达到 5 秒，说明仍然有不少用户会遭遇严重延迟。”

### 第四幕：一条神秘公式——利特尔法则

国王终于明白了。

然而，他又提出一个问题。

“假设王国一秒能够完成 1,000 个请求，每个请求平均耗时 0.2 秒，那么系统里平均同时有多少个请求？”

架构师微微一笑。

“这就是高并发领域著名的 Little's Law（利特尔法则）。”

他在黑板上写道：

\\[ L=\lambda W \\]

其中：

- \\(L\\)：系统内平均请求数量。
- \\(\lambda\\)：长期平均完成吞吐率。
- \\(W\\)：平均请求在系统内停留的时间。

代入数字：

\\[ L=1000\times0.2=200 \\]

“陛下，在符合稳态等适用条件时，系统中平均存在约 200 个尚未完成的请求。”

国王恍然大悟。

“也就是说，如果请求越来越慢，即使吞吐量不变，系统内积压的请求也可能越来越多？”

### 一、Redis 分布式锁

```

```

- `unique-token`：每个锁持有者使用唯一标识。

如果张三直接删除锁，就会误删李四的锁。

```

    return redis.call('DEL', KEYS[1])
end

return 0
```

### RabbitMQ 的本质

“陛下，消息队列就像邮政系统。”

“生产者把信件交给邮局。”

“邮局暂时保存信件。”

在我们的业务中：

- Producer：优惠券领取服务。
- Exchange：根据路由规则将消息交给队列。
- Queue：存放等待处理的领取任务。
- Consumer：执行数据库持久化操作的履约服务。

### 削峰填谷的数学原理

架构师解释：

“假设某一秒有 10,000 个有效任务进入队列。”

“而数据库每秒只能稳定完成 1,000 个任务。”

“那么第一秒，理想情况下只能处理其中的 1,000 个，剩余约 9,000 个需要等待。”

“如果后续没有新任务，且处理速度始终保持 1,000 个/秒，这一批任务理论上需要约 10 秒才能处理完。”

“如果持续每秒进入 2,000 个任务，但每秒只能处理 1,000 个，那么队列积压会持续增长。”

\\[ \Delta Q = \lambda\_{\text{in}}-\mu\_{\text{out}} \\]

其中 \\(\lambda\_{\text{in}}\\) 为进入速率，\\(\mu\_{\text{out}}\\) 为处理速率。

### 什么是幂等？

“陛下，假设您命令士兵关闭城门。”

“命令执行一次，城门关闭。”

“再执行一次，城门仍然关闭。”

“无论重复执行多少次，最终状态一样。”

“这就是幂等性的直观含义。”

不过，工程上的幂等还需要保证重复执行不会产生额外的业务副作用。

例如，重复发送短信、重复扣费、重复发券，都可能造成问题。

### 数据库唯一索引

对于一人只能领取同一种优惠券一次的业务，可以建立唯一约束。

```
CREATE TABLE coupon_claim (
    id BIGINT PRIMARY KEY,
    request_id VARCHAR(64) NOT NULL,
    user_id BIGINT NOT NULL,
    coupon_id BIGINT NOT NULL,
    status VARCHAR(32) NOT NULL,

    UNIQUE KEY uk_request (request_id),
    UNIQUE KEY uk_user_coupon (user_id, coupon_id)
);
```

架构师解释：

“`uk_request` 防止同一个业务请求被重复创建。”

“`uk_user_coupon` 防止同一个用户重复领取同一种优惠券。”

“这两个唯一约束解决的是不同问题。”

“但消费者仍然需要在事务中正确处理唯一键冲突，并确认已有记录是否确实代表同一次成功履约。”

```
@RabbitListener(queues = "coupon.claim.queue")
public void handle(
        ClaimMessage message,
        Channel channel,
        Message amqpMessage) throws IOException {

    long tag = amqpMessage.getMessageProperties()
            .getDeliveryTag();

    try {
        claimService.fulfillIdempotently(message);
        channel.basicAck(tag, false);
    } catch (Exception ex) {
        // 此处必须区分可重试和不可重试错误。
        // 实际系统需配置有限重试、退避、死信队列等。
        channel.basicNack(tag, false, false);
    }
}
```

常见算法包括：

固定窗口：按固定时间段统计请求数量，实现简单，但边界附近可能出现突发流量。

滑动窗口：将时间窗口细分或使用滚动统计，流量控制相对平滑。

令牌桶：按照一定速率补充令牌，允许一定程度的突发请求。

漏桶：按照相对稳定的速率处理或放行请求，平滑输入流量。

### 简化的 B+ 树结构

这是说明多路索引和叶子节点的概念图，并非严格的 InnoDB 页面布局或分隔键示例。

### 三、聚簇索引与二级索引

国王继续问：

“假设我用订单 ID 查找数据，和用用户 ID 查找数据，有区别吗？”

架构师写出：

```
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    amount DECIMAL(12, 2),
    status TINYINT,
    created_at DATETIME,
    KEY idx_user_id (user_id)
) ENGINE = InnoDB;
```

“在 InnoDB 中，主键对应的聚簇索引，其叶子节点保存完整的行记录。”

“而普通二级索引的叶子记录通常保存二级索引列以及主键值。”

查询主键：

```
SELECT *
FROM orders
WHERE id = 9527;
```

通常可以直接通过聚簇索引定位行。

但查询用户 ID：

```
SELECT *
FROM orders
WHERE user_id = 1001;
```

如果优化器选择使用 `idx_user_id`，可能需要：

先在二级索引中找到满足条件的主键。

然后通过主键访问聚簇索引，获取其他字段。

这个过程叫作：

回表。

国王若有所思。

“也就是说，先查目录，再根据目录中的编号取出完整档案？”

“没错。”

这叫作：

覆盖索引。

例如：

```
SELECT id, user_id
FROM orders
WHERE user_id = 1001;
```

对上面的索引而言，查询所需字段已经可以由二级索引提供。

无需为了其他列额外读取完整行。

### 一、LIMIT 的真正含义

```
LIMIT 10000000, 20
```

表示：

跳过前一千万条结果。

再取二十条。

“虽然最终只返回二十条，但是数据库为了确定这二十条在哪里，通常需要处理前面大量的索引记录。”

“如果还涉及排序、回表或其他操作，代价可能进一步增加。”

国王问：

“那为什么不直接告诉数据库，从哪一条记录开始？”

架构师眼前一亮。

“这就是游标分页。”

### 二、Keyset Pagination：游标分页

假设上一页最后一条订单 ID 是：

`10000000`

那么下一页可以这样查询：

```
SELECT *
FROM orders
WHERE id > 10000000
ORDER BY id
LIMIT 20;
```

“这一次，MySQL 可以通过主键索引定位起点，再向后扫描少量记录。”

“无需每次都重新跳过一千万条。”

国王惊叹：

“这不是比 OFFSET 快得多？”

“对于基于合适索引的连续翻页，通常是这样。”

“不过它也有约束。”

“如果业务需要随机跳转到第 500000 页，游标分页就没那么直接。”

“如果按创建时间排序，还需要考虑相同时间的记录如何稳定排序。”

架构师写下：

```
SELECT *
FROM orders
WHERE
    created_at < :lastTime
    OR (
        created_at = :lastTime
        AND id < :lastId
    )
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

“在 `(created_at, id)` 上建立合适的联合索引，能够帮助执行这种分页。”

“并且我们需要一个唯一的排序后缀，例如主键 ID，确保分页顺序稳定。”

| 字段            | 含义                                 |
| ------------- | ---------------------------------- |
| type          | 访问方式，如 `const`、`ref`、`range`、`ALL` |

### 三、联合索引与最左前缀

架构师又给国王看了一个索引。

```
CREATE INDEX idx_user_status_time
ON orders(user_id, status, created_at);
```

“陛下，它就像一个按用户、状态、时间依次排列的档案目录。”

下面的查询通常能够利用索引前缀：

```
WHERE user_id = 1001
```

以及：

```
WHERE user_id = 1001
  AND status = 1
```

甚至：

```
WHERE user_id = 1001
  AND status = 1
  AND created_at > '2026-01-01'
```

但是：

```
WHERE status = 1
```

没有提供第一列 `user_id`。

“因此，对于这类条件，传统上不能像匹配最左前缀那样直接定位。”

“不过，陛下，千万不要死记为‘跳过第一列就绝对不可能使用索引’。”

“不同 MySQL 版本可能具有不同的优化能力，例如 Skip Scan。还要根据覆盖情况、成本估计和实际执行计划判断。”

国王终于理解。

“优化器不是一个只会背规则的官员。”

“它会评估不同计划的成本，而统计信息和估计误差也会影响选择。”

## 第五幕：分表战争——一座城装不下所有档案

数月后。

尽管帝国优化了索引和慢查询，数据库压力仍然继续上升。

因为订单量已经突破三亿。

一张订单表还承担着大量写入、索引维护、历史归档和分析需求。

架构师来到国王面前。

“陛下，我们需要认真考虑数据拆分。”

“分库分表？”

“没错。”

“但我们必须先分清两种不同的拆分方式。”

### 一、垂直拆分

架构师拿出一个订单。

其中有：

订单编号。

用户编号。

支付金额。

收货地址。

物流备注。

商品快照。

售后信息。

“陛下，如果所有字段都塞进一张巨大表，某些查询可能读取和维护很多不必要的数据。”

“我们可以根据业务职责，把数据分成不同的表。”

例如：

  status

  order_id
  receiver
  address

“这叫垂直分表。”

“而将用户业务、订单业务、商品业务分到不同数据库实例，也是一种更大粒度的垂直拆分。”

“它能够改善职责边界和某些负载，但也可能引入跨表、跨服务查询。”

### 二、水平分表

“陛下，假设我们有一亿条订单。”

### 三、分库分表的代价

国王兴奋地说道：

“那么只要不断分片，数据库就能无限扩容？”

架构师摇头。

“事情没有那么简单。”

他列举出几个新问题。

第一个问题：跨分片查询。

如果一个用户的订单按照 userId 分片，查询某个用户很方便。

但财务官需要查询所有用户最近一小时的订单。

系统可能需要查询多个分片，然后归并结果。

第二个问题：跨分片排序与分页。

如果数据分散在十六张表里，想按全局创建时间排序，通常需要多分片查询与结果合并。

不能简单地对每张表都执行同一个 `LIMIT offset, size`，再随便拼接。

第三个问题：分布式事务。

如果订单、优惠券和支付记录被拆到不同数据库，原来一个本地 MySQL 事务可能无法覆盖全部操作。

第四个问题：扩容与数据迁移。

“陛下，假设今天按照 `%16` 分片。”

“明天分片数量增加到 32。”

“原来的分片规则会发生大量变化。”

“这意味着我们可能需要重新路由或者迁移数据。”

“所以实际系统常常会引入逻辑分片、物理分片映射、分片路由层等机制，降低扩容的改造成本。”

国王终于意识到：

“分库分表是把一个巨大的问题，拆成很多较小的问题。”

“但同时也会产生分布式系统的新问题。”

“完全正确。”

## 第六幕：雪花骑士——分布式 ID 的诞生

数据库管理员报告：

“但是它们可能产生相同的编号！”

国王问：

“不能继续使用 MySQL AUTO_INCREMENT 吗？”

“单个表内部当然可以。”

“但如果业务需要跨分片全局唯一的订单 ID，就必须重新考虑 ID 生成方式。”

架构师拿出一个新的方案。

架构师说道：

“我们可以考虑读写分离。”

### 主从延迟的故事

一名用户刚刚创建订单。

写请求成功提交到主库。

随后，他立刻查询自己的订单列表。

由于读请求被路由到从库，而从库尚未应用对应的复制事件。

“我明明刚下单，怎么订单列表里什么都没有？”

国王惊讶。

“数据库的数据不一致了？”

架构师回答：

“更准确地说，在异步复制场景下，主从之间可能存在暂时的数据可见性差异。”

“因此，我们需要根据业务对一致性的要求设计读路由。”

例如：

- 下单后立即查询订单状态，可以短时间内读取主库。
- 对一致性要求较低的商品展示，可以使用从库。
- 更复杂的系统还可以通过复制位置、会话级读策略等方式保障特定的一致性需求。

“但陛下，主从复制不是简单的灾备开关。”

“故障切换、数据丢失风险、复制延迟、事务顺序和应用读路由，都需要明确设计。”

## 第八幕：数据分析师的请求——为什么 OLTP 不应该承担所有任务？

某天，帝国财政大臣来到王宫。

“陛下，我想知道过去三年中，每个省份、每个月、每个商品类别的销售额变化情况。”

国王说道：

“这不是很简单吗？写一条 SQL。”

```
SELECT
    province,
    DATE_FORMAT(created_at, '%Y-%m') AS month,
    category_id,
    SUM(amount)
FROM orders
GROUP BY
    province,
    DATE_FORMAT(created_at, '%Y-%m'),
    category_id;
```

架构师看着这条 SQL，陷入沉思。

“陛下，这就是另一个问题。”

“我们的 MySQL 主要承担在线事务处理。”

“而财政大臣需要的是大规模数据分析。”

“这是两种不同的工作负载。”

### OLTP：在线事务处理

OLTP，即 Online Transaction Processing。

典型场景：

- 创建订单。
- 查询用户账户。
- 支付扣款。
- 更新库存。
- 修改订单状态。

特点通常是：

单次操作涉及的数据范围较小。

需要较低延迟。

强调事务正确性。

存在较多小规模读写操作。

### OLAP：在线分析处理

OLAP，即 Online Analytical Processing。

典型场景：

- 统计过去三年 GMV。
- 分析不同城市的用户消费行为。
- 计算商品转化率。
- 统计亿级订单趋势。
- 对历史数据执行多维聚合。

特点通常是：

需要读取大量记录。

涉及复杂聚合。

数据分析维度较多。

更加关注大规模扫描、计算吞吐量和聚合效率。

架构师告诉国王：

“陛下，如果把持续数十秒甚至数分钟的大型分析查询直接运行在核心交易库，可能严重影响在线交易。”

“不是因为 MySQL 完全不能分析数据。”

“而是交易型负载与分析型负载的资源需求不同，把它们混在一起可能造成竞争。”

“我们需要建立一座新的城市。”

国王问：

“叫什么？”

“数据仓库。”

## 第九幕：ClickHouse 与列式存储——只读取真正需要的列

架构师带着国王参观了两座档案馆。

第一座档案馆叫作行式存储。

里面每一份订单档案都完整地放在一起。

```
订单 1：
id、user_id、amount、status、created_at

订单 2：
id、user_id、amount、status、created_at

订单 3：
id、user_id、amount、status、created_at
```

国王问：

“这有什么问题？”

架构师说道：

“如果我们想读取某一条订单的全部字段，这种组织方式通常很自然。”

“但如果我们只需要统计一亿条订单的金额之和呢？”

“我们其实主要关心 amount 列。”

于是架构师带着国王来到第二座档案馆。

这里的记录按照列组织。

```
id 列：
1、2、3、4、5...

user_id 列：
1001、1002、1003...

amount 列：
99.9、199.0、68.0...

status 列：
1、1、2、3...
```

“这样，分析程序在适合的执行计划下可以只读取需要的列。”

“而且，同一列的数据类型和取值分布比较接近，通常更容易压缩。”

这就是列式存储的重要优势之一。

### 行式与列式的区别

### 行式存储

同一行的数据组织在一起，适合常见的事务型点查和行更新。

### 列式存储

同一列的数据组织在一起，适合大规模扫描和列聚合。

架构师继续说道：

“例如 ClickHouse 是面向分析场景设计的列式数据库。”

“它可以利用列式读取、压缩、向量化执行以及并行处理等机制来提升许多分析查询的效率。”

“不过，列式存储并不意味着所有查询都更快。”

“特别是频繁的单行更新、强事务约束以及传统 OLTP 工作负载，还需要根据具体数据库的能力来评估。”

### 为什么不是直接把 MySQL 换成 ClickHouse？

国王问：

“既然 ClickHouse 分析快，那把 MySQL 全部替换掉不就行了？”

架构师回答：

“陛下，工具是为特定工作负载服务的。”

“MySQL InnoDB 擅长很多典型的在线事务处理任务。”

“ClickHouse 擅长大量分析型工作负载。”

“合理的方案通常不是无条件替换，而是分工。”

例如：

```
用户下单
    ↓
MySQL 交易库
    ↓
数据同步 / CDC
    ↓
Kafka 等数据管道
    ↓
ClickHouse 分析库
    ↓
BI 报表 / 实时看板
```

“当然，真实系统必须处理数据同步失败、重复事件、更新与删除传播、乱序以及分析侧数据延迟等问题。”

国王若有所思。

“所以，帝国开始从单一数据库，走向多种存储系统协作。”

“没错。”

“而这，就是大数据时代真正的开端。”

### 面试回答思路

第一步：确认慢在哪里。

查看慢查询日志、SQL 执行计划和实际访问的数据量。

判断是全表扫描、索引不合理、排序、回表、锁等待，还是 CPU、内存、磁盘等资源瓶颈。

第二步：优化 SQL 和索引。

考虑合理的联合索引、覆盖索引、减少不必要字段，以及深分页改造。

同时关注索引的写入维护成本，不应无限增加索引。

第三步：判断是否需要缓存。

对于热点读数据，可以使用 Redis 等缓存减少数据库访问。

但必须考虑数据更新与一致性。

第四步：考虑业务归档与冷热分离。

如果大量历史订单不再参与高频在线查询，可以按生命周期归档。

但是需要保证审计、对账和历史查询仍然满足业务要求。

第五步：评估读写分离或分库分表。

只有当负载、容量或隔离需求真正达到相应阶段，再考虑引入更复杂的分布式数据库架构。

第六步：区分交易和分析负载。

如果慢查询的根源是大型统计与聚合任务，就要评估独立分析库、数仓或数据湖体系。

### 一、Shuffle 为什么需要网络传输？

假设一百台 Mapper 分别分析一部分用户订单。

每台机器都会产生这样的中间结果：

```
(北京, 100)
(上海, 200)
(广州, 150)
```

如果我们按照城市汇总销售额，就要保证同一个城市的数据到达同一个 Reducer。

于是，系统必须根据 Key 进行分区。

默认 HashPartitioner 的典型计算方式可以理解为：

```
partition = (key.hashCode() & Integer.MAX_VALUE)
            % numReduceTasks;
```

如果有四个 Reducer，那么不同城市的 Key 会被分配到对应的分区。

但是，同一个城市的数据可能来自几十台 Mapper。

这意味着什么？

大量数据需要跨机器传输。

国王问：

“网络不是很快吗？”

架构师回答：

“网络很快，但如果 Shuffle 需要传输数十 TB 数据，网络就可能成为主要瓶颈。”

他展开 Shuffle 的详细作战地图。

### MapReduce Shuffle 过程

Mapper 输出中间 Key-Value

Partition + Sort

根据 Key 分区，在 Map 侧组织有序数据

Spill / Merge

必要时溢写磁盘，并归并中间数据

Network Shuffle

Reducer 获取属于自己的 Map 输出分区

Merge + Group

合并、排序、按 Key 分组

Reduce 聚合

架构师说道：

“在 Hadoop MapReduce 中，Map 中间输出通常需要在本地组织并可能溢写磁盘，而 Reduce 端需要获取对应分区并进行合并与分组。”

“所以 Shuffle 可能同时消耗磁盘 I/O、网络带宽、CPU 和内存。”&#x20;

### 二、Combiner：先在本地汇总

国王忽然想到了一个办法。

“假设机器 A 产生了一百万个 `(Java, 1)`。”

“为什么不先在机器 A 上统计为 `(Java, 1000000)`，然后再传输？”

架构师露出了笑容。

“陛下，您已经理解 Combiner 了。”

Combiner 可以在 Map 端对符合条件的中间数据进行局部聚合。

例如：

原本：

```
(Java, 1)
(Java, 1)
(Java, 1)
(Java, 1)
```

经过本地汇总：

```
(Java, 4)
```

需要传输的数据量可能大幅下降。

但是必须注意：

Combiner 不保证一定执行，也不保证只执行一次。

因此，不能把需要精确执行一次的业务逻辑放进 Combiner。

而且，局部汇总必须在数学和业务语义上是安全的。

求和、计数通常适合这种设计。

直接把平均值做成简单的局部平均再平均，则可能得到错误结果。

例如：

A 组有 2 个学生，平均分 90。

B 组有 8 个学生，平均分 60。

直接求两组平均：

\\[ (90+60)/2=75 \\]

但真实总体平均：

\\[ \frac{2\times90+8\times60}{10}=66 \\]

“所以如果要分布式计算平均值，可以先聚合 `(sum,count)`，最终再用 `sum/count`。”

国王恍然大悟。

“看来分布式计算，不只是把任务拆开。”

“还要确保拆开以后，计算结果依然正确。”

对于可结合的聚合操作，先在 Mapper 本地合并热点 Key 的大量记录，降低网络和 Reduce 输入的数据量。

第二种：热点 Key 加盐。

例如原本：

```
(product_1001, value)
```

可以在允许的聚合场景中拆成：

```
(product_1001_0, value)
(product_1001_1, value)
(product_1001_2, value)
```

第一阶段分别聚合。

第二阶段再合并回原始 `product_1001`。

“这样可以把热点 Key 的计算压力分散出去。”

“但要注意，添加随机后缀并不总是正确，尤其涉及 Join、去重或对顺序敏感的操作时，需要专门设计。”

第三种：自定义分区策略。

通过分析 Key 分布，让任务分配更加合理。

但国王必须记住：

“仅仅增加 Reducer 数量，并不能自动拆散同一个热点 Key。”

第四种：针对大表 Join 的专门优化。

例如在后续 Spark 篇中，我们还会介绍广播 Join、倾斜 Join 优化和自适应查询执行。

## 第十一幕：真正的分布式工程——数据本地性与 InputSplit

国王原以为一切已经结束。

突然，HDFS 指挥官提出了一个问题。

“陛下，假设一块 128 MiB 的数据在机器 A 上。”

“但我们的 Map 任务却被调度到了机器 B。”

“会发生什么？”

国王回答：

“机器 B 要从机器 A 读取数据。”

“没错。”

“如果上千个任务都需要跨网络读取大量数据，就可能产生可观的网络压力。”

“所以，Hadoop 引入了一个非常重要的设计思想。”

移动计算，尽量靠近数据，而不是总把大量数据搬向计算。

### 一、数据本地性

架构师解释：

“如果某个计算任务需要处理 HDFS 上的数据，调度器会尽可能利用数据位置信息，将计算安排在靠近数据的位置。”

常见情况包括：

- 节点本地：任务运行在持有所需数据的节点。
- 机架本地：任务运行在同一机架的其他节点。
- 非本地：任务需要通过更远的网络路径读取数据。

“当然，这不是绝对要求。”

“如果数据所在节点已经非常繁忙，调度器也需要考虑资源利用率和等待时间。”

### 二、Block 与 InputSplit 的区别

国王突然问：

“既然 HDFS 已经有 Block，为什么 MapReduce 还需要 InputSplit？”

架构师笑了。

“这是面试里非常容易混淆的概念。”

Block 是存储层概念。

它描述 HDFS 如何将文件划分为物理存储的数据块。

InputSplit 是计算层概念。

它描述一个 Map Task 需要处理的逻辑输入范围。

两者并不必然一一对应。

例如：

HDFS 把文件保存成若干 Block。

MapReduce 的 InputFormat 则决定如何生成 InputSplit。

RecordReader 再把 Split 中的数据解析为 Mapper 能处理的 Key-Value 记录。

“所以，一个 Mapper 通常对应一个 InputSplit，而不是严格地对应一个 HDFS Block。”

“如果文件由多行文本组成，InputSplit 的边界还可能落在一行中间，RecordReader 必须正确处理记录边界。”

国王终于理解。

“原来数据存储的切分方式，与计算任务的切分方式，并不是同一个概念。”

## 第十二幕：Java 工程师的试炼——亲手写一个 MapReduce

第二天，首席架构师召集了 Spring 王国的 Java 工程师。

### Mapper：把单词转换成键值对

```
public class WordCountMapper extends Mapper<
        LongWritable,
        Text,
        Text,
        IntWritable> {

    private static final IntWritable ONE =
            new IntWritable(1);

    private final Text word = new Text();

    @Override
    protected void map(
            LongWritable key,
            Text value,
            Context context
    ) throws IOException, InterruptedException {

        String[] words = value.toString()
                .split("\\s+");

        for (String w : words) {
            if (!w.isEmpty()) {
                word.set(w);
                context.write(word, ONE);
            }
        }
    }
}
```

国王看到了一些陌生类型。

“`LongWritable` 是什么？”

“为什么不用 Java 原生的 `Long`？”

工程师解释：

“Hadoop 提供了一套 Writable 类型，用于框架中的数据序列化和传输。”

例如：

- `IntWritable` 对应整数值。
- `LongWritable` 对应长整数值。
- `Text` 表示文本数据。

“Mapper 的输入 Key 通常由具体 InputFormat 和 RecordReader 决定。”

“对于常见 TextInputFormat，Key 通常是行在文件中的字节偏移量，Value 是一行文本。”

### Reducer：汇总相同单词的计数

```
public class WordCountReducer extends Reducer<
        Text,
        IntWritable,
        Text,
        IntWritable> {

    @Override
    protected void reduce(
            Text key,
            Iterable<IntWritable> values,
            Context context
    ) throws IOException, InterruptedException {

        int sum = 0;

        for (IntWritable value : values) {
            sum += value.get();
        }

        context.write(key, new IntWritable(sum));
    }
}
```

架构师点头。

“很不错。”

“对于 WordCount，我们还可以把这个 Reducer 用作 Combiner，因为计数求和支持安全的局部聚合。”

### Job：组织整个计算任务

```
Configuration conf = new Configuration();

Job job = Job.getInstance(conf, "word-count");

job.setJarByClass(WordCountApp.class);

job.setMapperClass(WordCountMapper.class);
job.setCombinerClass(WordCountReducer.class);
job.setReducerClass(WordCountReducer.class);

job.setOutputKeyClass(Text.class);
job.setOutputValueClass(IntWritable.class);

FileInputFormat.addInputPath(
    job,
    new Path("/input/logs")
);

FileOutputFormat.setOutputPath(
    job,
    new Path("/output/wordcount")
);

System.exit(job.waitForCompletion(true) ? 0 : 1);
```

“这样，我们就定义了输入、Mapper、Combiner、Reducer 与输出路径。”

“那 MapReduce 是不是比普通 Java Stream 强得多？”

架构师摇头。

“它们解决问题的范围不同。”

“Java Stream 主要是在一个 JVM 的执行环境中表达数据处理流水线。”

“Hadoop MapReduce 则可以协调多个节点完成分布式数据处理。”

“但如果数据只有几万条，单机 Java 程序就能快速处理，使用 Hadoop 可能反而带来不必要的调度和 I/O 开销。”

执行分区任务

简化示例：一个 Executor 可以在资源允许时并行运行多个 Task；Partition 与 Executor 不是永久一对一绑定关系。

“国王，RDD 是一个分布式数据集的逻辑抽象，而不是必须在创建时就把全部数据装进内存。”

### 二、Resilient：弹性与容错

国王问：

“如果一台 Executor 突然宕机，它负责的分区数据不就丢失了吗？”

Spark 微微一笑。

“RDD 的重要设计之一，是记录计算依赖关系。”

“这个关系叫作 Lineage。”

例如：

```
原始日志 RDD
     ↓ filter
有效日志 RDD
     ↓ map
用户金额 RDD
     ↓ reduceByKey
用户消费总额 RDD
```

“如果某个分区丢失，Spark 在满足条件时可以沿着依赖关系重新计算它。”

“这意味着，对于很多确定性计算，我们不必在每个步骤都立即把数据完整持久化。”

国王点头。

“这就是 Resilient。”

“是的。”

“但容错并不是免费的。如果依赖链很长，重新计算的代价也可能很大。”

“因此，我们还需要 Cache、Persist 和 Checkpoint。”

### 三、RDD 的不可变性

Spark 继续说道：

“还有一个关键特点。”

“RDD 不可变。”

国王问：

“那如何修改其中的数据？”

“我们不会原地修改 RDD。”

“而是通过 Transformation 生成新的 RDD。”

例如：

```
numbers = sc.parallelize([1, 2, 3, 4])doubled = numbers.map(lambda x: x * 2)
```

`numbers` 仍然表示原始数据集。

`doubled` 是新的 RDD。

“不可变设计让依赖追踪和失败后的重算更加容易组织。”

## 第三幕：Lazy Evaluation——国王下达命令，士兵却没有行动

第二天，国王决定亲自使用 Spark。

他写下一段 PySpark 代码。

```

```

国王等待了一会儿。

却没有看到他期待的计算输出。

他愤怒地问：

“我已经调用了 map 和 filter，为什么 Spark 没有立即完成整个任务？”

Spark 回答：

“陛下，因为它们是 Transformation。”

### 一、Transformation：描述计算

常见 RDD Transformation：

- `map`
- `filter`
- `flatMap`
- `mapPartitions`
- `reduceByKey`
- `join`
- `distinct`

“这些操作主要是在构建新的 RDD 及其依赖关系。”

“它们通常不会立即触发整个分布式作业执行。”

### 二、Action：触发计算

Spark 在代码后面补上一行：

```

```

这一次，计算开始执行。

输出：

```
[6, 8, 10]
```

Spark 说道：

“`collect()` 是 Action。”

“它会触发计算，并把结果收集到 Driver。”

“不过，如果结果巨大，直接 collect 可能把 Driver 内存撑爆。”

“这也是为什么生产环境中，不能随意对海量 RDD 使用 collect。”

国王若有所思。

“所以 map 和 filter 更像是制定作战计划。”

“Action 才是正式下达开战命令？”

“很形象。”

### 三、为什么要惰性执行？

“陛下，假设我们需要经过五步计算。”

“如果每一步都立即执行并物化结果，可能引入大量不必要的数据处理。”

“而惰性执行让 Spark 可以在触发 Action 时，根据依赖关系组织任务。”

“对于能够流水线执行的窄依赖操作，多个步骤可以合并在一个 Stage 内执行。”

“而在 DataFrame 与 Spark SQL 层面，Catalyst 还可以进一步优化逻辑执行计划。”

> 记忆：Transformation 构建计算关系，Action 触发实际计算。

## 第四幕：DAG 战争——Spark 如何指挥一千台机器？

Spark 在地上画出一幅作战地图。

“陛下，DAG 的全称是 Directed Acyclic Graph。”

“有向无环图。”

“您可以把它理解为一张带有方向、且不包含依赖环路的计算关系图。”

例如：

```
读取订单
    ↓
过滤有效订单
    ↓
提取 userId 和 amount
    ↓
按 userId 分组聚合
    ↓
按金额排序
    ↓
保存结果
```

“这条数据处理流水线并不是每一步都必须单独启动一轮全新的分布式作业。”

“Spark 会分析依赖，划分 Stage，再将 Stage 拆成 Task。”

### 一、Job、Stage、Task

架构师要求 Spark 用最简单的语言解释三个概念。

Spark 回答：

Job：通常由一个 Action 触发的计算作业。

Stage：根据计算依赖与 Shuffle 边界划分出的任务阶段。

Task：一个 Stage 内针对某个数据分区执行的最小调度工作单元。

例如：

```
Job：统计用户消费金额

Stage 0：
  Task 0 → Partition 0
  Task 1 → Partition 1
  Task 2 → Partition 2
  Task 3 → Partition 3

Shuffle

Stage 1：
  Task 0 → Partition 0
  Task 1 → Partition 1

结果输出
```

“陛下，多个 Task 可以被调度到不同 Executor 并行执行。”

“但 Stage 之间存在必要的依赖约束。”

### 二、窄依赖与宽依赖

国王问：

“究竟是什么决定了 Stage 如何拆分？”

Spark 答道：

“首先需要理解两种依赖。”

窄依赖（Narrow Dependency）

例如：

```
rdd.map(lambda x: x * 2)
```

通常一个子分区只依赖有限数量的父分区，不需要全局重新分配数据。

宽依赖（Wide Dependency）

例如：

```
pairs.reduceByKey(lambda a, b: a + b)
```

同一个 Key 的数据可能存在于多个父分区。

为了聚合，需要跨分区交换数据。

这种 Shuffle 依赖通常构成 Stage 边界。

### 窄依赖与宽依赖

窄依赖

每个子分区通常依赖少量父分区

宽依赖

子分区可能依赖多个父分区的数据

国王恍然大悟。

“所以 Shuffle 不仅昂贵，还会影响整个作业的阶段划分。”

“没错。”

“这也是 Spark 性能调优的重要切入点。”

## 第五幕：Cache 与 Persist——为什么内存不是越多越好？

Spark 帝国取得了第一次胜利。

但是第三天，监控平台突然报警。

“陛下！Executor 内存即将耗尽！”

国王愣住了。

“不是说 Spark 擅长内存计算吗？”

“为什么反而出现内存不足？”

Spark 回答：

“因为内存是有限的资源。”

“能够使用内存，不等于应该把所有数据全部放进内存。”

### 一、没有缓存时会发生什么？

假设我们有一批日志，需要进行两种分析。

```
logs = spark.read.parquet("/data/logs")valid = logs.filter("status = 200")count = valid.count()users = valid.select("user_id").distinct().count()
```

国王问：

“这里的 valid 不是已经生成了吗？”

“为什么第二次分析可能又要读取原始数据？”

Spark 解释：

“DataFrame 的执行也是惰性的。”

“如果没有缓存或其他可复用机制，多个 Action 可能重复计算相同的数据处理链。”

### 二、Cache：存储可复用的结果

Spark 增加了一行：

```
valid = logs.filter("status = 200").cache()valid.count()  # 首次执行，填充缓存valid.select("user_id").distinct().count()
```

“第一次 Action 触发计算并填充缓存。”

“后续 Action 有机会复用已经缓存的数据。”

“但缓存不是调用 `cache()` 后立即将所有数据完整加载进内存。”

“缓存数据也可能因为内存不足而被淘汰，或者根据持久化策略存储到磁盘。”

### 三、Persist：选择不同存储策略

Spark 展示几种常见策略。

| 策略                | 主要特点          |
| ----------------- | ------------- |
| `MEMORY_ONLY`     | 尽量在内存中保存      |
| `MEMORY_AND_DISK` | 内存不足时可使用磁盘    |
| `DISK_ONLY`       | 保存在磁盘         |
| `MEMORY_ONLY_2`   | 保留两个副本，提高容错能力 |

“具体支持哪些存储级别，以及默认行为，取决于 Spark API 和版本。”

“例如 PySpark RDD 与 DataFrame 的默认持久化行为不能不加区分地混为一谈。”&#x20;

国王问：

“那我把所有 DataFrame 都缓存，不就能加速了吗？”

Spark 摇头。

“完全不是。”

“缓存需要占用存储资源。”

“如果数据只使用一次，缓存可能没有收益，反而增加计算和内存压力。”

“如果缓存对象太多，还可能挤占 Shuffle 和执行内存。”

“所以真正需要缓存的，通常是计算代价高、预计会被反复使用的数据。”

### 四、Checkpoint：截断过长的依赖链

架构师又问：

“如果一个 RDD 的 Lineage 已经有几百层，发生故障后重新计算岂不是很昂贵？”

Spark 点头。

“这就需要考虑 Checkpoint。”

“Checkpoint 可以把数据物化到可靠存储，并使后续恢复不必一直追溯完整的上游依赖链。”

“它与 Cache 的主要目标并不相同。”

- Cache/Persist：重点是数据复用和性能。
- Checkpoint：重点是截断依赖、简化恢复路径。

“实际使用中，Checkpoint 同样有 I/O 成本，必须谨慎安排。”

### 一、Catalyst 的任务

Catalyst 是 Spark SQL 的查询优化框架。

它会参与解析 SQL、分析语义、优化逻辑计划和选择物理执行方案。

### Spark SQL 查询计划演化

SQL / DataFrame

### 二、谓词下推 Predicate Pushdown

“不过，具体能下推到什么程度，取决于数据源和表达式的支持情况。”

“不是所有 WHERE 条件都能完全下推。”

### 三、列裁剪 Column Pruning

国王又问：

Spark 回答：

“我们可以尝试只读取必要字段。”

Catalyst 主要负责查询计划优化。

## 第七幕：Join 之战——两张亿级表如何连接？

财政大臣又提出一道难题。

“陛下，我们有两张表。”

第一张：

`orders`

包含一亿条订单。

第二张：

`users`

包含一百万个用户。

“我们想将订单关联用户信息，再统计不同地区的销售额。”

SQL 如下：

```
SELECT
    u.city,
    SUM(o.amount)
FROM orders o
JOIN users u
    ON o.user_id = u.id
GROUP BY u.city;
```

国王问：

“Spark 会怎么执行 Join？”

架构师回答：

“主要取决于数据规模、Join 类型、数据分布、统计信息和配置。”

“我们先讨论两种典型策略。”

### 一、Broadcast Hash Join：把小表送到每一座城

假设一边的数据经过过滤和压缩后只有 5 MB。

而另一边有 100 GB。

Spark 可以考虑把小表广播给参与计算的 Executor。

“这样，大表不必仅仅为了这个 Join 而全部按照连接键重新洗牌。”

### Broadcast Join 简化结构

小表：用户维度数据

广播到执行节点

Executor 1

大表分区

小表副本

Executor 2

大表分区

小表副本

Executor 3

大表分区

小表副本

“但广播小表也消耗 Driver、网络和 Executor 内存资源。”

“如果小表并不小，强行广播可能造成内存压力甚至任务失败。”

### 二、Sort Merge Join：双方重新分区并排序

当两边数据都比较大，而且连接条件适合时，Spark 可能采用 Sort Merge Join。

典型过程：

双方根据 Join Key 进行 Shuffle。

相同 Key 被分配到对应分区。

各分区内进行排序。

然后执行归并连接。

“它通常适合较大规模的等值 Join。”

“但是 Shuffle、排序和数据倾斜都可能产生较高成本。”

### 三、AQE：战斗过程中调整策略

国王继续问：

“假设 Spark 在任务开始前估计 users 表有 100 MB。”

“但实际运行时，经过过滤只有 2 MB。”

“能不能临时改变计划？”

Spark 答道：

“这就是 AQE。”

AQE（Adaptive Query Execution），自适应查询执行。

它可以利用运行时获得的统计信息，对部分物理执行计划进行调整。

例如：

- 合并较小的 Shuffle 分区。
- 在适合时调整 Join 策略。
- 对支持的倾斜 Join 场景进行优化。

Spark 相关优化依赖准确的统计信息、运行时数据与具体配置；即使提供了 Join Hint，也不能保证所有情况下都采用指定策略。

## 第八幕：数据倾斜再现——最强大的计算军团，也无法逃脱热点

战争持续了数日。

Spark 帝国的计算节点大部分已经完成任务。

可最后一个 Task 却迟迟无法结束。

国王愤怒地问：

“我们不是已经有了 AQE 吗？”

Spark 回答：

### 一、热点 Key

假设平台有一千万条订单。

其中 30% 的订单属于同一个商家。

如果按照 `merchant_id` 分组：

```
df.groupBy("merchant_id").sum("amount")
```

这个热点商家可能让对应分区承担大量工作。

尤其是在 Join 等操作中，如果热点 Key 两侧都有大量记录，甚至可能产生远超输入规模的中间结果。

### 二、为什么增加分区数不一定有用？

国王说：

“那就把分区数量从 200 改成 2000！”

Spark 摇头。

“如果同一个 Key 按 Hash 规则始终进入一个分区，那么单纯增加分区数量并不能把它拆开。”

“不过，分区数量过少导致的普通负载不均衡，确实可能通过调整并行度改善。”

### 三、热点加盐

对于可拆分聚合，可以考虑把热点 Key 拆成多个子 Key。

例如：

```
merchant_1001_0
merchant_1001_1
merchant_1001_2
merchant_1001_3
```

第一阶段分别聚合。

第二阶段再合并到：

```
merchant_1001
```

“但加盐必须保持业务语义正确。”

“并不是所有 Join 都能简单加盐。”

“对于复杂场景，最好先借助 Spark UI 和执行计划确认倾斜位置，再设计优化策略。”

## 第九幕：OOM 之夜——为什么 128GB 内存仍然不够？

深夜。

Spark 帝国最昂贵的一台服务器突然发出警报。

```
java.lang.OutOfMemoryError:
Java heap space
```

国王震惊。

“我们给它配了 128GB 内存！”

“为什么还是 OOM？”

Spark 冷静地回答：

“陛下，机器物理内存、Executor 可用内存与某个 Task 真正能够使用的内存，并不是同一个概念。”

“而且 OOM 可能发生在不同位置。”

### 一、Driver OOM

例如：

```
all_orders = df.collect()
```

如果结果集非常大，全部收集到 Driver，就可能导致 Driver 内存不足。

### 二、Executor OOM

常见原因：

- 单个分区过大。
- Shuffle 聚合数据结构占用大量内存。
- 广播表过大。
- 缓存过多。
- 用户自定义函数创建大量对象。
- 数据倾斜导致少数 Task 负载过高。

### 三、容器内存超限

“陛下，Spark 还可能因为堆外内存、Python Worker 内存等消耗，使整个容器超过资源限制。”

“这类故障未必会表现为 Java heap space。”

“有时任务会因 Container 被资源管理器终止而失败。”

### 四、正确排查流程

架构师制定了一套排查方案。

首先定位故障发生在 Driver 还是 Executor。

然后检查 Spark UI 中的 Stage、Task、Shuffle Read、Shuffle Write、Spill、GC、失败原因等指标。

接着排查是否存在数据倾斜、异常大分区、错误广播或不合理缓存。

最后再决定是否调整分区、Join 策略、缓存方案以及资源配置。

“陛下，第一反应不应该永远是增加内存。”

“增加内存有时只是掩盖根本问题。”

## 第十幕：真正的工程实践——用 Spark 统计一亿条订单

国王终于提出一个现实问题。

“我们学了这么多原理。”

“现在，如果真的有一亿条订单，究竟应该怎么做？”

架构师拿出一份 PySpark 程序。

### 第一步：读取 Parquet 数据

```
from pyspark.sql import SparkSessionfrom pyspark.sql.functions import (    col, sum as spark_sum, count)spark = SparkSession.builder \    .appName("OrderAnalytics") \    .getOrCreate()orders = spark.read.parquet("/data/orders")
```

“这里使用 Parquet，而不是直接在 Driver 中读取一亿条记录构造成 List。”

“Parquet 是列式文件格式，比较适合许多批量分析任务。”

### 第二步：过滤有效订单

```
valid_orders = orders.filter(    (col("status") == "PAID") &    (col("amount") > 0))
```

“这里的过滤操作不会立即触发整个计算。”

### 第三步：按用户聚合

```
user_stats = valid_orders.groupBy("user_id").agg(    spark_sum("amount").alias("total_amount"),    count("*").alias("order_count"))
```

“这里涉及按照 user_id 分组。”

“通常会产生需要关注的 Shuffle。”

### 第四步：写入结果

```
user_stats.write \    .mode("overwrite") \    .parquet("/output/user_stats")

## 第三幕：Consumer Group——为什么增加消费者不一定提升吞吐量？

国王问：

“如果仍然只有三个 Partition，在同一个普通消费组中，不能让十个消费者分别独占十个不同分区来并行读取。”

“通常最多只有三个消费者能获得这些分区，其余消费者可能空闲。”

### 一、Consumer Group 的基本规律

同一个 Consumer Group 中，一个 Partition 在同一时刻由一个组成员负责消费。

但不同 Consumer Group 可以独立读取同一 Topic。

例如：

```
payment-events
    │
    ├── Group A：实时 GMV 统计
    │
    ├── Group B：风控分析
    │
    └── Group C：数据仓库同步
```

“这样，实时统计和风控可以分别维护自己的进度。”

“谁快谁慢，不必使用同一个消费位置。”

国王问：

“它负责的 Partition 怎么办？”

“Consumer Group 会根据成员变化等情况重新分配 Partition。”

“这叫 Rebalance。”

“但 Rebalance 不是免费的。”

“它可能造成短暂的消费中断、分区所有权转移，以及状态恢复等开销。”

“而且如果业务提交 Offset 与实际处理结果的时机不正确，就可能出现重复处理或者丢失处理结果。”

### 三、Offset 提交的陷阱

第一条：

```

   ↓
处理业务
   ↓
程序崩溃
```

“如果 Offset 已经提交，但业务处理失败，恢复时可能跳过该事件。”

第二条：

```
读取消息
   ↓
处理业务
   ↓

```

“这种顺序可以支持常见的至少一次处理设计。”

## 第四幕：Leader、Follower 与 ISR——Kafka 如何应对 Broker 宕机？

当天夜里。

一台 Kafka Broker 突然失去连接。

国王猛地站起。

“消息丢了吗？”

Kafka 回答：

“陛下，我们通常可以通过副本机制增强可用性与持久性。”

### 一、Leader 与 Follower

对于一个 Partition，可以设置多个副本。

例如副本因子为 3：

```
Partition 0

Broker A：Leader
Broker B：Follower
Broker C：Follower
```

Leader 负责该分区的常规读写请求。

Follower 从 Leader 复制日志数据。

### 二、ISR 是什么？

Kafka 解释：

“ISR 是 In-Sync Replicas，表示被视为保持同步状态的副本集合。”

“发生 Leader 故障时，Kafka 可以从符合要求的副本中选举新的 Leader。”

国王问：

“只要副本因子为 3，就绝对不会丢消息吗？”

“不。”

“还需要考虑 Producer 的确认策略、最小同步副本要求、副本同步状态、Leader 选举策略以及底层持久化故障。”

### 三、三个重要参数

```
acks=all
enable.idempotence=true
retries=2147483647
```

“`acks=all` 表示 Producer 要求 Leader 在满足其确认语义后再确认写入。”

“`enable.idempotence=true` 可以避免生产者在支持的条件下因重试导致的重复写入。”

“但幂等 Producer 不等于业务级事件永远不重复。”

“如果业务应用自己产生了两次相同事件，Kafka Producer 不会凭空知道这是同一次订单支付。”

Broker 端还需要合理配置：

```
min.insync.replicas=2
```

“例如副本因子为 3、最小同步副本为 2，并配合 `acks=all`，可以避免只剩一个同步副本时仍按正常方式接受这类写入。”

“代价是可用性与持久性之间需要权衡。”

国王终于理解。

副本因子决定数据复制份数的目标，确认和同步策略决定某些故障情况下如何接受写入；它们共同影响可靠性。

## 第六幕：时间之争——一笔迟到的订单

晚上八点零五分。

直播大屏统计出：

```
20:00—20:05
成交金额：100000 元
```

国王十分满意。

然而几秒后，一条支付事件到达 Flink。

```
{
  "orderId": 9527,
  "amount": 500,
  "eventTime": "20:04:58"
}
```

国王疑惑：

“现在已经是 20:05:08。”

“为什么这笔订单的时间却是 20:04:58？”

架构师回答：

“因为事件发生时间和事件到达计算系统的时间，不一定相同。”

“网络延迟、消息积压、生产者缓冲和重试，都可能造成数据晚到。”

### 一、Processing Time：处理时间

指的是计算算子处理事件时，所在机器的系统时间。

例如：

订单真正支付时间：20:04:58。

事件到达 Flink：20:05:08。

如果按照 Processing Time 统计，它会被归入 20:05 之后的窗口。

### 二、Event Time：事件时间

指业务事件本身携带的发生时间。

如果按照 Event Time 统计，上面的订单应属于：

`20:00—20:05`

“陛下，Event Time 更适合许多需要按照真实业务发生时刻进行归属的分析。”

“但代价是，我们需要处理乱序和迟到。”

### 三、Watermark：时间推进的公告

Flink 统帅取出一份告示。

“我需要一种机制，帮助计算算子判断事件时间已经推进到了哪里。”

“这就是 Watermark。”

假设目前观察到的最大事件时间为：

`20:05:10`

我们采用最多容忍 10 秒乱序的策略。

那么可以近似理解为：

```
当前最大事件时间：20:05:10

Watermark：约 20:05:00
```

这表示系统认为事件时间已经推进到相应位置，可以触发符合条件的事件时间计算。

但 Watermark 并不能保证现实世界中再也不会出现更早的事件。

## 第七幕：窗口王国——无穷的数据流如何划分计算范围？

### 一、滚动窗口 Tumbling Window

假设窗口长度为五分钟。

- 在允许的范围内保留窗口状态，接纳部分迟到事件并重新输出结果。
- 将超过允许迟到范围的事件分流到侧输出流，单独补偿。

## 第八幕：State——为什么 Flink 能记住过去？

直播运营总监又提出了一个要求。

“我们需要判断每个用户在一分钟内是否连续支付失败三次。”

国王问：

“这不是检查当前事件就可以了吗？”

Flink 回答：

“不行。”

“单条事件无法告诉我们用户过去一分钟已经失败过多少次。”

“我们需要记住之前发生的事情。”

“这就是 State，状态。”

### 一、无状态计算

例如：

```
金额 100 → 乘以汇率 → 金额 110
```

只依赖当前输入。

不需要知道之前的数据。

### 二、有状态计算

例如：

```
用户 A：失败一次
用户 A：失败两次
用户 A：失败三次 → 触发风控
```

必须保存之前的计数和相关时间信息。

“这就是有状态计算。”

### 三、Keyed State

Flink 可以通过 `keyBy(userId)`，使相同用户的事件进入对应的键控逻辑分区。

每个 Key 可以维护自己的状态。

例如：

```
user_1001 → failCount = 2
user_1002 → failCount = 0
user_1003 → failCount = 1
```

常见状态抽象包括：

`ValueState`、`ListState`、`MapState`、`ReducingState` 等。

“如果用户有一亿个，状态不会撑爆内存吗？”

Flink 点头。

“这是一个真实的问题。”

“因此，状态规模、状态后端、TTL、状态清理，以及 Checkpoint 成本，都是重要的工程设计因素。”

“一些状态后端能够结合磁盘和内存管理大型状态，但不会让存储和恢复成本凭空消失。”&#x20;

## 第九幕：Checkpoint——计算到一半，机器突然宕机

晚上九点。

系统运行正常。

国王脸色大变。

“用户计数状态是不是全部丢失了？”

“如果数据从头重新处理，成交额不会重复统计吗？”

Flink 统帅却没有慌张。

“陛下，这就是 Checkpoint 发挥作用的时候。”

### 一、Checkpoint 的基本思想

“我们定期为流式作业创建一致性状态快照。”

“其中不仅包括算子状态，还需要协调可恢复数据源的读取位置。”

例如：

```
Checkpoint 100：
  Kafka Partition 0 → 对应消费位置
  Kafka Partition 1 → 对应消费位置
  用户 A 状态 → 100 元
  用户 B 状态 → 300 元
```

“当计算任务失败时，我们可以从最近一个成功完成的 Checkpoint 恢复状态和输入进度。”

“之后重新处理尚未包含在恢复快照中的事件。”

### 二、Checkpoint Barrier

国王问：

“多台机器同时处理数据，怎样保证快照逻辑上一致？”

Flink 回答：

“Checkpoint Barrier 是协调分布式快照的重要机制。”

“它会随数据流经过相关算子。”

“在多输入场景中，需要保证快照所记录的状态与输入进度处于一致的切面。”

“框架可以采用对齐或在支持条件下采用非对齐 Checkpoint 等方式处理。”

“这一机制受到分布式快照思想的影响。”

### Flink Checkpoint 与故障恢复

Kafka 事件流

Flink Operators

持续处理事件、更新 State

Checkpoint 100

可靠保存状态与进度

任务故障

恢复 Checkpoint + 重放后续事件

Flink 说道：

“只要输入源支持恢复和重放，状态快照一致，且恢复所需数据仍然可用，就可以实现作业状态的 Exactly-Once 一致性语义。”

“但是，陛下，这还不意味着所有外部系统都天然 Exactly-Once。”

Flink 官方对 Checkpoint、一致性和恢复的说明也明确区分了状态一致性与外部 Sink 的端到端保证。

### 三、Checkpoint 与 Savepoint

国王问：

“Checkpoint 和 Savepoint 是不是一样？”

“它们都涉及状态快照，但用途不同。”

|      | Checkpoint | Savepoint    |
| ---- | ---------- | ------------ |
| 主要目的 | 运行时容错恢复    | 有计划的停止、迁移、升级 |
| 触发方式 | 通常周期性自动触发  | 通常由用户或运维操作触发 |
| 生命周期 | 通常由运行时管理   | 通常由用户管理      |
| 典型用途 | 故障恢复       | 应用发布、版本迁移    |

“实际版本中还存在保留 Checkpoint 等机制，所以不能简单认为 Checkpoint 永远会在任务停止后被删除。”

## 第十幕：Exactly-Once——究竟是什么只执行一次？

国王拿出一份报告。

上面写着：

“本系统保证 Exactly-Once。”

架构师看了一眼，皱起眉头。

“陛下，这句话不够精确。”

“必须问清楚：到底是哪一部分保证 Exactly-Once？”

### 一、三种处理语义

At-Most-Once：最多处理一次，可能因为故障而丢失处理。

At-Least-Once：至少处理一次，发生恢复或重试时可能重复处理。

Exactly-Once：从定义好的系统边界观察，处理结果与恰好执行一次具有等价效果。

“注意，Exactly-Once 不意味着 CPU 上的某段代码物理上只运行了一次。”

“失败重试过程中，同一个事件的计算逻辑可能执行不止一次。”

“关键在于最终可观察结果是否重复产生副作用。”

### 二、Flink 内部状态一致性

假设用户的支付金额是 100 元。

Flink 处理事件后，内部聚合状态增加 100 元。

但任务在下一次 Checkpoint 完成前崩溃。

恢复时，Flink 回到此前的状态，并重放输入事件。

“如果恢复机制配置正确，就不会因为这次重放而让内部状态永久多加一次。”

### 三、外部数据库的难题

国王问：

“那如果已经把统计结果写进 MySQL，崩溃后又写一次呢？”

架构师说道：

“这取决于 Sink 的语义。”

例如：

```
UPDATE live_gmv
SET amount = amount + 100
WHERE room_id = 1001;
```

如果同一个事件重复执行，就可能多加 100 元。

而如果写入的是某个窗口版本的确定性聚合结果：

```
INSERT INTO live_gmv (
    room_id, window_start, amount
)
VALUES (1001, '2027-01-01 20:00:00', 5000)
ON DUPLICATE KEY UPDATE
    amount = VALUES(amount);
```

重复写入相同结果通常不会产生重复累加。

“当然，若迟到事件导致窗口金额发生合法修正，我们仍需要处理结果版本和乱序覆盖问题。”

“如果外部系统和连接器支持合适的事务协议，也可以采用更强的协调机制。”

“但不能因为开启了 Flink Checkpoint，就宣称任意数据库写入天然端到端 Exactly-Once。”

### 三、Spring Boot 业务事务

示意代码：

@Transactional
public void confirmPayment(PaymentResult result) {
    int updated = orderMapper.markPaidIfUnpaid(
        result.orderId(),
        result.paymentId()
    );

    if (updated == 0) {
        return;
    }

    outboxMapper.insert(
        PaymentEvent.from(result)
    );
}
```

“这里假设支付结果已经经过可信渠道验证，`markPaidIfUnpaid` 是条件更新，而且只有实际完成状态转换时才写出事件。”

“如果发布失败，可以重试。”

“而为了处理发布成功但尚未标记 Outbox 已发送就崩溃的情况，下游还必须具备去重能力。”

### 四、Flink SQL 计算五分钟 GMV

Flink 可以使用 SQL 描述实时计算。

先假设系统已经通过 Kafka Connector 建立了包含 `order_id`、`room_id`、`amount` 和事件时间列的可信事件表，并且上游具有明确的去重语义。

下面是窗口聚合的核心 SQL：

```
SELECT
    room_id,
    window_start,
    window_end,
    SUM(amount) AS gmv
FROM TABLE(
    TUMBLE(
        TABLE payment_events,
        DESCRIPTOR(event_time),
        INTERVAL '5' MINUTES
    )
)
WHERE status = 'PAID'
GROUP BY
    room_id,
    window_start,
    window_end;
```

架构师提醒：

“这是聚合核心逻辑，不是完整的可直接部署脚本。”

“实际需要定义 Kafka Source、Watermark、序列化格式、Sink、Checkpoint 和恢复策略。”

“尤其要注意，同一笔支付如果存在重复事件，在聚合之前需要可靠去重，否则金额仍然可能被重复累计。”

“此外，如果业务使用 UTC 事件时间，但报表要求北京时间自然分钟边界，就必须明确时间类型与时区配置。”

## 第二幕：背压——为什么下游堵塞会向上游传染？

架构师带领国王来到 Flink 数据河道。

这里有四座处理工厂。

```
Kafka Source
      ↓
数据解析
      ↓
窗口聚合
      ↓
ClickHouse Sink
```

每座工厂通过有限容量的数据通道连接。

架构师说道：

“假设 Kafka 每秒产生 10 万条事件。”

“数据解析工厂每秒能处理 12 万条。”

“窗口聚合工厂每秒可以处理 11 万条。”

“可是 ClickHouse Sink 每秒只能写入 3 万条。”

国王问：

“那多出来的七万条数据去哪了？”

“先进入缓冲区。”

“缓冲区满了之后，Sink 的上游无法继续以原来的速度发送数据。”

“窗口聚合工厂开始受到阻塞。”

“随后，数据解析工厂也开始受影响。”

“最终，Kafka Source 的读取速度也可能下降。”

“这就是背压传播。”

### 一、背压的本质

背压（Backpressure）是一种流量控制现象：当下游无法及时接收数据时，压力通过处理链路向上游传播，避免无限制地向有限缓冲区写入。

### 背压传播过程

Kafka Source

读取速度被迫下降

Parse

输出缓冲逐渐填满

Window Aggregate

等待下游释放空间

ClickHouse Sink

真正的处理瓶颈

示意：数据向下流动，阻塞压力可能向上游传播。实际 Flink 网络交换、算子链和背压状态会因执行拓扑而不同。

国王恍然大悟。

“也就是说，Kafka Lag 增长，未必是 Kafka 本身出了问题？”

“正是。”

“Source 因下游背压而减少读取，也会造成 Kafka 消费进度落后。”

### 二、背压与消息积压的区别

架构师写下两个词。

Backpressure：处理链路中的流量反向约束。

Consumer Lag：消费者读取或处理进度相对于日志末端的落后程度。

“两者有关联，但不是同一回事。”

“背压是一种机制或运行状态，Lag 是一个可观测的积压指标。”

“Kafka Lag 增长可能由 Flink 背压造成，也可能由消费者停止、Source 分配异常、Kafka 读取受限等原因造成。”

### 三、为什么背压不一定是坏事？

国王问：

“既然背压会让系统变慢，为什么不把它彻底删除？”

架构师回答：

“如果没有背压，而下游处理速度一直低于上游输入速度，中间缓冲可能不断增长。”

“最终，系统可能因内存耗尽而崩溃。”

“所以背压本身是保护机制。”

“需要解决的是持续过载的根本原因，而不是盲目取消背压。”

### 二、增加 Partition 就能解决吗？

国王立即提出建议：

“现在有 32 个 Partition，我们改成 128 个！”

Kafka 统帅回答：

“陛下，如果瓶颈来自分区数量限制并行度，增加 Partition 可能有效。”

“但是需要区分三种情况。”

第一种：消费组并行度被 Partition 数量限制。

例如只有 8 个 Partition，配置 32 个 Source Reader，也无法通过普通分区分配方式让全部 Reader 分别负责不同分区。

第二种：Flink 算子计算资源不足。

可以考虑增加并行度和资源，但需要确认 CPU、内存、网络和数据倾斜情况。

第三种：下游 Sink 是瓶颈。

此时增加 Kafka Partition 可能毫无帮助。

“而且，扩展 Topic 分区数后，相同 Key 的默认分区映射可能发生变化。”

“所以增加 Partition 并不是一个完全没有副作用的操作。”

国王终于放弃了盲目扩容。

## 第四幕：Flink 指挥体系——JobManager、TaskManager 与 Slot

架构师将国王带到了 Flink 军团总部。

“陛下，要排查 Flink 性能问题，您必须先弄清楚它的运行结构。”

### 一、JobManager：总指挥部

JobManager 负责协调 Flink 作业运行。

其中包括作业调度、故障恢复与 Checkpoint 协调等职责。

实际部署中可能涉及多个 JobManager 相关组件与高可用机制。

### 二、TaskManager：执行节点

TaskManager 负责真正执行任务。

一个 TaskManager 通常可以提供多个 Task Slot。

国王问：

“一个 TaskManager 就等于一台物理服务器吗？”

“不一定。”

“它是一个执行进程或运行组件，可以按部署方式与资源配置映射到不同机器或容器。”

### 三、Slot：资源分配单位

“Slot 是 Flink 用于隔离和分配任务资源的重要抽象。”

“但陛下，不要把一个 Slot 机械理解成一个 CPU 核心。”

“多个 Slot 通常共享 TaskManager 的一些底层资源，而具体 CPU、内存和调度资源保障取决于部署配置。”

### 四、Operator Chain：将算子连接执行

考虑下面的数据流：

Flink 可能把满足条件的相邻算子组成 Operator Chain。

“这样可以降低算子间部分序列化、网络交换和调度开销。”

“但不是所有算子都能链在一起。”

“例如 `keyBy` 引入的数据重新分区通常会形成交换边界。”

“并行度决定一个算子同时可以有多少个并行实例。”

“Slot 决定框架如何安排相应资源。”

“TaskManager 提供执行环境。”

“不能把三者简单画等号。”

## 第五幕：Checkpoint 风暴——为什么快照越来越慢？

帝国完成第一轮排查后，监控官又报告：

“陛下！Flink Checkpoint 原本只需要 8 秒，现在已经增长到 95 秒！”

“有些 Checkpoint 甚至直接超时！”

国王问：

“是不是状态数据太大？”

架构师回答：

“有可能。”

“但 Checkpoint 变慢，至少需要区分三类问题。”

### 一、Barrier 传播和对齐耗时

“第一类，是 Barrier 难以通过拥堵的数据通道。”

在传统的对齐 Checkpoint 中，多输入算子需要协调来自不同输入通道的 Checkpoint Barrier。

假设算子有两个输入。

```
输入 A：Barrier 100 已到达

输入 B：仍然有大量数据积压
        Barrier 100 迟迟没有到达
```

“为了取得一致性切面，已经收到 Barrier 的输入可能需要暂时停止继续消费其后的相关数据，等待其他输入。”

“如果背压严重，这种等待就可能明显增加。”

### 二、状态快照耗时

第二类，是状态数据本身太大。

假设 Flink 维护着五千万用户的状态。

每个用户都有多种统计信息。

总状态规模达到数百 GB。

“创建、组织并持久化状态快照，需要消耗 CPU、磁盘和网络等资源。”

“如果 Checkpoint 存储系统吞吐不足，也会明显拖慢整个过程。”

### 三、异步持久化耗时

第三类，是写入远端 Checkpoint 存储非常慢。

例如：

- 对象存储响应变慢。
- 网络吞吐不足。
- 后端存储频繁限流。
- 单次需要上传的数据量过大。

架构师说道：

“所以，我们应分别观察 Checkpoint 的开始延迟、对齐时间、同步阶段、异步阶段和整体完成时间。”

“如果不区分是哪一段慢，直接调整超时时间，只能暂时掩盖问题。”

Flink 官方的 Checkpoint 调优文档也强调，应将持续背压、Barrier 对齐、状态快照和存储开销分别分析。

### 四、Unaligned Checkpoint：让 Barrier 穿过拥堵河道

国王问：

“如果 Barrier 总是被缓冲区中的数据阻挡，能不能让它更快通过？”

架构师说道：

“这就是 Unaligned Checkpoint 的重要思路。”

“它允许把部分正在传输的数据也纳入 Checkpoint 状态，从而降低严重背压场景下等待 Barrier 对齐造成的耗时。”

传统对齐方式：

```
等待相关输入 Barrier
        ↓
完成一致性快照
        ↓
恢复正常处理
```

非对齐方式：

```
记录算子状态
      +
记录必要的在途数据
        ↓
构成可恢复的一致性快照
```

“但是，陛下，Unaligned Checkpoint 并不能消除背压。”

“它还可能增加 Checkpoint 数据量、存储 I/O 和恢复开销。”

“如果真正瓶颈是 Checkpoint 存储写入太慢，开启 Unaligned 甚至可能让情况更糟。”

“所以它是特定问题的优化手段，不是万能开关。”&#x20;

## 第六幕：RocksDB 地下城——一亿用户的状态存在哪里？

第二天，国王发现 Flink 的某个任务维护了海量用户状态。

他问：

“这些状态全部放在 Java 堆内存中吗？”

架构师回答：

“不一定。”

“Flink 可以采用不同状态后端管理状态。”

### 一、HashMapStateBackend

架构师带国王来到一座速度极快的档案馆。

这里所有常用档案都直接放在管理员触手可及的位置。

“HashMapStateBackend 在 JVM 堆中管理工作状态。”

“它的状态访问通常比较直接。”

“但是状态规模受 JVM 堆内存及其他运行资源约束。”

“如果状态特别大，可能带来较高的 GC 压力和内存风险。”

### 二、EmbeddedRocksDBStateBackend

接着，他们来到一座巨大的地下城。

无数档案存放在分层的存储结构中。

“EmbeddedRocksDBStateBackend 使用嵌入式 RocksDB 管理键控状态。”

“状态可以利用本地磁盘与内存资源，适合很多大状态场景。”

“但访问可能涉及序列化、原生内存、缓存和磁盘 I/O，性能特征与纯堆内状态不同。”

“对于特定场景，RocksDB 还可以使用增量 Checkpoint，减少需要重复上传的状态数据。”

### 两种常见状态后端的权衡

| 维度            | HashMap          | RocksDB           |
| ------------- | ---------------- | ----------------- |
| 工作状态位置        | JVM Heap         | 本地 RocksDB        |
| 单次访问开销        | 通常较低             | 通常较高              |
| 大规模状态         | 受 Heap 约束明显      | 更适合较大状态           |
| GC 压力         | 可能较高             | 状态不主要占据 Java Heap |
| 增量 Checkpoint | 不采用 RocksDB 增量机制 | 支持相关机制            |

架构师提醒：

“状态后端不等于 Checkpoint 持久化位置。”

“状态后端负责如何管理工作状态，Checkpoint 存储负责快照最终可靠保存在何处。”

“即使使用 RocksDB，也需要考虑本地磁盘空间、远端 Checkpoint 存储、恢复时间和状态 TTL。”&#x20;

“那是不是 RocksDB 一定比 HashMap 更好？”

“不。”

“如果状态规模很小，又对状态访问延迟十分敏感，堆内状态可能是更简单、更合适的选择。”

## 第七幕：超级直播间——为什么增加一百倍并行度也没用？

战争来到最艰难的一天。

监控官报告：

“陛下！我们已经将 Flink 的计算资源增加了一倍。”

“可还有一个 Task 的 CPU 达到 100%，其他 Task 却非常空闲！”

架构师立刻要求查看 Key 分布。

结果令人震惊。

全平台存在几万个直播间。

其中一个超级直播间独占 60% 的交易事件。

而实时计算代码是：

```
stream
    .keyBy(PaymentEvent::roomId)
    .process(new RoomGmvProcessFunction());
```

国王问：

“这有什么问题？”

架构师解释：

“`keyBy(roomId)` 会使同一个直播间的事件被路由到同一个 Keyed Operator 并行实例。”

“即使我们将并行度从 32 扩容到 128，单个超级直播间的同一个 Key 仍不会因此自动分散到 128 个实例。”

“那个热点 Task 仍然可能成为瓶颈。”

### 一、不能直接随机分散吗？

国王问：

“那我们直接随机把这个直播间的事件分成一百份！”

“如果业务是可以结合的求和统计，可以这样设计。”

“但需要两阶段聚合，才能保证结果正确。”

### 二、两阶段聚合

原始事件：

```
room_1001
room_1001
room_1001
...
```

先对热点直播间添加子 Key：

```
room_1001_00
room_1001_01
room_1001_02
...
room_1001_31
```

第一阶段：

各子 Key 并行计算局部成交金额。

第二阶段：

将所有子 Key 的局部结果聚合到真正的直播间 ID。

### 热点直播间的两阶段聚合

超级直播间：room_1001

每秒 60,000 条事件

子 Key 0

局部聚合

子 Key 1

局部聚合

子 Key 2

局部聚合

子 Key 3

局部聚合

第二阶段聚合

合并局部结果，得到真实 GMV

国王问：

“这样是不是能无限扩展？”

架构师摇头。

“不是。”

“第二阶段仍然需要合并结果。”

“如果局部聚合每收到一条事件就输出一次，第二阶段依然可能面对大量更新。”

“正确做法通常要控制局部聚合的输出频率，设计增量汇总机制，并明确窗口和结果版本语义。”

“此外，去重必须在正确的业务层次完成。”

“如果原始支付事件重复，简单随机加盐后两条重复事件可能进入不同子 Key，造成重复累计。”

“这也说明，热点拆分不仅是性能优化，更需要正确性设计。”

## 第八幕：扩容之战——Flink 如何重新分配一亿个用户状态？

经过热点拆分，帝国终于稳定下来。

但是，国王又提出一个问题。

“假设我们的 Flink 作业当前并行度为 32。”

“现在我要扩容到 128。”

“那些已经计算出来的用户状态怎么办？”

架构师解释：

“这就涉及 Flink 的状态重分配。”

### 一、为什么不能简单地重启？

假设有一亿个用户，每个用户都维护消费累计值。

如果不恢复原有状态，直接启动一套空白作业，就可能丢失历史累计信息。

“所以我们通常需要从兼容的 Checkpoint 或 Savepoint 恢复。”

### 二、Key Group：状态迁移的基本单元

Flink 对 Keyed State 的分配并不只是简单地把每个 Key 随机交给 Task。

它使用 Key Group 组织键控状态。

“Key Group 是 Flink 对 Keyed State 进行重新分配的重要基本单元。”

“Key Group 数量与算子的最大并行度相关。”

例如：

```
最大并行度：128
当前并行度：4

Task 0 → Key Group 0—31
Task 1 → Key Group 32—63
Task 2 → Key Group 64—95
Task 3 → Key Group 96—127
```

扩容至 8 个并行实例时，可重新分配为：

```
Task 0 → Key Group 0—15
Task 1 → Key Group 16—31
...
Task 7 → Key Group 112—127
```

“这样，Flink 能够按照 Key Group 重新分配状态，而不是让每个业务用户自己负责迁移。”

Flink 的官方状态模型明确说明了 Key Group 与并行度调整之间的关系。

### 三、Savepoint 发布流程

### 一、阻塞式线程模型的局限

考虑一个极简的阻塞式服务器。

```
Socket socket = serverSocket.accept();

InputStream in = socket.getInputStream();

int data = in.read();
```

当线程执行阻塞读取时，如果没有数据到达，线程可能处于等待状态。

如果采用一个连接长期绑定一个平台线程的简单模型，连接数上升会造成大量线程资源占用。

“但现代高并发网络服务器通常不会如此直接地为每条连接永久分配一个线程。”

### 二、NIO 与事件循环

架构师带国王来到 Netty 军团。

“陛下，NIO 可以利用非阻塞通道、Selector 等机制管理多个连接。”

“一个事件循环线程可以关注许多 Channel 的 I/O 事件。”

当某条连接变为可读时，框架调用相应处理逻辑。

当某条连接暂时没有事件时，不需要为它一直占用一个专属执行线程。

### 事件驱动长连接模型

大量客户端连接

Netty EventLoop

监听 Channel 的读写与其他相关事件

连接 A

连接 B

连接 C

示意：实际 Netty 通常拥有多个 EventLoop 线程，并将 Channel 分配给相应 EventLoop。

国王问：

“这样就能随意管理一百万条连接？”

“仍然不能。”

“每条 TCP 连接都需要一定的内核和应用资源。”

“WebSocket 连接还会涉及协议状态、缓冲区、心跳、认证状态等开销。”

“文件描述符上限、内核参数、网络带宽、TLS 成本、连接分布和消息发送速率都需要评估。”

### 三、WebSocket 与 SSE 怎么选？

架构师拿出两份协议卷宗。

| 比较    | WebSocket       | SSE                  |
| ----- | --------------- | -------------------- |
| 通信方向  | 双向              | 服务器到客户端单向            |
| 典型用途  | 聊天、弹幕、实时互动      | 通知、状态更新、AI 流式输出      |
| 浏览器支持 | WebSocket API   | EventSource API      |
| 底层模型  | 建立 WebSocket 连接 | HTTP 响应持续推送          |
| 断线恢复  | 需要自行设计协议细节      | EventSource 支持自动重连机制 |

“如果直播间既需要用户持续发送弹幕，又需要服务器推送互动消息，WebSocket 通常比较自然。”

“如果只是把最新 GMV 或 AI 生成内容单向推送到客户端，SSE 也可能非常合适。”

“但无论哪种，都需要考虑心跳或保活策略、断线重连、消息序号和慢客户端处理。”

### 四、一百万连接到底需要多少内存？

架构师提出一个假设。

“如果我们粗略地假设，每个在线连接平均占用 20 KiB 的某类应用与连接管理资源。”

一百万连接：

\\[ 1000000\times20\text{ KiB}\approx19.1\text{ GiB} \\]

“这只是非常简化的容量示例。”

“真实内存还包括 JVM 堆、直接内存、Socket Buffer、TLS 状态和其他系统开销。”

“不同协议栈、内核配置和业务代码下，每连接内存占用可能差异很大。”

“所以连接密度必须通过压测测量，而不是完全依靠公式猜测。”

### 二、消息广播成本

架构师拿出一份新的计算。

“假设一条弹幕经过协议封装后，平均向每个观看用户发送 200 字节。”

“如果向一百万名观众各发送一份：”

\\[ 1000000\times200=200000000\text{ B} \\]

“约为 200 MB 的应用层消息数据，不计额外协议和网络开销。”

“如果这个直播间每秒有 100 条需要全员广播的弹幕呢？”

\\[ 200\text{ MB}\times100=20\text{ GB/s} \\]

国王脸色一变。

“每秒要发送二十 GB？”

“在这些假设下，是的。”

“而实际网络传输还会有额外开销。”

“这说明，用户可以发送 100 条弹幕，不代表系统应该把 100 条弹幕原样展示给所有在线观众。”

### 三、消息分级

架构师划分了三种消息。

强业务消息：支付状态、重要账户通知等，需要明确的可靠性与业务确认机制。

普通互动消息：弹幕、点赞、入场提示，可以按照产品要求采取批量、限频、采样、合并与优先级控制。

实时统计消息：例如在线人数、点赞总数和 GMV，可以定期推送最新快照，不必把每次计数变化都单独发送给所有用户。

“对于点赞数量，我们完全可以每隔一定时间汇总，再推送最新结果。”

“对于超级热门直播间的弹幕，还需要考虑展示节流、房间级限流及用户端承载能力。”

### 四、慢客户端问题

国王问：

“如果用户网络特别慢，服务器不停推送消息，会怎么样？”

架构师回答：

“如果无限制地往每条连接的发送队列中积累数据，就可能造成内存增长。”

“因此，要为连接设置可控的待发送数据上限。”

“对于可丢弃的互动类消息，可以考虑丢弃过期内容、合并快照或断开长期无法消费的连接。”

“对于必须可靠送达的业务通知，则应通过持久化通知记录、确认和补拉机制保证，不应该仅依赖 WebSocket 的一次发送。”

国王终于明白：

百万长连接的难点不仅是建立连接，更是如何以有限的资源持续、安全地管理消息流量。

## 第五幕：Redis 热点围城——缓存也会被击穿

凌晨一点。

商品服务突然发出警报。

一位超级主播正在介绍某件商品。

这一刻，上百万用户反复刷新商品详情。

大量请求指向同一个 Key：

```
product:detail:1001
```

国王大笑。

“我们有 Redis！这种场景正适合缓存！”

架构师却并不乐观。

“陛下，Redis 可以减少数据库查询压力。”

“但高热点 Key 仍然需要考虑 Redis 节点负载、网络吞吐和缓存失效。”

### 一、缓存穿透

国王问：

“什么是缓存穿透？”

架构师讲起一个故事。

一群恶意访客不断查询根本不存在的商品：

```
product:999999999
product:888888888
product:777777777
```

Redis 查不到。

MySQL 也查不到。

如果每个请求都继续查询数据库，大量不存在的数据请求就可能绕过缓存。

“这就是缓存穿透。”

常见防线包括合法性校验、缓存空值、布隆过滤器和限流。

### 二、缓存击穿

另一种情况：

一个超级热点商品一直存在 Redis 中。

突然，其缓存 TTL 到期。

数万请求同时发现缓存不存在。

于是，全部尝试查询 MySQL。

“这就是典型热点 Key 失效导致的缓存击穿。”

架构师写下：

```
大量请求
    ↓
Redis 热点 Key 失效
    ↓
多个请求同时回源
    ↓
MySQL 压力急剧上升
```

可考虑单飞加载、短期重建锁、逻辑过期或预热等策略，但必须明确过期数据能否被业务接受。

### 三、缓存雪崩

“陛下，假设十万个商品缓存被统一设置了相同 TTL。”

“它们在同一时刻大规模失效。”

“这就可能引发缓存雪崩。”

“我们可以根据访问分布、缓存热度等设计过期策略，也可以在合适的 TTL 基础上加入随机抖动。”

“但更重要的是回源限流与降级保护。”

### 四、缓存一致性

国王问：

“如果 MySQL 中商品价格改了，Redis 还是旧价格怎么办？”

架构师回答：

“这就是缓存一致性问题。”

“常见 Cache-Aside 策略是在更新数据库事务成功后删除或失效相应缓存。”

“但仍需考虑并发读写、缓存回填竞态、删除失败和消息传播延迟。”

“另外，支付、订单结算时的价格与库存，不应无条件相信一个可能过期的商品展示缓存。”

“展示性能与交易正确性，应分别设计。”

## 第六幕：RabbitMQ 与 Kafka——两支消息军团如何分工？

国王突然提出疑问。

“我们现在既有 RabbitMQ，又有 Kafka。”

“它们不都是消息系统吗？”

“为什么不只保留一个？”

架构师回答：

“当然可以评估合并，但必须看业务需求。”

“它们不是简单的谁先进、谁落后。”

### 一、RabbitMQ：业务异步履约

例如：

优惠券领取成功后，进入异步履约。

订单提交后，触发后续处理。

某项业务任务失败后，需要有明确的重试和死信治理。

“RabbitMQ 在很多业务任务分发场景中十分合适。”

### 二、Kafka：事件流与数据管道

例如：

支付成功事件需要被多个独立系统订阅。

用户行为事件需要保留一段时间，供风控和分析消费。

Flink 需要在故障恢复时重放仍被保留的事件。

“Kafka 的分区日志、保留策略和独立消费组适合许多此类场景。”

Kafka 的分区日志和消费组模型，使同一个 Topic 可以被不同的逻辑订阅者独立读取。

### 三、不要机械地两个都上

国王问：

“那是不是所有大型项目都需要同时使用 RabbitMQ 和 Kafka？”

“不一定。”

“如果只有少量异步任务，RabbitMQ 可能足够。”

“如果已经有 Kafka，并且业务能够接受其消费、重试和故障治理方式，也可能统一在 Kafka 上。”

“引入两套消息基础设施意味着两套监控、容量管理、故障处理和运维成本。”

“技术选择必须服务于业务，而不是为了凑齐技术栈。”

### 一、完整领取链路

```
用户点击领取
      ↓
API Gateway
      ↓
身份校验、活动校验、限流
      ↓
Redis Lua
      ├─ 已领取 → 返回
      ├─ 库存不足 → 返回
      └─ 预占成功
              ↓
可靠记录履约任务
              ↓

              ↓

              ↓
MySQL 创建领取记录
              ↓
更新最终状态
              ↓
用户查询领取结果
```

架构师说道：

“这里有几个必须说清楚的工程问题。”

### 二、预占成功不等于最终领取成功

“Redis 返回预占成功，只能说明入口阶段的资格校验和预占操作完成。”

“如果数据库履约尚未完成，接口不应该直接声称优惠券已经最终发放成功。”

“可以返回一个请求编号和处理中状态。”

例如：

```
{
  "requestId": "claim_9527",
  "status": "PROCESSING"
}
```

前端通过查询或事件通知获取最终状态。

### 三、Redis 与消息队列之间的可靠性

国王问：

“如果 Redis 已经扣减库存，但服务在消息发送前崩溃呢？”

架构师回答：

“这正是跨系统一致性的难点。”

“不能仅凭一段 Lua 脚本，就声称整个流程不会丢任务。”

“要么设计可靠、可恢复的预占任务记录与补偿机制，要么重新调整事务边界，例如使用数据库 Outbox。”

“最终方案取决于活动吞吐、允许的延迟、故障恢复要求与数据库写入容量。”

### 四、最终防线：数据库约束

架构师在 MySQL 中建立业务唯一约束。

```
CREATE TABLE coupon_claim (
    id BIGINT PRIMARY KEY,
    request_id VARCHAR(64) NOT NULL,
    user_id BIGINT NOT NULL,
    coupon_id BIGINT NOT NULL,
    status VARCHAR(32) NOT NULL,

    UNIQUE KEY uk_request (request_id),
    UNIQUE KEY uk_user_coupon (user_id, coupon_id)
);
```

“这样可以防止同一个领取请求重复创建，也能约束一人一券的业务规则。”

“不过，如果允许每个用户领取多张，约束就需要按照真实业务重新设计。”

“而数据库唯一索引也不能单独保证活动总库存不超额，还需要库存不变量的整体设计。”

### 一、为什么不能把交易正确性交给实时看板？

国王问：

“Flink 已经统计了成交额，为什么还需要 MySQL 交易库？”

架构师回答：

“因为两者的职责不同。”

“MySQL 保存订单和支付状态等权威业务事实。”

“Flink 处理事件，构建派生统计结果。”

“Redis 和 ClickHouse 中的 GMV 可以因异步处理而存在短暂延迟。”

“但这不应影响支付是否成功的最终判断。”

### 二、事件去重

架构师强调：

“消息系统可能重复投递。”

“同一支付事实如果出现重复事件，Flink 不应该简单地重复增加金额。”

“可以根据具有明确语义的支付事件 ID、订单状态版本等信息设计去重。”

“而且去重状态需要考虑生命周期。”

“如果 TTL 太短，较晚到达的重复事件可能绕过去重。”

### 三、退款和订单撤销

国王突然想到：

“如果用户支付 100 元，后来退款 100 元怎么办？”

架构师回答：

“首先要定义指标。”

“GMV、实付金额、净收入和退款后净额，不一定是同一个指标。”

“如果要统计净支付额，就需要正确处理退款事件。”

例如：

```
支付成功：+100
退款成功：-100
净支付额：0
```

“但如果一笔订单部分退款两次，需要区分不同退款事件，防止重复扣减。”

“指标口径不明确，即使计算完全没有 Bug，报表也可能与财务对不上。”

## 第九幕：高可用战争——如果整个可用区突然失联？

大促进行到一半。

突然，数据中心某一片区域发生网络故障。

大量应用实例无法继续响应。

国王震惊。

“我们有一百台服务器！为什么还会受到这么严重的影响？”

架构师回答：

“陛下，如果这一百台都部署在同一个故障域，那么它们并不一定构成足够可靠的系统。”

### 一、多可用区部署

架构师拿出地图。

“我们可以将合适的业务服务分布到多个可用区。”

```
           入口负载均衡
                ↓
     ┌──────────┴──────────┐
     ↓                     ↓
可用区 A                可用区 B
Java 实例集群           Java 实例集群
缓存/消息节点           缓存/消息节点
     └──────────┬──────────┘
                ↓
     具备故障恢复能力的数据层
```

“但必须注意，应用跨区部署不意味着数据库自动具备同等级别的容灾能力。”

“Redis、Kafka、MySQL 等有状态服务需要分别设计副本放置、故障切换与数据一致性。”

### 二、RTO 与 RPO

国王问：

“我们怎样衡量容灾能力？”

架构师写下两个指标。

RTO（Recovery Time Objective）：业务恢复时间目标。

RPO（Recovery Point Objective）：可接受的数据恢复点目标，通常体现为最多能够容忍多长时间的数据损失。

“例如，RTO 为 5 分钟，不意味着系统必然在 5 分钟恢复，而是要求架构与演练达到这个目标。”

“RPO 为 0 也不是随便增加两个异步副本就能保证的。”

### 三、限流、熔断与降级

当某个依赖服务出现故障，架构师下令：

“保护交易主链路！”

推荐服务暂时降级。

部分非关键统计更新允许延迟。

弹幕展示进行限频。

但支付、库存、订单状态等核心业务依然按照严格规则执行。

“陛下，降级不意味着可以牺牲交易正确性。”

“对于资金类操作，宁愿明确失败或者进入可追踪的待处理状态，也不能凭空宣称成功。”

### 四、自动扩容并不是瞬间完成

国王问：

“Kubernetes HPA 不是能够自动扩容吗？”

架构师回答：

“是的，但 HPA 通过周期性控制循环，根据资源或业务指标调整工作负载副本数量。”

“从发现负载变化，到新实例启动、预热、就绪、实际承接流量，需要一定过程。”

“对于已知的大促，往往还需要提前容量规划与预扩容，而不是全部依赖流量到来后的自动伸缩。”&#x20;

## 第十幕：可观测性——为什么系统没有报警，却已经影响用户？

大促结束前，国王看到监控大屏全部显示绿色。

CPU 正常。

内存正常。

服务器没有宕机。

国王满意地说道：

“系统运行得很好。”

但一名用户投诉：

“我领取优惠券以后，页面显示处理中，等了三分钟也没结果。”

架构师立即说道：

“陛下，服务器健康不代表业务健康。”

“我们需要完整的可观测性体系。”

### 一、Metrics：指标

指标帮助回答：

“问题影响有多大？”

例如：

- API QPS、错误率、P95、P99。
- JVM Heap 使用率与 GC 停顿。
- Tomcat 活跃线程与数据库连接池使用情况。
- Redis 请求延迟与缓存命中率。
- RabbitMQ 队列深度和消息等待时间。
- Kafka Consumer Lag。
- Flink 背压、Checkpoint 耗时和 Watermark 进度。

### 二、Logs：日志

日志帮助回答：

“发生了什么？”

例如：

```
requestId=abc123
orderId=9527
couponId=1001
status=FULFILLMENT_RETRY
reason=DB_TIMEOUT
```

架构师强调：

“结构化日志要便于关联，但不应该随意记录密码、Token 或敏感个人信息。”

### 三、Tracing：分布式追踪

一条用户请求可能跨越多个服务。

```
Gateway
   ↓
CouponService
   ↓
Redis Lua
   ↓
RabbitMQ
   ↓
FulfillmentConsumer
   ↓
MySQL
```

“如果使用分布式追踪，我们可以把请求路径中的多个 Span 关联起来。”

“异步消息跨越生产者和消费者时，需要正确传播 Trace Context，并合理使用上下文关联关系。”

“但不是说每一条高吞吐事件都必须以相同采样率保存完整 Trace。”

“否则观测系统本身也可能承受巨大成本。”

### 四、SLO：从机器指标转向用户体验

架构师写下：

> 99.9% 的关键 API 请求在指定统计周期内满足成功与延迟目标。

“这是一种示意性的服务等级目标。”

“真实系统需要明确什么算成功、统计窗口多长、是否排除某些请求，以及延迟门槛是多少。”

“例如支付请求返回 200，并不一定表示支付最终成功；业务指标必须对应真实用户结果。”

### 五、事故复盘

国王问：

“每次故障都要写报告吗？”

架构师回答：

“重要事故应该留下可执行的复盘结果。”

“包括时间线、影响范围、直接原因、深层原因、有效与无效的处置措施，以及后续需要验证的改进项。”

“不能只写一句‘服务器压力过大，已经扩容’就结束。”

## 第十二幕：最终验收——一次针对整个帝国的故障演练

天穹直播平台上线前最后一天。

国王下令进行完整压测。

这一次，架构师没有只检查 QPS。

他准备了四场战争。

### 第一场：峰值流量

模拟高峰期的 API 请求、长连接建立、商品查询与交易写入。

记录不同负载下的吞吐量、P99 和错误率。

同时观察数据库和缓存是否存在共享瓶颈。

### 第二场：单实例故障

随机停止若干无状态应用实例。

检查请求是否能够切换至其他健康实例。

对于长连接服务，还要验证客户端重连、房间重新订阅和消息补拉。

### 第三场：消息积压

人为降低消费者处理速率。

观察 RabbitMQ 与 Kafka 的积压增长、限流策略和恢复速度。

确保没有无界队列吞噬内存，也没有无限重试导致故障扩大。

### 第四场：数据库与状态恢复

模拟数据库主节点不可用、Flink Task 故障和 Sink 写入异常。

验证交易状态正确性、Checkpoint 恢复、事件重复处理以及最终对账结果。

架构师告诉国王：

“压测时，必须避免真实付款、真实通知和其他不可逆业务副作用。”

“故障演练应在隔离环境或具备严格防护的受控范围内进行。”
